# Contract — FIELD.SEQ.EARTH (Earth8 field sequencer)

> Ledger: `design/blocks.yml` · owner ZH-035 · phase 7 · maturity SPECIFIED

## Purpose and exclusions

Evaluate Earth8 patch programs (height/material/nav/hazard field semantics) against terrain patches; implements the E profile of ops.yml.

## This is a PROFILE, not a block

Owner ruling, 2026-08-22: **one engine, five profiles.** This contract
describes a CONFIGURATION of `FIELD.SEQ.CORE`, which is a complete Field IR
sequencer and is already `RTL_VERIFIED`. There is no separate
`FIELD.SEQ.EARTH` sequencer in hardware and there is not going to be one.

The ledger records this as `kind: profile` with
`implemented_by: FIELD.SEQ.CORE` (rule V21), which is why this entry carries
no `reference_model`, no directed or random test of its own, and no ALM
budget: the engine carries all three, and counting them again here counted
one engine five times.

**Why the five were never distinguishable in hardware.** `zhao_field_seq` has
no profile input and no profile-specific port. The thing that would
distinguish a profile -- which registers the input and output lanes bind to --
is carried by the DECODED PROGRAM (`zfield::Decoded::in_lanes` /
`out_lanes`, filled by the decoder from the image), not by the block. So a
profile is a program set plus shell wiring, not a hardware variant.

**What is still open, and it is not hardware.** The `E` profile of
`ops.yml` still needs its lane binding written down: which registers the
inputs arrive in and which the outputs are read from, per program. That is a
software and shell question, and it belongs with the blocks that consume the
output.

The sections below are the generated stubs. They are kept rather than deleted
because a profile still has an I/O contract at the shell boundary -- but they
describe a configuration of the engine, never a second engine.

## Input and output packet layouts

**The lane binding is the ratified E record** (`spec/form/field-ir.md` §7.1),
input lanes mapping to R0.. in record order:

| lane | reg | type | v3 source kind |
|---|---|---|---|
| `x` | R0 | fx | **varying** — generated by the Earth lattice walker |
| `z` | R1 | fx | **varying** — generated by the Earth lattice walker |
| `age` | R2 | u32 | uniform — field descriptor |
| `phase` | R3 | fx | uniform — field descriptor |
| `p0`..`p7` | R4..R11 | fx | uniform — field descriptor |

| output | type | reducer law at TERRAIN.PATCH |
|---|---|---|
| `height` | fx | command-ordered saturating add |
| `velocity` | fx | its exact declared accumulation (TERRAIN.VELOCITY law) |
| `material` | u32 | exact writer-selection law |
| `nav_cost` | fx | its declared reduction |

**DECLARED 2026-08-27 (Field v3 probe 5), chosen not found.** The two rows
above that POINT at laws had no declaration anywhere in the tree: no
document defined the material writer-selection and none defined nav_cost's
reduction (there is no FIELD.OUT.MATERIAL / FIELD.OUT.NAV entry in
`design/ops.yml`). Their first written forms are:

- **material**: the LAST field in COMMAND ORDER that covers the vertex AND
  writes the material lane wins, wholesale (the u32 is opaque per
  `spec/form/domains-and-effects.md` §5); the accumulator initialises to 0.
- **nav_cost**: command-ordered saturating `fx_add` chain, init 0 — the
  same one-reduction argument TERRAIN.VELOCITY's V1 makes: one evaluation
  must never be reduced by two different rules.

Declared in `fpga/rtl/synth/zhao_probe_patch_acc.sv` (the probe that first
needed them) and pinned by
`tests/differential/field_patch_acc_directed.cpp`. Recorded here for
negotiation: amending either is a contract change plus a probe-test change,
not a silent RTL edit.

Outputs take their values from the registers the program's I/O map names at
END. In v3 the plan marks those registers and writeback SNOOPS them into
per-context export registers, so END enqueues a complete four-point result
without re-reading registers through a host port.

**The Earth walker replaces point transport.** The walker knows patch origin,
pitch, lattice index, field footprint and the prepared uniform block; it
generates four `x,z` points per vector group directly. Uniform lanes live in
the scalar bank, loaded ONCE per association from the field descriptor. The
v2 generic 12-in/4-out host stream (27,225 clocks/association measured
against a 10,416 allowance) is not part of this profile's production path.

**The uniform SatLedger result** of the preparation is carried in the field
descriptor and ORed with the varying execution result, exactly as if every
point had executed the uniform instructions itself.

## Backpressure rules

Ready/valid toward TERRAIN.PATCH's field-major reducer. The walker stalls on
a full service queue or a full export queue; nothing is dropped; one result
per active vertex per accepted association, in field command order.

## Memory ownership

None of its own beyond the walker state and export registers. Programs and
FPLANs live in FIELD.PROGCACHE's store; tables in the curve service's cache;
the patch accumulator is TERRAIN.PATCH's.

## Q formats and rounding

None of its own — every value is fx16 (or the u32/material lanes) and every
rounding decision belongs to the canonical op semantics. Preparation on the
ARM uses the SAME `zref::` fixed-point primitives as `zfield::interpret`; no
floats, no approximate CPU version, anywhere.

## Latency (fixed or variable)

Variable per association (program- and footprint-dependent), bounded by the
deadline below.

## Target throughput — THE REAL DEADLINE

One full patch = 1,089 lattice vertices = **273 four-wide vector groups** if
the groups are packed flat and aligned.

**CORRECTED 2026-08-27 (Phase 4 walker): the UPDATE path costs 297, not 273,
and budgeting it at 273 under-provisions the executor by 8.8%.** The walk is
row-major — z-then-x, the cartridge patch order the reference records
velocity in — and 33 is not a multiple of 4, so a four-wide group cannot
straddle a row boundary. Every row costs `ceil(33/4) = 9` groups and a full
patch costs `9 × 33 = 297`. The last group of each row carries one live lane
of four.

273 is still the right number for the patch accumulator's INIT and DRAIN,
which walk the flat 1,089 in ALIGNED groups; probe 5 measures both (273 for
INIT/DRAIN, 297 update groups) and they are different traversals of the same
store rather than a disagreement. The 6,000-clock per-association target
below has room for 297; the correction matters because a reader budgeting
executor issue slots from this line would come up 24 groups short per
association, and 128 associations would hide 3,072 clocks.

Per-service targets (the Phase 3 probe gates; a probe that misses kills or
changes its topology before it reaches the engine):

| resource | target |
|---|---|
| vector instruction issue | 1 group instruction / clock |
| four-point CURVE II | ≤ 14 |
| four-point DIST2 II | ≤ 20 |
| vector multiply/MAD | II 1 |
| prepared RING | 9 multiplier slots / group |

**Hard per-association target: ≤ 6,000 clocks per full 1,089-vertex
association** (expected binding service ≈ 5,460 for the three committed
programs after exact uniform preparation, plus scheduling/mask/plan margin).

**Frame acceptance ceiling: ≤ 850,000 Field/Earth-slice clocks for the
128-association stress frame**, including worst-case patch init/finalise
(128 × 2 × 273 = 69,888 vector clocks) and plan/table/setup margin.

The clock decision rule: the complete measured Earth slice must finish the
frozen worst frame inside **80 %** of its actually available cycles —
1,333,333 at 100 MHz (64 %), 1,200,000 at 90 MHz (71 %), 1,066,667 at 80 MHz
(80 %), 789,600 at the current 59.22 MHz (108 % — fails).

## NOT STARTED 2026-08-19, and the sizing that says why

The TERRAIN.VELOCITY increment reached this block with budget left and did not
start it. Recorded here rather than only in a run report, so the next author
negotiates the scope instead of discovering it.

**This block is the whole Field IR machine, not a profile of it.** The ledger's
`reference_model: zref::fieldir::interpret` does not resolve (see below); the
real one is `zfield::interpret`, and it is a **31-opcode** dispatch
(`reference/src/zfield/zfield_interpret.cpp`, opcodes 0x00-0x29) over a 64x32
register file with 3-source group reads and 1-3 lane destination writes. The E
profile does not restrict it: `spec/form/field-ir.md` 7.2 says "v1: all five
profiles admit the full opcode table" and the per-profile whitelist is a hook,
not a restriction. So "implements the E profile" means implements everything.

Four of the 31 are block-sized sub-blocks in their own right, none of which
exists in `fpga/rtl/`:

| needed | law | why it is not a line of RTL |
|---|---|---|
| `isqrt_u64` | qformats 7.2 | exact floor sqrt over 64 bits; LEN2/LEN3/DIST2/NORMALIZE2/NORMALIZE3 all need it |
| `field_rcp` + `rcp_u24_norm` | qformats 6.1/6.2 | two DISTINCT reciprocals that the spec says are "never conflated"; NORMALIZE also needs a normalize-shift loop around the second |
| sin/cos | qformats 7.1 | 257-entry Q1.16 quarter-wave LUT with the quadrant fold; SIN, COS, ROT2 and ROT3 all consume it |
| the PWL table walker | field-ir 3.15 | CURVE / DCURVE / SPLINE over {x,y,dy} triples: a segment search plus three different finishes, of which SPLINE is a Hermite |

and NOISE2 wants the PCG RXS-M-XS lattice hash of qformats 7.5 on top.

**The precedent is explicit.** A previous increment refused FIELD.SEQ.STAMP as
"a block-sized project, not an increment tail" and that judgement was welcomed.
FIELD.SEQ.EARTH is the SAME interpreter with a different I/O record
(field-ir 7.1: earth takes 12 in-lanes and 4 out, stamp 8 and 3), so it is
strictly the larger job, not the smaller one. Starting a third of it and
calling it a block would be worse than not starting.

**What a future increment should do first, in this order:**

1. Land the four sub-blocks separately, each with its own constructed
   exact-equality boundaries (`isqrt` at perfect squares and at `n-1`;
   `field_rcp` at 0 — which must return `0x7FFFFFFF` and raise RCP0 — and at
   the powers of two; sin/cos at the 257th entry and at the quadrant folds;
   the table walker at a knot, exactly, and at both ends of a segment). None of
   these is in `design/blocks.yml`, so registering them is part of the work.
2. Only then the sequencer, register file and dispatch.

**A ledger deviation this block inherits, which the next author must not trip
over:** `reference_model: zref::fieldir::interpret` does not resolve. The real
interpreter is `zfield::interpret`, and it is not merely a different namespace
— **ALL FORTY `reference_function:` entries in `design/ops.yml` name
`zref::fieldir::*` and that namespace does not exist anywhere in the tree.**
The op semantics live inside `zfield_interpret.cpp`'s switch, not as callable
per-op functions, so the per-op differential tests `design/ops.yml` promises
(`tests/differential/field_*.cpp`) have nothing to call. That is a systemic
hole under the whole op table and it is NOT fixed one entry at a time; it wants
either 40 thin named wrappers in the reference or one recorded amendment
saying the switch is the reference. Deciding which is part of this block's
scope, not a side errand.
