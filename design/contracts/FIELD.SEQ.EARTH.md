# Contract — FIELD.SEQ.EARTH (Earth8 field sequencer)

> Ledger: `design/blocks.yml` · owner ZH-035 · phase 7 · maturity SPECIFIED

## Purpose and exclusions

Evaluate Earth8 patch programs (height/material/nav/hazard field semantics) against terrain patches; implements the E profile of ops.yml.

## This is a PROFILE, not a block

Owner ruling, 2026-08-22: **one engine, five profiles.** This contract
describes a CONFIGURATION of `FIELD.SEQ.CORE`, which is a complete Field IR
sequencer and is already `RTL_VERIFIED`. There is no separate
`FIELD.SEQ.EARTH` sequencer in hardware and there is not going to be one.

The ledger records this as `kind: profile` with
`implemented_by: FIELD.SEQ.CORE` (rule V21), which is why this entry carries
no `reference_model`, no directed or random test of its own, and no ALM
budget: the engine carries all three, and counting them again here counted
one engine five times.

**Why the five were never distinguishable in hardware.** `zhao_field_seq` has
no profile input and no profile-specific port. The thing that would
distinguish a profile -- which registers the input and output lanes bind to --
is carried by the DECODED PROGRAM (`zfield::Decoded::in_lanes` /
`out_lanes`, filled by the decoder from the image), not by the block. So a
profile is a program set plus shell wiring, not a hardware variant.

**What is still open, and it is not hardware.** The `E` profile of
`ops.yml` still needs its lane binding written down: which registers the
inputs arrive in and which the outputs are read from, per program. That is a
software and shell question, and it belongs with the blocks that consume the
output.

The sections below are the generated stubs. They are kept rather than deleted
because a profile still has an I/O contract at the shell boundary -- but they
describe a configuration of the engine, never a second engine.

## NOT STARTED 2026-08-19, and the sizing that says why

The TERRAIN.VELOCITY increment reached this block with budget left and did not
start it. Recorded here rather than only in a run report, so the next author
negotiates the scope instead of discovering it.

**This block is the whole Field IR machine, not a profile of it.** The ledger's
`reference_model: zref::fieldir::interpret` does not resolve (see below); the
real one is `zfield::interpret`, and it is a **31-opcode** dispatch
(`reference/src/zfield/zfield_interpret.cpp`, opcodes 0x00-0x29) over a 64x32
register file with 3-source group reads and 1-3 lane destination writes. The E
profile does not restrict it: `spec/form/field-ir.md` 7.2 says "v1: all five
profiles admit the full opcode table" and the per-profile whitelist is a hook,
not a restriction. So "implements the E profile" means implements everything.

Four of the 31 are block-sized sub-blocks in their own right, none of which
exists in `fpga/rtl/`:

| needed | law | why it is not a line of RTL |
|---|---|---|
| `isqrt_u64` | qformats 7.2 | exact floor sqrt over 64 bits; LEN2/LEN3/DIST2/NORMALIZE2/NORMALIZE3 all need it |
| `field_rcp` + `rcp_u24_norm` | qformats 6.1/6.2 | two DISTINCT reciprocals that the spec says are "never conflated"; NORMALIZE also needs a normalize-shift loop around the second |
| sin/cos | qformats 7.1 | 257-entry Q1.16 quarter-wave LUT with the quadrant fold; SIN, COS, ROT2 and ROT3 all consume it |
| the PWL table walker | field-ir 3.15 | CURVE / DCURVE / SPLINE over {x,y,dy} triples: a segment search plus three different finishes, of which SPLINE is a Hermite |

and NOISE2 wants the PCG RXS-M-XS lattice hash of qformats 7.5 on top.

**The precedent is explicit.** A previous increment refused FIELD.SEQ.STAMP as
"a block-sized project, not an increment tail" and that judgement was welcomed.
FIELD.SEQ.EARTH is the SAME interpreter with a different I/O record
(field-ir 7.1: earth takes 12 in-lanes and 4 out, stamp 8 and 3), so it is
strictly the larger job, not the smaller one. Starting a third of it and
calling it a block would be worse than not starting.

**What a future increment should do first, in this order:**

1. Land the four sub-blocks separately, each with its own constructed
   exact-equality boundaries (`isqrt` at perfect squares and at `n-1`;
   `field_rcp` at 0 — which must return `0x7FFFFFFF` and raise RCP0 — and at
   the powers of two; sin/cos at the 257th entry and at the quadrant folds;
   the table walker at a knot, exactly, and at both ends of a segment). None of
   these is in `design/blocks.yml`, so registering them is part of the work.
2. Only then the sequencer, register file and dispatch.

**A ledger deviation this block inherits, which the next author must not trip
over:** `reference_model: zref::fieldir::interpret` does not resolve. The real
interpreter is `zfield::interpret`, and it is not merely a different namespace
— **ALL FORTY `reference_function:` entries in `design/ops.yml` name
`zref::fieldir::*` and that namespace does not exist anywhere in the tree.**
The op semantics live inside `zfield_interpret.cpp`'s switch, not as callable
per-op functions, so the per-op differential tests `design/ops.yml` promises
(`tests/differential/field_*.cpp`) have nothing to call. That is a systemic
hole under the whole op table and it is NOT fixed one entry at a time; it wants
either 40 thin named wrappers in the reference or one recorded amendment
saying the switch is the reference. Deciding which is part of this block's
scope, not a side errand.
