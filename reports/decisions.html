D-1 · the clamp in the flat-shade law
Where does the shade get clamped?
BLOCKS: TERRAIN.SHADE and TERRAIN.NORMALMAP RTL — nothing gets built until this is answered

shade_flat_tri_dir clamps to [0, 0x10000] inside the function. Any additive term — detail normals, a second sun, a spell light — has to be summed before that clamp, or it can't brighten a face that's slightly turned away.

  • (a) the law grows an unclamped variant; the clamp moves to where shade becomes colour
  • (b) the additive term is passed into the function, so one function owns sum and clamp
Recommend (a). Keeps detail out of a function terrain and creatures share, and it's a pure refactor — the golden CRCs must not move, which is also how you'd know it was done right.
D-2 · cartridge resource kinds
Where do texture and material bytes live?
BLOCKS: MATERIAL.RESOLVE, and generic upload for everything

.zpak has no generic texture-page or material-set kind — while creature parts claim texture pages, terrain names tilesets, and DrawForm takes a material-set handle.

  • (A) generic TEXTURE_PAGE + MATERIAL_SET + MESH_STREAM
  • (B) every family page carries its own subpages, one nested layout
  • (C) generic immutable RESOURCE_BLOB + typed manifests
Recommend A. Only A lets MEM.UPLOAD be one general mover for all immutable assets, and only A gives the texture cache's invalidate one obvious publisher. B needs three family loaders to agree forever; C adds indirection this console has refused elsewhere.

Default if unruled: every asset compiler invents its own layout — the thing the audit names as what cannot work.

D-3 · cache coherence
How does a new upload stop the old bytes being served?
Invisible when wrong: correct memory, wrong picture, no counter moves

The texture cache already has invalidate inputs and notes that an uploaded palette page otherwise leaves stale data. Nothing drives them.

  • (a) drive an explicit invalidate at the caches holding that resource
  • (b) bind the cache tag to the resource generation, so an old line can't match a new request
Recommend (b). Structural rather than procedural, needs no list of who caches what, and the generation is already carried for staleness.
D-4 · depth quantisation
Separate block, or a stage inside GEOM.PROJECT?
Twelve files consume invw24; the producer emits Q16.16 1/w

Either is fine. The audit is specific only about the alternative: "just do not leave it in integration glue."

Either — (b) is arguably tidier since the reciprocal is produced there. I registered it separately only because adding unbuilt work to a built, verified block hides that work inside a green row.

Default if unruled: it stays glue, differently in each of the twelve places.

D-5 · fog
Who carries fog, and does cel fog before or after toon?

The arithmetic is specified. RASTER.FRAGMENT says colour arrives already fogged — and GEOM.PROJECT has no colour input to have fogged it with. SetEnvironment is still a reserved command.

  • general law today: lighting → fog → interpolate → toon
  • cel probably wants: unfogged lighting → interpolate → toon → texture → fog
Recommend GEOM.LIGHT carries it, and rule the cel ordering as the second one — fogging before toon quantises fog into hard bands. Do it before the colour packet freezes; afterwards it's an ABI change rather than a wiring choice.

Default if unruled: fog is never carried at all. Nothing breaks; the game just has no distance haze.

D-6 · local spell lighting
Do fireballs light the world?

Prose today, not a format. The failure mode is specific: if giant magical fireballs bloom but cast no coloured light onto nearby creatures, terrain or structures, the effects look pasted onto the world.

Recommend this table as v1: creatures/objects → bounded top-K diffuse lights · terrain → sun + broad spill / global flash, not every point light · particles/spells → emissive/additive + existing glow tags.

And: the accumulator does not need K permanent engines merely because K terms are legal.

Default if unruled: no dynamic lights. Safe for the machine, costly for the look.

D-7 · water and lava
Does the game want liquid surfaces — yes or no?

TWOD.PLANE explicitly refuses to be a general world-depth plane; intersecting liquid must be triangles through the main renderer. That's fine and needs no hardware.

Recommend: answer it either way. If yes, freeze the cheap v1 (low-poly surface, scrolling texture, alpha or additive, optional vertex waves, explicit depth-write policy, no reflection, no refraction, explicit sorting). If no, delete the phrase from the ledger.

The danger is neither option — it's the stale phrase "water/lava" making someone assume a solution exists when the plane engine refuses the relevant depth behaviour.
D-8 · normal maps beyond terrain
Refuse general tangent-space normal maps in v1?

The terrain normal-map unit is cheap precisely because a heightfield's tangent frame is world-axis-aligned. It does not generalise to creatures or props, which need a real tangent frame per vertex.

Recommend: refuse explicitly, in writing. The danger is someone inferring that the terrain block generalises and budgeting as if it does. Cheap to prevent now.

Not a decision, but owed: the near-plane law drops an entire triangle when any vertex is behind the eye. Deliberate and documented — but it needs a close-camera stress reel (giants, Zixx, beams, large terrain triangles) because it can visibly pop geometry, and only watching it tells you how badly.
