# M2's deletion trigger: are its preconditions actually met?

`design/prod_manifest.yml:69` still carries:

```
- zhao_texture_combine       # REFUTED (D19q); delete when v1 is measured
```

and above it, the written instruction: *"When that fit lands, delete this row,
its RTL, and `tests/texture/texture_combine_diff.cpp` together."*

**Deletion is the owner's call. This is the analysis that has to precede it
whoever makes it, and it turns up a complication.**

## Current state, read today rather than from the docket

| block | ALM | reg | Fmax | status |
|---|---|---|---|---|
| `zhao_texture_combine` (refuted, D19q) | 494 | 524 | 100.12 | **failed:structure** |
| `zhao_texture_material_combine_v1` | 1,475 | 893 | **36.28** | ok |
| `zhao_texture_material_combine_v2` | 870 | 918 | **114.04** | ok |

Still true: the refuted block remains in the production manifest **and** is
instantiated by `zhao_prod_top` at :4456.

## The complication: V1's measurement cannot be verified

**V1's fit predates the provenance guard — there is no `.sources.sha256` for
it.** So there is no way to confirm from artefacts that the recorded 1,475 ALM /
36.28 MHz describes the file on disk now.

I first called it stale because the source mtime is newer than the fit summary.
**That was the wrong test and I withdraw it:** git shows no commit touching
`zhao_texture_material_combine_v1.sv` since 2026-09-06, and this tree's CRLF
normalisation moves mtimes for reasons unrelated to content. Using mtime as a
proxy for "the file changed" is the same class of error as measuring a drawing
to get a 3D radius — a real number standing in for the thing you actually meant.

The content is *probably* unchanged. **"Probably" is exactly what a deletion
trigger should not rest on**, and the fix is cheap: re-fit V1 when the toolchain
frees. That also produces the digest that was missing, so the next person does
not repeat this.

## A separate finding, and it is the more valuable one

**`zhao_prod_top` instantiates V1 while the texture island uses V2**, and V1
runs at **36.28 MHz against a 100 MHz product clock**. V2 is 870 ALM at 114.04.

I checked whether the swap is mechanically possible:

```
V1 ports: 26 | V2 ports: 27
in V1 only:  none
in V2 only:  phases_issued_o   (an output)
shared names with different direction: none
```

**V2 is a strict superset of V1's interface.** Every existing connection maps
unchanged; the single new port is an output. So the production top can take V2
without a port change — and `zhao_prod_top.sv` is generated by
`tools/quartus/gen_prod_top.py`, so the edit is to the manifest plus a
regeneration, not hand-wiring.

That is a **-605 ALM and +77.76 MHz** change to a block currently sitting three
times under the product clock in the production top. It is not in the running
fit's closure.

## Recommended, for the owner

1. **Re-fit V1** behind the island fit — closes the unverifiable-measurement
   gap and produces its missing digest.
2. **Then execute M2's trigger** as written: the manifest row, the RTL and
   `tests/texture/texture_combine_diff.cpp`, together.
3. **Separately, move `zhao_prod_top` to V2.** Superset interface, measured,
   and it removes a 36 MHz block from a 100 MHz machine.

None of the three is done here. 1 needs the toolchain; 2 and 3 are deletions and
production-composition changes, which are the owner's call, not a barge-ahead.
