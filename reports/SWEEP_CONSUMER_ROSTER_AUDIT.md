# Guard 7 audit: who actually elaborates each swept file

Generated by `tools/sweep_consumers.py`, 2026-08-28.

Guard 7 says a sweep must not mutate a file that a target it does not run
also elaborates -- that target's model would carry mutant-derived code nothing
scores. Every driver implemented it as `grep -B12 "TOP_MODULE <module>"`, which
reads the file's role as a TOP and misses every use of it as a SUBMODULE.

That held while each swept block was its own top. It stopped holding the moment
one was composed: `zhao_probe_v3_exec` became a submodule of
`zhao_probe_v3_engine` and the grep returned NOTHING, so the sweep aborted
naming an empty roster. Correct refusal, useless diagnosis.

This table reads SOURCES instead, expanding the `set()` variables most raster
and terrain cones are written with -- a literal-only scan reports "nothing
elaborates this" for five drivers, which is the same false all-clear wearing
the other face.

## What the gaps mean

A consumer that is not run is not automatically a defect. The sweep rebuilds
only its own targets, so the others keep PRISTINE models for the whole run --
provided nothing else builds, which `tools/run_sweep_detached.sh` already
forbids. What the gap really costs is COVERAGE: a mutant that breaks only the
tile pipe's use of `zhao_raster_earlyz` survives this sweep and looks like a
hole in the block rather than a hole in the roster.

The three drivers with no `TARGETS=` line at all (`debug_crc`, `geom_cull`,
`geom_lod`, `geom_skin`) predate that convention and were not audited here.

The v3 drivers now assert the real rule: every target run must elaborate the
file, and every other consumer must be named in `UNRUN_CONSUMERS` with a
reason. The rest still carry the old grep.
