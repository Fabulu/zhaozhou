## 5. THE TRAPS — every one of these cost someone hours today

**Environment**

* **Bash is broken in this tree** (profile parse error mangles the command).
  PowerShell only.
* PowerShell 5.1 mangles multiline `git commit -m`. Always `git commit -F file`.
* In a PowerShell double-quoted string the **backtick is the escape character** —
  writing a comment containing a backtick-r sequence injected carriage returns
  into three source files.
* `Get-Content | -join` round-trips mangle UTF-8. Use
  `[IO.File]::ReadAllText`/`WriteAllText`.
* `git show HEAD:f > out` prepends a **UTF-8 BOM**; `git diff > out` from a
  `powershell -File` subprocess writes **UTF-16**. Use `git diff --output=`, and
  join patch lines with explicit LF (`WriteAllLines` emits CRLF and breaks
  `git apply`).

**SystemVerilog / toolchain**

* A comment line whose first token after `//` is the word **"verilator"** is
  parsed as a PRAGMA and fails the entire lint with `%Error-BADVLTPRAGMA`.
* **`verilate()` does not pass `-Wall`**, so `-Wall` errors in RTL go unseen by
  every test target. Lint explicitly. UNUSEDSIGNAL found three real correctness
  holes today, including a response port carried and never read that would have
  published a corrupt page.
* Quartus 17.0 rejects: inline `for (genvar ...)`; module-scope `if` elaboration
  guards (use `initial begin ... end`); implicit generate (needs explicit
  `generate`/`endgenerate`); unary minus on a size cast `-W'(x)` (needs
  `-(W'(x))`).
* A Verilated test main that `return`s instead of calling **`zhao::exit_hard`**
  hangs under ctest for the full timeout at ~0 CPU with an empty output file —
  `tests/harness/zhao_sim.hpp` documents the libwinpthread deadlock. **~0 CPU
  after minutes means BLOCKED, not slow.**

**Git, with several packets running — read this twice**

* **The index is SHARED.** `git commit` with no pathspec commits the WHOLE index,
  including other packets' staged work. Check `git diff --cached --name-only`
  before every commit.
* **`git commit --only` is WRONG for shared files** — it takes WORKING-TREE
  contents, sweeping in others' uncommitted edits. Correct only for files you
  exclusively own. It also cannot name untracked files.
* **The working recipe** is a private index:
  `$env:GIT_INDEX_FILE` + `git read-tree HEAD`, `git apply --cached` only your
  hunks, commit, then `git reset -q HEAD -- <paths>` (a private-index commit
  advances HEAD without touching the shared index, so your paths then read as
  staged REVERTS to everyone else).
* **`read-tree` and `commit` MUST BE ATOMIC.** Run them in separate tool calls
  and any packet committing in between makes your index describe the past — your
  commit then silently reverts everything they landed. This happened twice today,
  once for 529 deletions. Every local signal looks fine; **the only tell is the
  commit summary reporting more files than you staged.**
* If a shared file gains another packet's hunk between your read and your add,
  stage by **excluding their hunks** rather than naming yours.
* **Lint and smoke the EXACT BLOB you will commit**, via `git archive HEAD` or an
  isolated `git worktree` — not the working tree. Two packets produced broken
  staged blobs the working tree never showed.
* `git checkout -- <file>` **discards** another agent's uncommitted work and
  unstaged changes have no reflog.
* **The scratchpad is shared between agents.** Prefix every temp file.
* **A private index protects another agent's INDEX and does NOTHING for their
  WORKING TREE.** A packet rewrote `design/prod_manifest.yml` between another's
  edit and its `git add`; eight lines were lost and the wrong packet's line went
  into the wrong commit. The fix that works: build the blob from HEAD **plus your
  own lines**, install it with `git update-index --cacheinfo`, and assert the
  staged path count.
* **`open(p,'wb').write(build(open(p,'rb').read()))` TRUNCATES ON EXCEPTION.**
  Python creates the write handle BEFORE evaluating the argument, so when
  `build()` raised on a mismatched anchor it left `design/prod_manifest.yml` at
  **zero bytes**, destroying another packet's uncommitted row — which has no
  reflog. Read fully, transform, then open for writing. This is CLAUDE.md's
  zero-byte-backup lesson in new clothes and it cost real work today.
* **A generated file is ZERO BYTES while its writer runs.** `design/prod_manifest.yml`
  was observed empty for ~2 minutes while a packet rewrote it. It recovered, but
  the writer truncates before writing, so a crash in that window leaves an empty
  manifest — and every gate that reads it then passes or fails about nothing.
  This is CLAUDE.md's zero-byte-backup lesson in new clothes. If a gate suddenly
  reports something absurd, check the file has bytes before believing it.

Three silences on one array:

2. **Quartus's own uninferred list.** The map report carries 46 `Info (276004)`

It says clean today while the array is flops; it will say clean afterwards

only visible to the fitter"* is also a real answer.

### The second target, already diagnosed and NOT yet assigned

`zhao_forge_assemble` holds **37,644 registers in its own node**, and
`pos_q [MAX_VERTS] + inv_q [MAX_VERTS]` at `MAX_VERTS = 520` and `POSW = 43` is

both are the checker's own rules:

* **an asynchronous RESET LOOP over the array** -- `:710-713`, `for (k = 0; k <

* **a combinational read** -- `:579-580`, `wire [POSW-1:0] pos_rd_c =
  pos_q[rd_a_q];`, a continuous assignment through a dynamic index.

**It is therefore NOT free**, and that is the honest difference from PALRAM:
removing the combinational read costs a pipeline stage on that path, and the
reset loop has to be replaced by an explicit validity discipline rather than
simply deleted. Both are real design changes with real timing consequences, and
neither should be waved through as an area win.

wrong place. **Reducing them is an architecture question, not a conversion**,
and pretending otherwise would put a cheap label on expensive work.

## 15.23 - 45 MULTIPLIERS IN 164 LINES, MEASURED STANDALONE IN 14 SECONDS

15.22 named `zhao_geom_attrsetup` as the first DSP packet on the strength of an
entity-table row. **It is now measured directly**, and it cost fourteen seconds:

```

  Total DSP Blocks       45
  Total registers       225
  Block memory bits       0
  digest bd84da4c2517, rtlCleanAtHead true
```

**45 DSP — 40% of the entire shipping device — from 164 lines.** The standalone
row matters: nothing about the composition is inflating it, and the block is the
densest DSP consumer in the console outside the per-pixel tile pipe.

| DSP Block Usage Summary | used |
|---|---:|
| **Independent 27x27** | **24** |
| Two Independent 18x18 | 15 |
| Sum of two 18x18 | 6 |
| Fixed Point Dedicated Pre-Adder | 6 |
| Fixed Point Dedicated Output Adder Chain | 6 |

### The hypothesis, stated as one

**Every multiply in the block is declared far wider than its operands can hold**,
and DSP inference follows declared width:

* `n0_c = 96'(w0_0) * 96'(va_i) + ...` — `w` is 46 bits, `va` is 32. Declared
  **96 x 96**.
* `dndx_c = (-(72'(cy_by))) * 72'(va_i) + ...` — a coordinate difference is 22
  bits. Declared **72 x 72**.
* `w0_0 = -(46'(cx_bx) * 46'(by_i)) + ...` — operands 22 and 21. Declared
  **46 x 46**.

**And the block says so itself, with reasoning that is correct about the wrong
resource:** *"96 is carried so the widths are obviously sufficient rather than
exactly sufficient — this block is once per triangle, not per pixel."* That is a
sound trade against **ALUTs and latency**, and it is exactly why the block is only
938 ALUTs. **The cost landed in DSPs**, on the ceiling that is 335% breached.

**This is NOT established and must not be quoted as though it were.** Quartus
does strip redundant sign extension in some shapes, and the 24 `27x27`s may not
decompose the way the declarations suggest. *"I can see a wide literal"* is not a
measurement. The experiment settles it in fourteen seconds a run and
`BRIEF-ATTRSETUP.md` demands one change at a time.

### The line that may not be crossed

The block's whole justification is that it emits **exactly** the oracle's
numerator, *"proved over 32,805 pixel-attributes and five triangle shapes in
`tests/proofs/attribute_plane_equivalence.cpp`"*. So **narrowing a MULTIPLY is
legal and narrowing a RESULT is not** — multiply at the operands' true widths,
sign-extend the product, leave `n0_o` at 96 bits and `dndx_o`/`dndy_o` at 72,
and the emitted value is bit-identical. The header's bounds argument **is the
specification of those output widths**, not commentary on them.

Reducing precision to save a DSP is the owner's fenced move (*"NOT authority to
… waive a correctness failure, or call reduced work equivalent merely to … fit a
device"*), and if the ceiling cannot be met without losing bits, that is an
escalation rather than a decision.

### And if the widths are not the answer

Then the block genuinely needs 45 multipliers, and the question becomes R1 and R4
— the reusable quarter-square primitive, the 26+6 hybrid, the coefficient-table
primitive, the colour/fog replacements — which the rescue roadmap has recorded as
**absent** since it was written. A quarter-square trades a multiplier for two
lookups and an adder, and **memory is the resource we have**: 53% used, roughly
259 M10K free. That is PALRAM's lever pointed at a different ceiling.

**The brief forbids starting an R1 primitive speculatively**, and says to price
it first. A general primitive written before anything consumes it is how this
campaign acquired blocks nothing reads.

### ANSWERED 2026-09-26 BY THE ATTRSETUP PACKET -- AND THE HYPOTHESIS WAS WRONG

`zhao_geom_attrsetup` is **45 DSP -> 36** and 940 combinational ALUTs -> 836,
registers unchanged at 225, every emitted bit identical. But **the declared
widths above are innocent, all three of them.** Eight arms of
`tests/probes/zhao_attrsetup_mul_probe.sv`, one change each, ~14 s a map:

| arm | change | DSP | 27x27 | ALUT |
|---|---|---:|---:|---:|
| 0 | nothing (POSITIVE CONTROL) | 45 | 24 | 940 |
| 1 | `w0_0..w2_0` 46x46 -> 22x21 | 45 | 24 | 940 |
| 2 | `n0_c` 96x96 -> 46x32 | 45 | 24 | 940 |
| 5 | `dndy_c` only, 72x72 -> 22x32 | 45 | 24 | 940 |
| 6 | `dndx_c` only, 72x72 -> 23x32 | **36** | 15 | 836 |
| 7 | `dndx_c` negation moved OUT, **widths left at 72** | **36** | 15 | 887 |
| 3 | both partials narrowed (SHIPPED) | **36** | 15 | 836 |

Arms 1, 2 and 5 are the plain `WIDE'(narrow) * WIDE'(narrow)` shape and cost
**exactly nothing** -- Quartus 17.0.2 already strips that sign extension. Arm 7
names the cause: it changes no width at all and recovers all nine blocks. **The
cost was NEGATING THE SIGN-EXTENDED VALUE.** `-(sext(x,72))` is a 72-bit
subtract from zero, and after it the top 50 bits are no longer a recognisable
replication of the sign bit. `dndy_c` never negates, which is exactly why arm 5
is flat. The same file proves the distinction twice: its edge products negate
the **product**, `-(46'(cx_bx) * 46'(by_i))`, twelve lines from the partials
that negated the **operand**, and only the second shape cost anything.

**So §15.24's instruction to hunt declared widths in the other census blocks is
withdrawn.** The pattern that pays is **an arithmetic operation applied to a
widened value before the multiply**, not a wide literal;
`tools/budget/dsp_mode_census.py`'s header carried the wrong diagnosis and now
carries this one. A grep of `fpga/rtl` finds the `-(WIDE'(x)) * ...` shape
**nowhere else in production** (the pattern was verified to fire on the
pre-repair line before its silence was believed).

The console should now be **375 -> 366** against the shipping 112 -- and that
366 is an INFERENCE, not a measurement. It rests on §15.24's finding that the
standalone counts match the composed entity table exactly, so a leaf DSP is a
console DSP one for one. **No console fit has been run since the repair**, and
the next one is the thing that confirms or refutes it. **This does not close
the ceiling and must not be read as progress toward it** -- 36 is still 32% of
the part in one block. What remains there is 15 multiplies at genuine widths and
there is no further declared-width money in it. The next levers are priced, not
started, in commit `d33fee02` section 7: attrsetup **time-multiplexing** (its
sibling `zhao_geom_attrpack` already runs three lanes through one shared core
and its header says the decision "is in the OPERAND MUX, not in the
arithmetic") ahead of R1/R4, whose ALM cost is unmeasured and lands on the
ceiling that is already 3.5x over.
