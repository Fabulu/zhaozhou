0. THE DECISION
===============

Keep V3. Do not build V4 to explain the first V3 fit.

The first V3 composition costs 13,133 ALMs, 20,561 fitted registers, 45 M10Ks,
and 17 DSP blocks. Its reported first-corner Fmax is 82.41 MHz. That is a real
baseline, not an end-state success. The full timing report is less flattering:
the second slow corner reports 81.58 MHz, and the worst multicorner hold slack
is -4.346 ns. Neither number is a statement that the hardware is safe to run at
that frequency. [S01-S04]

The next work should change SPECIFIC representations and boundaries:

  A. Repair the remaining verification-contract defects without pretending the
     whole architecture is broken. Preserve the newly working ingress-class and
     identity-error wiring. Replace or retire the expander's algebraically dead
     overflow monitor. Keep the corrected zero-work test; do not redesign the
     owner to cure the test's now-retracted memory-environment failure.

  B. Run a small palette timing experiment before undertaking another large
     surgery: count lookups/stale/cold from the ALREADY REGISTERED lookup verdict.
     This moves statistics off the same-cycle request-to-verdict-to-counter cone
     without changing palette contents, lookup legality, or colour latency.

  C. Recover the previous brief's FULL response metadata design: one synchronous
     common-stream join carrying sample metadata AND palette identity AND the
     descriptor's owner generation. The working candidate's 21-bit description
     is not the complete design and does not remove the palette-binding reads
     on the measured critical family. The existing 40-bit proposal was right to
     include those fields; do not accidentally optimize the wrong subset.

  D. Pipeline the actual island RCP service's PREPARATION path. Allocate and
     reserve a context at acceptance; carry raw input and token through bounded
     normalization/seed stages; expose that context to the existing micro-job
     scheduler only after initialization has completed. Keep the existing S1
     selection reservation and exact reciprocal arithmetic.

  E. Make final acceptance a joint predicate: intended functionality, sustained
     workload, allocated resources, and complete timing checks on the SAME
     specimen. A headline Fmax, a passing fitter process, or a historically green
     colour test is not a substitute for that predicate.

Do not launch four enormous full-island fits merely to make the work look
scientific. Use small functional/leaf experiments first. Compose independently
validated changes at an explicit milestone when that is the economical choice;
label the result as a combined change rather than inventing individual MHz
contributions. Preserve sufficient evidence to split it later if a regression
actually needs attribution.

This order is deliberately different from "the RCP is 0.041 ns worse, therefore
it must be the first edit." At the sampled slow corner the RCP input path is
-2.134 ns, while the palette counter family is already -2.093 ns. They are
practically co-limiters. The cheapest well-targeted experiment can go first;
there is no credible claim that either repair alone will close the island.
[S03-S07]

Do not use the historical 7,500-ALM limit as a physical cliff. Keep it as a
historical-rule result. Product allocation is a separate decision requiring a
count-once whole-console resource projection. The first fit has not established
that 13.1k is acceptable, but neither has it established that an 11-12k island
would be a disaster. Registers are an architecture/packing diagnostic, not a
second imaginary chip-capacity emergency. [S01, S22]

================================================

1.1 What was actually fitted
----------------------------

The first V3 composition was measured on provisional 5CSEBA6U23I7 with Quartus
Prime Lite 17.0.2. The fitter completed at 10:07:37 CEST on September 8. The
normal TimeQuest report ended at 10:10:38. The measurement entry records 18

                                      Legacy Stage A       First V3
  Top                                 island_top           island_v3_top
  ALMs                                11,562               13,133
  Fitted registers                    19,203               20,561
  M10K blocks                         39                   45
  Memory bits                         45,624               54,014
  DSP blocks                          17                   17
  First reported Fmax                 84.03 MHz            82.41 MHz

The clean comparison is +1,571 ALMs, +1,358 registers, +6 M10Ks, and no DSP
change. The headline Fmax difference is -1.62 MHz; a matched multicorner
before/after comparison is not supplied by merely subtracting those headline
values. [S01-S03, S22]

The 746 ALMs identified as containing virtual pins are NOT 746 demonstrably
removable ALMs. Useful logic may share them. Do not subtract them from 13,133
and call the remainder the production core. There are 1,491 virtual pin bits;
that boundary is a characterization choice, not the finished console wiring.
[S01]

The increase does not prove V3 was the wrong migration. It does prove that the
migration has not paid for itself in area yet. Avoid both extremes: "V3 failed,
start over" and "it is correct architecture, therefore the cost is irrelevant."
The next storage and control changes must earn their costs in measurements.

The current report parser selects the FIRST regex match for a restricted-Fmax

Hold and other timing requirements must be checked separately; reducing the

Therefore the next brief cannot promise "82 -> 100 MHz" while ignoring hold.
There are TWO physical questions:

  Can all setup paths satisfy the 10 ns period with the required interfaces?
  Are all short-path, reset, clock, and other required timing checks legal?

That is NOT a prediction of the next placement. It is a demonstration that

2.2 Repair C is wired, but the event is still identically false
--------------------------------------------------------------

The new expander counter is: [S11, S15]

  fq_full_c = (fq_occ_c >= FQD)
  f_ready_o = !fq_full_c
  accept_c = f_valid_i && f_ready_o

  if (accept_c && fq_full_c)
      wq_overflow_o <= wq_overflow_o + 1

Substitution gives:

  f_valid_i && !fq_full_c && fq_full_c

This is false for every Boolean value, including a corrupt occupancy value.
The counter and the top-level sticky derived from it can still synthesize to
constant zero. The code no longer has an undriven source, but it has not gained
a meaningful baseline hardware observable. This is a SOURCE finding, not an
unperformed FPGA fit claim.

There is a particularly revealing mutation. Change the common fullness test
from occupancy >= 4 to occupancy > 4. The queue now admits a fifth entry. The
monitor still cannot fire, because both acceptance and detection consult the
same wrong predicate in complementary form. Our independent C1 check includes
this case.

A mutation that forces f_ready_o high independently of full CAN make this
monitor fire. That demonstrates the instrument in a DIFFERENT circuit. It does
not prove the normal synthesized circuit retains a usable detector, and it does
not detect a shared-definition error in the existing form.

Choose one honest policy:

  Policy C-a, verification only:
    Keep the queue safety properties as simulation/formal assertions. Version or
    retire the legacy hardware port rather than advertising a constant-zero
    signal as runtime protection. An interface compatibility tie-off must be
    identified as unsupported observability, not "preserved overflow detection."

  Policy C-b, bounded hardware integrity monitor:
    Detect a separately meaningful state violation, for example the extended
    pointer-difference occupancy exceeding the legal depth, with a sticky event
    and a declared detection latency. Derive the legal limit independently of
    the producer-ready expression. Check invalid state encodings or mismatched
    committed-write/reservation accounting only where those independent facts
    already exist. Inspect synthesis to confirm the monitor's intended logic
    survives, and inject the relevant state/commit faults in the verification
    model.

C-b is not a promise to prevent the first bad write. A post-edge range check
may report corruption after it happened. Say that explicitly. Do not build a
second complete queue engine merely to monitor the first. A small independent
range check plus strong assertions can be the right boundary.

Ordinary valid && !ready remains legal backpressure and must not become a
fault. No need to redesign the functioning FIFO to preserve a misleading old
port name.

The same retraction mentions a garbage-valued cnt_combine_jobs_o. Its added

3. VERIFICATION: MAKE THE ENVIRONMENT PART OF THE CONTRACT
=========================================================

3.1 Admission is not completion
-------------------------------

The existing fault probe is useful for checking whether an invalid class was
COUNTED AT ADMISSION. Its first phases do not supply texture memory and only
check that some traffic was admitted. They cannot establish "healthy traffic
continues to complete after the fault." These are different claims. [S12, S14]

Retain two explicit tests rather than making one misleadingly broad:

  INGRESS-OBSERVABILITY test:
    bounded admission stimulus, exact accepted-beat counting, illegal class
    counter delta equals the number of accepted illegal beats, legal stalls do
    not count again, and legal admission still works afterwards.

  END-TO-END RECOVERY test:
    real fill responses, palette setup, AUX response model where needed, all
    accepted fragments tracked to ordered terminal results, and finite queues
    drained. Inject an allowed fault, check its exact terminal/diagnostic
    semantics, and require later legitimate fragments to retire correctly.

A safety property can be tested with responses withheld. A liveness property
requires stated fairness or response assumptions. "The memory never answers"
is an appropriate test of bounded storage and backpressure; it is not a test
that can require eventual completion without an explicit cancellation protocol.

3.2 Phase boundaries must be explicit
-------------------------------------

Before changing the test's workload or global binding mode, either:

  - finish every accepted obligation, including posted responses and delayed
    diagnostic events, then establish quiescence; or
  - reset/cancel under a specified test contract and establish a fresh epoch.

A few hundred idle clocks are not a proof of drain. Count submitted versus
retired work, check service obligations, and print the first unresolved token
rather than a global "stuck" headline. Resetting between isolated cases is
legitimate. It does not test cancellation of late external responses; that
requires a different case with those responses actually modelled.

3.3 Preserve the useful existing gates, but do not freeze their coverage
----------------------------------------------------------------------

The 541-check owner suite, 119-check composed suite, and 392-record paired
compatibility run remain valuable historical gates. They should remain intact
as regression coverage, not be discarded because a new input family was absent.
Their scope is not "all possible texture traffic." [S21-S22]

Extend coverage with targeted schedules rather than only growing a headline
check count:

  - zero samples with and without AUX, mixed with one/two/three-sample traffic;
  - changing palette slots/generations and material recipes on adjacent owners;
  - response bursts meeting an abrupt downstream stall;
  - a returning stale/future token beside legitimate traffic;
  - completion, retirement, and admission around full and wrap boundaries;
  - nonuniform texels and asymmetric filter fractions that expose wrong joins.

Every meaningful check needs a distinguishing bad case. A comparison of two
systems that share the same wrong driver is still a comparison of two wrong
systems. Keep the reference result computation and transaction-specific data
checks, not just identical output files.

3.4 Do not conceal an expected failure in the ordinary green result
------------------------------------------------------------------

Keeping an intentionally failing development probe outside the ordinary green
suite can be reasonable temporarily, but it is NOT coverage in that suite.
Track its expected failure, command, and activation condition explicitly. When
the test is fixed/passing, register it with its intended labels. Where a known
failure remains, use a separately visible quarantine/expected-failure lane;
absence from ctest must not be summarized as "everything passes."

The repaired nine-check zero-work probe was registered in ctest by commit
276e4be1 at 10:57:28 CEST during this review. Preserve that completed step.
The broader runtime fault coverage for identity and capacity remains an
additional obligation. [S26]


4. PALETTE TIMING: SPLIT THE VERDICT FROM THE STATISTICS
======================================================

4.1 Read the actual cone
------------------------

The CLUT queue head's token indexes top-level palslot_m and palgen_m. Those
values drive the palette leaf's selected generation/residency checks and its
same-edge accepted-BEGIN forwarding. The verdict currently ALSO drives the
stale/cold counter update on that same edge. [S05-S06]

The source therefore contains this long structure:

  class-queue pointer
    -> queued route-token selection
    -> 64-owner palette-binding selection
    -> resident palette slot/generation selection
    -> accepted-BEGIN / stale / resident classification
    -> 32-bit diagnostic-counter update

The setup report's cq_rp -> cold_o/stale_o endpoints agree with this structural
explanation. This is not a claim to have read every placed net in the oversized
full-detail report. [S04-S06]

The 21-bit sampmeta row contains format/fractions/sub-byte selectors. It does
NOT contain the palette slot or palette generation. Moving only those 21 bits
cannot, by itself, remove the two palette-binding selections named above.

4.2 Experiment P-CNT: use the verdict register already present
-------------------------------------------------------------

The palette already captures:

  l1_v_q      -- lookup accepted on the preceding edge
  l1_stale_q  -- captured stale verdict, including same-edge BEGIN
  l1_res_q    -- captured residency, excluding same-edge BEGIN
  l1_data_q   -- synchronous RAM result

Proposed counter structure, expressed as semantic pseudocode:

  on each clock, after reset handling:
      if l1_v_q:
          lookups_o += 1
          if l1_stale_q:
              stale_o += 1
          else if not l1_res_q:
              cold_o += 1

Do not change the RAM read, lookup output valid, lookup data, or accepted-BEGIN
forwarding in this experiment. Only the counters consume the registered
classification instead of the live request classification. [S05]

The old cold condition was !res_r[lu_slot] under !stale. The new condition uses
!l1_res_q under !l1_stale_q. They represent the same accepted event: an accepted
same-slot BEGIN implies stale, so it cannot enter the cold-only branch. This
partition was exhaustively checked over the four Boolean inputs in C3.

4.3 The latency change is real and must be declared
--------------------------------------------------

At the public counter ports the three counts are now one cycle later. This is
not cycle-by-cycle equivalence. A correct acceptance condition is:

  original_count = retimed_count + pending_captured_event  (modulo 2^32)

After one extra event-drain edge, the counts agree. Reset clears the pending
valid and counters under the same reset contract; do not allow a pre-reset
captured event to increment a new frame's counters after reset.

If a consumer samples these counters as an atomic frame snapshot, move that
snapshot behind the event drain or explicitly carry the pending event into its
accounting. If any functional control reads them, audit that dependency before
changing timing. Do not assume an output named "counter" is necessarily unused
for control. In the inspected leaf they are diagnostic outputs. [S05]

Never replace the captured verdict with a fresh comparison against current
palette state one cycle later. A reload between acceptance and accounting would
then reclassify an old request. C3 includes this mutation.

4.4 What success and failure look like
--------------------------------------

Functional acceptance:
  exact lookup colours/status and accepted lookup sequence unchanged;
  same-slot BEGIN/lookup rules unchanged;
  stale/cold/lookup event counts agree after accounting for the one-cycle delay;
  back-to-back lookups and counter wrap handled;
  reset discards pending events under the declared epoch rule.

Structural acceptance:
  cold_o/stale_o updates no longer depend on live lookup inputs in the same
  cycle. They depend on the captured verdict. Observe this in source/netlist,
  not only through a changed critical endpoint.

Physical acceptance:
  measure the representative leaf or a narrow dispatch/palette seam first;
  in composition, report the old family, its replacement, all-corner WNS/TNS,
  hold checks, and resource delta. A remaining l1_stale_q/l1_res_q path may be
  the next limiter. A counter's own carry path may also become visible.

No specific MHz gain is promised. This is a cheap, falsifiable reduction in
combinational work. It is preferable to a speculative large rewrite when much
of the observed path's tail is diagnostic bookkeeping.

4.5 Conditional request capture, not an automatic pile of skids
---------------------------------------------------------------

If the palette request/verdict cone remains too long after P-CNT, put a complete
resolved lookup record before the leaf:

  {route_token18, palette_slot2, palette_generation8, palette_index8, valid}

Do not register the token and leave the selected palette generation live; do
not register only valid; do not sample the token again when the result returns.
Keep request and response association explicit through the extra cycle.

This stage changes lookup timing relative to concurrent palette loads. Preserve
the leaf's rule at the ACTUAL lookup-acceptance edge, and define the higher-level
ordering between admitted samples and loader transactions. Fully drained upload
phases remain directly comparable. Arbitrary reload races cannot be judged by
assuming the old and new latency pipelines look up on the same wall-clock edge.

The palette result has no ready input. A new stage must preserve guaranteed
result acceptance or reserve a response holding slot BEFORE launching a lookup.
Round-robin arbitration of posted palette results without a holding/credit rule
would reintroduce a dropped completion. Keep the existing priority law unless
that storage contract is deliberately changed and tested. [S05-S06]

Do not retain a redundant capture stage merely because it was once needed.
After the full metadata join, its registered packet may already supply the
boundary this experiment sought. Re-evaluate the physical cone before adding
another cycle and another copy of every field.


5. THE FULL METADATA JOIN: MOVE THE READ BEFORE THE SPLIT
========================================================

5.1 This is a correction to the working candidate, not a new invention
--------------------------------------------------------------------

The earlier owner brief already specified a 40-bit metadata record including
palette identity and owner-generation alignment. The new working report reduces
its description to the existing 21-bit sampmeta row and proposes widening queues
by 21 bits. That is incomplete relative to both the earlier decision and the
new palette timing evidence. [S16-S17]

Restore the full contract. There is no need to ask for another policy ruling
merely to carry the fields the existing brief already listed.

5.2 Storage and access inventory
--------------------------------

Present source shape: [S06, S16]

  sampmeta_m[64][3], 21 bits per entry:
      {nibble1, format3, fraction_v8, fraction_u8, byte_select1}
      192 * 21 = 4,032 declared bits.
      One planner-accept writer; three asynchronous response-side readers.

  palslot_m[64], 2 bits; palgen_m[64], 8 bits:
      owner-specific palette binding captured at admission;
      response-side indexed reads feed the CLUT lookup.

The memory has ONE natural common response stream before class fan-out.
Use it. Do not replicate a wide RAM for three asynchronous readers, and do not
serialize the independent downstream decode lanes behind a new shared read
arbiter. Those are both more expensive answers to a port problem that can be
removed by choosing a better join point. [S08, S16]

5.3 Proposed row and packet, with exact widths
---------------------------------------------

For the current four-palette-slot profile:

  descriptor owner generation       8
  palette slot                      2
  palette generation                8
  resolved format                   3
  fraction U                        8
  fraction V                        8
  byte selection                    1
  CLUT4 nibble selection            1
  reserved                          1
                                  --
                                  40 bits

Use address {owner_slot6, sample_index2}: 256 rows, of which sample index 3 is
invalid. Reject that encoding before treating a row as valid metadata. A table
address fitting in eight bits is not proof that every encoded sample is legal.

The descriptor's generation is an alignment check against the RETURNED token.
It is not a second allocator, not a new lifetime authority, and not permission
to replace a stale returned generation with the generation found in RAM.
V3 still decides return authority using its own ownership/issue/claim rules.

The dispatcher candidate uses DATAW=104 for {metadata40, texels64}; TOKW stays
18. It already has a separate class input and an encoded class in the route
identity. Preserve their agreement explicitly; do not smuggle metadata into the
opaque caller context or rename metadata as extra token bits. [S08, S17]

A 256x40 simple-dual-port configuration is supported by Cyclone V M10K. This is
a legal geometry, not a guarantee that any proposed HDL will infer exactly one
block. Extra ports, reset/control, collision semantics, and synthesis choices
must be checked in the actual RAM report. [V03-V04]

5.4 Carry the palette binding from the right transaction
--------------------------------------------------------

The row is written when a planned sample becomes a committed cache request.
Its format/fractions/nibble come from THAT plan result; its palette binding must
belong to the SAME descriptor. The current global input, a later planner head,
and the palette slot's newly loaded generation are all invalid substitutes.

Preferred end-state:

  admission-captured fragment attributes
    -> expander's complete request record
    -> planner pipeline with palette binding sideband
    -> accepted planned sample and metadata publication

For this profile the palette sideband is ten bits. Thread it through the actual
internal registers/queue entries, not only the module ports. This is exactly
what the earlier six-cache-sites-versus-four-ports failure taught. Default
parameters/adapters should preserve the old oracle's legal configuration while
the V3 path adopts the new fields.

A bounded intermediate implementation may use the existing owner palette table
at the REQUEST side, with a synchronous, credited join, until the sideband is
threaded end to end. That is acceptable only when its writer/reader and lifetime
are explicit. It is not grounds to claim that table deleted. Do not leave the
old response-side asynchronous readers as a permanent convenience.

Delete the response-only palslot_m/palgen_m storage only after all functional
readers are replaced. Front-end fpsl_m/fpgn_m can remain if they still supply the
expander; identical bit meanings at different required read points do not make
an additional RAM port free.

5.5 Publication and first-hit timing
------------------------------------

A registered metadata write is not complete on the edge that captures the write
record. Name the events:

  P0: planner/cache request accepted; identity and row captured.
  P1: registered write command commits the metadata row.
  P2+: a response read may consume that published row.

The exact cycle count depends on the selected bank primitive. Derive it from
its RTL and the earliest possible cache hit, not from an average miss latency.

Choose and prove one rule:

  - the minimum accepted-request-to-metadata-read latency already exceeds the
    write/publication latency; or
  - cache issue/read eligibility waits for metadata publication; or
  - a bounded recent-write forwarding record covers the documented collision.

No unbounded CAM and no multiported scoreboard are needed. Keep one full
{write_enable, address, data} record together. A bare delayed enable with a live
address/data bus is the old defect in a new location.

RAM payload and its read output belong in a clock-only memory process with
supported controls. Reset valid, occupancy, generation/epoch authority, and
pipeline state; do not clear every metadata word. Never assert that this coding
style inferred RAM until the MAP inventory names the bank. [V04, S17]

5.6 Response read reservation and capture
-----------------------------------------

Proposed response path:

  cache terminal response
    -> J0 reserve capacity and capture complete response/token
    -> JR synchronous metadata read using captured address
    -> JC capture returned row with matching data/token
    -> JQ held joined packet
    -> existing raw dispatcher and per-class queues
    -> existing CLUT/nearest/bilinear/error consumers

The destination reservation includes BOTH packets already held and reads that
have launched but not returned:

  reserved = held_packets + metadata_reads_in_flight
  0 <= reserved <= join_capacity

Increment on accepted launch; decrement on actual downstream packet acceptance.
Do not free the reservation because a RAM read completed or a queue head became
visible. A suddenly stalled consumer must have room for every already launched
read. This is the same structural rule the repaired V3 queues already enforce.

Four reservations are a sensible experiment, not a capacity derived by magic.
Derive the necessary depth from the actual read/capture stages and desired
initiation rate. A conservative full-to-free bubble is acceptable initially;
continuous backpressure through unrelated lanes is not.

Validate row association at JC. A bad returned token must not cause a row from
another generation to authorize work. An invalid association follows a named
terminal/error contract retaining the original identity, allowing the owner to
reject stale traffic without granting it current write authority.

5.7 Class consumers read packets, not owner tables
-------------------------------------------------

After the join:

  CLUT consumes its packet's palette slot/generation, format, and sub-byte
  selectors. The palette leaf STILL checks current residency/generation at
  lookup acceptance. A cached "resident" bit would become stale during loads.

  NEAREST consumes the packet's format and texel. It does not read the current
  planner mode, and unused cache lanes are not treated as valid samples.

  BILINEAR holds one complete footprint and its own fractions/format while all
  four RGBA channel jobs are accepted. Metadata may not advance when only R/G
  have been issued. Return collection remains token/channel aligned.

  ERROR retains enough identity and status for a counted terminal outcome.
  It must not pop an invalid class into nothing.

Remove all three old sampmeta response reads in the same conversion. Keeping
one as a "fallback" can retain the entire multi-reader fabric structure and
invalidate the expected area mechanism.

5.8 Costs, deletion ledger, and falsifiers
-----------------------------------------

The claimed area mechanism is deleting 4,032 bits of multi-read storage and its
selection networks, plus response-side palette-binding selection where removed.
It is NOT "save 4,032 registers by adding one RAM" as a measured fact.

The existing dispatcher has four raw entries plus four entries in each of four
class queues: twenty payload slots. Carrying forty additional bits through all
of them adds up to 800 DECLARED payload bits, before extra join registers. Some
may map differently after synthesis; no fitted-register count is promised.
[S08]

A useful ledger for this packet:

  DELETE/REPLACE:
    sampmeta_m[64][3] fabric shape and three late reads;
    response-side palslot_m/palgen_m reads;
    old response palette tables only when their remaining consumers are gone;
    duplicated live-input aliases and raw slicing replaced by named records.

  ADD:
    one legal synchronous metadata bank and registered write/read records;
    bounded join credits and holding capacity;
    metadata carried through dispatcher queues;
    ten-bit request palette sideband and its pipeline carriage;
    row/token generation alignment check and its defined error path.

  RETAIN:
    V3 owner authority and C0-C4 return discipline;
    palette residency/load protocol;
    exact format/alpha/bilinear arithmetic;
    legitimate front-end attribute copies that still supply separate read points.

First use MAP to test the storage hypothesis. If metadata remains in fabric,
inspect the named refusal reason, actual read count, memory process, and output
register boundary. Do not run a four-hour fit hoping placement fixes a failed
memory architecture. If the bank infers but total area does not improve enough,
read the hierarchy and queue cost before changing a second unrelated subsystem.

The old P0-E census was for a different composition. Its "no more large async
arrays" conclusion cannot be inherited by this newly widened owner metadata.


6. RCP PREPARATION: RESERVE FIRST, THEN PREPARE
=============================================

6.1 Work on the service that is actually instantiated
----------------------------------------------------

The V3 top instantiates zhao_raster_rcp24_svc with eight contexts and a 14-bit
owner token. It does not instantiate zhao_raster_rcp24_v3. A good result on the
alternative V3 leaf is not a timing repair to this composition. [S06-S07]

The existing service already has the successful S1 selection/issue record.
Its pending bit clears when work is selected into that record, not when the
multiplier eventually executes. Preserve that reservation rule and its tests.
Do not redo P0-B under a different name.

The present ingress path still performs normalization, shift, seed-ROM lookup,
zero selection, and context initialization from the input denominator in one
acceptance operation. That source structure is directly relevant to the fitted
frag_depth_i -> c_x path. [S04, S07]

6.2 A request is an owned transaction before it is executable
------------------------------------------------------------

Proposed logical phases:

  FREE
    -> PREPARING, at accepted input
    -> EXECUTABLE, after complete initialization
    -> RESERVED/EXECUTING micro-job
    -> EXECUTABLE continuation or DONE
    -> FREE, only when the result's ownership is transferred under its contract

PREPARING counts as occupied. The context cannot remain apparently free while
its raw request travels through the new preparation registers.

The minimum accepted record contains:

  context index, owner token14, raw denominator24, validity

Further records carry the normalized mantissa, shift/k, zero flag, and seed as
needed. No preparation stage consults a current input pin for a request captured
earlier. The token and chosen context index travel through every stage.

6.3 A practical staged implementation
-------------------------------------

Start with the smallest separation that the source and measured path justify:

  N0 ACCEPT/RESERVE
    Determine an available context under the existing allocation rule.
    Atomically reserve it and capture raw denominator, token, and context index.
    It is allocated but not eligible for micro-job selection.

  N1 NORMALIZE
    From N0's raw register, compute leading-zero information and normalized
    mantissa/k/zero. Capture the full preparation record.

  N2 SEED / INITIALIZE
    Read the unchanged seed function/ROM from the registered normalized value.
    Commit the context's initial m/x/w/k/zero/token state.
    Make the context pending only when that initialization is complete.

If the leading-zero plus shift operation is itself too long, split N1 into a
leading-zero stage and a shift/index stage. Do not merely add an input flop and
leave the entire original long cone from that flop to c_x: that would move the
bad path from a port to a register without reducing its combinational depth.

This is a pipeline, not a serial preprocessor. Different requests may occupy
N0/N1/N2 simultaneously when contexts and stage capacity permit. A fixed-latency
preparation pipeline can be straightforward because each accepted item already
owns its destination. If any stage can stall, propagate the whole record and
its valid/credit state together.

The shape must account for initialization and micro-job writeback landing on the
same edge for DIFFERENT contexts. Do not turn an existing multi-event context
update into two nonblocking writes that accidentally overwrite each other.
Prove that the reserved preparation context cannot be the context already in
S1/M1 writeback. One writer-per-row/event ownership law must remain explicit.

6.4 Publication, allocation, and reset invariants
------------------------------------------------

Required invariants:

  preparing(c) implies allocated(c) and not executable(c).
  each accepted input owns exactly one context.
  each occupied context has exactly one current owner token.
  preparation publication writes the context that was reserved at acceptance.
  no context can be selected twice while its micro-job is in S1/M1.
  reset clears every preparation-valid/reservation state that can publish later.

Do not set c_pend at raw acceptance if the operands are not yet initialized.
Do not let an allocator see a slot as free until an agreed release event.
Do not rebuild a 64-entry owner allocator inside an eight-context arithmetic
service; the local index is a service reservation, not a second island identity.

C5 independently demonstrates the duplicate-allocation hazard when reservation
is deferred until preparation completion. It does not establish the repository
implementation's correctness or throughput.

6.5 Preserve the exact reciprocal law
-------------------------------------

Retain the current seed contents, four dependent multiplier jobs, unsigned
64-bit wrap semantics, the specified round-half-up rescaling, and the deliberate
32-bit iterate truncation. Denominator zero remains governed by the existing
contract; do not add a zero-work shortcut in the same experiment merely because
it looks cheap. [S07]

The prior brief's exhaustive normalization checker can be reused. Its existence
is not evidence that a newly typed SystemVerilog expression has the same sizing
and signedness. Run the actual RTL/reference differential and check boundary
values, zero, powers of two, and normalization transition points.

A simplification of seed-index extraction from a normalized mantissa is a
representation change only if bit-equivalence is established at the expression's
actual widths. Do not combine an approximate reciprocal, a changed ROM, and a
pipeline repair into one allegedly attributable fit.

6.6 Throughput is an acceptance condition, not a comment
-------------------------------------------------------

Four multiply launches per reciprocal is necessary but insufficient. A design
can perform exactly four launches and still leave the multiplier idle most of
the time. Record both total launches and elapsed sustained-stream cycles.

Measure, with the consumer ready and sufficiently many independent requests:

  accepted/completed reciprocals and their token identity;
  multiplier launches per reciprocal;
  steady-state reciprocal initiation/completion interval;
  multiplier idle cycles categorized by dependency, no input, no context,
  preparation, and blocked output;
  context occupancy, including PREPARING and completed-but-unreleased work.

Eight contexts may still hide the added preparation latency; that is a workload
question to measure, not a theorem from the number eight. As a necessary
capacity condition, average occupied lifetime times target throughput cannot
exceed available contexts. Do not widen every store to 64 because the island
has 64 owners. Increase local contexts only after a measured capacity stall
justifies the extra storage and routing.

The structural target is removal of the unregistered input-to-normalize-to-seed-
to-context chain. The numeric target is progress toward complete 100-MHz timing
without reducing the required sustained rate. Both must be checked.

6.7 Free selection and completion are conditional follow-ups
------------------------------------------------------------

The setup summary also names free_i-related synthesized endpoints. First
classify them in the detailed timing netlist. If the allocator becomes the
limiter, a registered free-context reservation/head or local predecode can be
considered. It must consume a context at N0 and return it at the defined result
transfer; no stale registered credit may admit an extra context.

The current DONE output is selected by a live priority scan. At the state level,
a lower-index context becoming done can replace the offered higher-index result
while the consumer is stalled. C6 shows that abstract possibility. It does NOT
prove that a damaging schedule is reachable from reset in this RTL. [S07]

Establish the actual interface contract and test it. If stable offered data while
valid && !ready is required and the test finds preemption, reserve/hold the
selected result or capture a whole completion packet. Do not free its context
until the packet has another reserved owner. Do not register only the index
while permitting the payload row to be overwritten underneath it.

The Stage-A RCP-to-PERSPUV capture already provides a downstream boundary.
Audit whether a new internal hold is needed for protocol stability, timing, or
neither; do not stack duplicate result queues without a measured purpose.


7. FRONT-END LIFETIME, RESET, AND NAMESPACE REUSE
===============================================

7.1 The invariant is about every legitimate reader, not just final output
------------------------------------------------------------------------

V3's leaf owner correctly allows a required-source mask of zero to become ready
at admission. The composed island still sends that owner through RCP, PERSPUV,
and expansion, where owner-keyed sidecars may be read. The safety obligation is:

  no slot is reused while any legitimate operation can still read or mutate
  data belonging to the previous owner of that slot.

The isolated 300/300 zero-work result does not prove this implication. It checks
retired tags on one schedule. In particular, a late front-end read might not
change the base-only output in that workload. [S06-S07, S10, S14]

7.2 Instrument the real last-use events first
--------------------------------------------

For every owner, record the relevant events at their actual handshakes:

  admission;
  RCP result accepted into the UVW join;
  PERSPUV result accepted into expansion;
  last owner-sidecar read captured;
  final sample/AUX issue from the expander, where applicable;
  COMBINE acceptance;
  FINAL publication;
  external ordered output acceptance;
  any subsequent same-slot admission.

The last read may precede expander completion if the expander has already copied
all needed attributes into its own packet. Determine that from the actual port
inventory. Do not choose "RCP finished" just because it is a convenient pulse.
Also distinguish late operations that only hold complete private copies from
operations that still read owner-slot storage.

Required stimulus includes alternating zero/nonzero counts, AUX-only work,
nonuniform context and material fields, stalls at PERSPUV/expander/COMBINE/output,
and repeated slot reuse with a functioning memory environment. Assert the
lifetime implication directly; tags and eventual counts alone are too weak.

7.3 A small phase bit is the bounded repair if the ordering is not guaranteed
----------------------------------------------------------------------------

If the structural lifetime implication cannot be established for the intended
pipeline, add a FRONT_COMPLETE condition, not another owner allocator:

  - clear a per-owner phase bit on accepted admission;
  - set it from a full-handle event after the last legitimate front-end use;
  - require it at the actual COMBINE handshake, together with the existing
    material alignment condition;
  - preserve a single matching valid/ready acceptance predicate;
  - reject stale completion events rather than setting a successor's phase bit.

With COMBINE blocked until the last front-end use, a FINAL cannot legitimately
complete early and output retirement cannot release the owner too soon. This
uses the existing owner lifecycle rather than adding a second release counter.

The phase bit need not live inside v3own if the composition owns the additional
front-end obligation. Keeping the owner leaf interface intact may be the
smallest verified change. The return-authority assertion suite must continue to
pass, and any change to the owner itself needs its own exact invariant review.

Resolve simultaneous admission/phase completion for the same physical slot by
full identity and explicit next-state precedence. Do not set a bit by slot alone
from a delayed packet. Do not implement a combinational all-front-end-quiet
reduction in normal admission to avoid writing one small phase plane.

If a proof from the actual service/lifetime contract makes FRONT_COMPLETE
redundant, retain that proof/assertion and omit the hardware. Do not add it just
because the discarded zero-work stall report sounded alarming. This is a safety
closure decision with a narrow fallback, not a mandatory speculative pipeline.

7.4 Reset and wrap are end-to-end transport problems
---------------------------------------------------

The current owner fence explicitly lacks external producer-acknowledgment phases.
Local quiet covers internal owners, queues, reservations, and stages. It does
not certify that a memory adapter or AUX producer can no longer deliver old
traffic. [S10, S17]

A production barrier needs an explicit contract:

  STOP admission of new namespace work.
  FINISH or cancel already accepted work under defined terminal semantics.
  QUIESCE producers: acknowledgment covers accepted work and delayed responses.
  DRAIN residual transport and local posted/pending packets.
  REOPEN only after the new namespace is unambiguous.

This slow control belongs in a fence state machine, not in the normal ready
cone. Widening a generation field postpones aliasing; it does not establish a
quiescence guarantee.

Untyped/untagged memory-fill returns deserve special attention. If an adapter
resets its expected transaction state and an old untagged fill beat later arrives,
a local owner-generation comparison may have nothing to compare. The adapter
must either drain/cancel with a real external acknowledgment or carry sufficient
identity through the external protocol. Do not invent safety by clearing a local
FIFO while leaving the producer alive.

Keep the existing transitional fence until the replacement barrier is complete.
Do not combine per-slot wrap permission and a new epoch fence into accidental
repeated drains or indefinite permission to reuse names. The complete barrier
can later reduce unnecessary drain overhead; its proof must come before that
optimization.

7.5 The return pipeline is not negotiable collateral damage
-----------------------------------------------------------

Preserve snapshot identity AND current identity at claim. The existing tests
already showed distinct future-token and retired-token hazards. Preserve recent
claim forwarding, merged same-owner event masks, registered payload write
commands, and publication after the write. [S10, S17]

Actual COMBINE acceptance, not candidate reservation or bank-read reservation,
authorizes FINAL. A new metadata or FRONT_COMPLETE stall must not move that
permission earlier. Liveness-policy tightening at C4 is separate from the
already completed generation representation migration; never resurrect gen_q
because a new packet stage needs an identity check.

The current owner return ports are unconditionally ready under its reserved
fixed-latency storage contract. This matters to the posted palette response.
Changing that property requires a new response reservation/holding contract at
the caller, not just a different ready assignment. [S10]


8. SECONDARY AREA WORK: LOCAL CONTROL, NOT ANOTHER GLOBAL SCOREBOARD
==================================================================

8.1 Do not guess where 13,133 ALMs live
--------------------------------------

The scalar fit summary cannot apportion the current cost among owner control,
expanded sample metadata, cache, RCP, palette, expander, material join, and
characterization boundary. Before a second large area intervention, retrieve the
small per-entity resource table and RAM-inference inventory from this fit.

Do not repeat the leaf-sum subtraction that predicted a free island reduction
from T2. V3 was not in the legacy island. The first V3 measurement is its own
specimen, and old local improvements must not be counted a second time. [S22]

8.2 One credible owner-control experiment remains
------------------------------------------------

The inspected ISSUE validation reads req_q[slot] and iss_q[slot] through global
indexed selects, computes iss_t_ok_c/iss_a_ok_c, then uses the accepted result in
per-owner next-state updates. That is a potential global select-and-redistribute
structure even after the generation table was removed. [S10]

A representation-preserving experiment is:

  validate event range/full-ticket membership once per incoming event;
  predecode the destination slot;
  evaluate the selected row's required/issued conditions locally;
  update that row's issued mask on the SAME acceptance edge;
  reduce a narrow rejection event for diagnostics separately.

For row i, the identity "slot == i implies req_q[slot] == req_q[i]" licenses the
local predicate. The challenge is preserving event/error semantics and synthesis
sharing, not inventing new owner semantics.

Do not indiscriminately replicate full ticket arithmetic in every row. Keep the
bounded identity check per event lane, then share/predecode its destination.
Do not add another cycle to ISSUE without addressing a same/next-cycle return
snapshot that relies on the old issue visibility. Start with an exact algebraic
migration rather than a new notification protocol.

If hierarchy/timing attribution warrants more work, physically local groups of
narrow phase bits and registered candidates can be explored. Use small local
state and explicit event coalescing, not a 64-owner multiported RAM that requires
replication or hidden arbitration to handle concurrent TMU/AUX/FINAL events.

This is SECONDARY to measured ingress and palette failures unless the new
composition's attribution says otherwise. The owner leaf being near 100 MHz
is not a reason to ignore its area, but it is a reason not to restart all owner
logic before reading the composition.

8.3 Keep the queues already shown to work
-----------------------------------------

The V3 logical ticket count, head/spare/in-flight accounting, and output/read
reservation rules were expensive to get right. Preserve them. Moving a wide
packet body into RAM is a port/latency change, not a reason to replace the entire
queue protocol. [S10, S17]

For tiny wide depth-four queues, compare the actual costs of a register body and
synchronous packed storage only when attribution identifies them as worthwhile.
A RAM-backed body may need a head register, spare capacity, read reservation,
and control that erase its nominal saving. Do not export every temporary queue
as a standalone fit merely because it exists.

8.4 A duplicated field is not automatically redundant hardware
--------------------------------------------------------------

Examples that require port/lifetime reasoning:

  The caller context is needed early for AUX/expansion and later for ordered
  retirement. Deleting a copy requires supplying the additional read point or
  carrying a private record; it is not legal to read out_ctx at the early stage.

  Base/material fields are used by different phases. A separate record can be
  justified by independent synchronous readers. Collapse them only with an
  explicit port schedule and capacity/latency proof.

  The 46-bit MATERIAL plane includes has_aux. Dropping that bit because the
  first architectural list said 45 changes which third sample COMBINE receives.

The old integration already paid for exactly these mistakes. The deletion ledger
must state which consumer now supplies each field. "The name disappeared" is
not sufficient evidence of a correct deletion. [S06, S09, S17]

8.5 Do not reduce capability to satisfy an old allocation silently
-----------------------------------------------------------------

Reducing owner capacity from 64, removing error paths, bypassing alpha, making
Mosaic counter-only, or disabling AUX can make a fit smaller. Those are feature
or throughput reductions unless explicitly authorized as a profile. They are
not wins against the same target.

Similarly, adding RAM is neither automatically good nor bad. It is good when it
removes a measured logic/routing cost at acceptable latency, port bandwidth, and
whole-machine allocation. Keep ALM/register/M10K/DSP and the exact feature
profile together in every comparison.


9. FEATURE-LIVE COMPOSITION AND SUSTAINED RATE
=============================================

9.1 Compatibility closure is not feature closure
------------------------------------------------

The old and new island matching 392 records establishes valuable compatibility
for that stimulus. It cannot establish a feature neither top actually exercises
as a result-affecting part of the datapath. [S06, S21-S22]

Maintain two named milestones:

  COMPATIBILITY V3:
    preserves the exercised legacy island contract and numerical results;
    useful for measuring the ownership/storage migration.

  PRODUCT TEXTURE PROFILE:
    all required bindings, addressing, formats, alpha, AUX, material recipes,
    Mosaic behavior, and surrounding Fog integration are active where required;
    performance/resources/timing measured on this actual configuration.

Do not let compatibility be called product acceptance. Conversely, do not mix
all missing product functionality into the first metadata experiment and then
claim the resulting area delta measures only metadata.

9.2 Binding and class authority
-------------------------------

The current planner reads global bind_base_i and bind_mode_i at its own request
handshake. The existing directed fixture therefore uses fully drained mode
phases. It is not a general proof that mixed-format fragments carry their own
binding configuration through a live pipeline. [S06, S17]

The intended product needs a transaction-bound resolved binding or an explicit
configuration epoch that prevents mutation while consumers still need the old
state. It must not attach mode A at admission and later read mode B at planning.

Class should ultimately be derived from the resolved format/filter law, not be
an independently authoritative input that can disagree with it. Existing mismatch
counters are useful during migration; their existence is not the final repair.
Preserve malformed-format/refusal semantics rather than narrowing three format
bits to a width that aliases illegal codes onto legal ones.

Do representation migration and policy/feature cleanup in separate reviewable
steps. Once the resolved descriptor is authoritative, remove the obsolete
source of truth and prove the deletion with mixed, transaction-specific data.

9.3 Mosaic must select something that changes the fetch
-------------------------------------------------------

The inspected top consumes Mosaic's selection through observability rather than
making that selection the real planner/address authority. Its counter moving
keeps some logic alive but does not prove the material's chosen tile affects the
sample. [S06]

A product gate must vary the selected tile/material and observe the corresponding
address and colour difference. Carry the selected identity through a credited
join, or explicitly define a supported profile without Mosaic. Do not use the
cost of the present partial integration as a full-feature area ceiling.

9.4 AUX and Fog keep their own scope
------------------------------------

AUX coordinates must belong to the fragment making the AUX request, not the
fragment currently retiring. Preserve the recent expander context carriage.
For the production interface, explicitly separate opaque caller context from
world/geometry fields where the architecture requires both. Do not silently
repack caller-owned bits to avoid adding a named field. [S06, S17]

Fog is authorized work for Manafold, not accidental priority drift. Keep its
established ordering: after material/toon processing and before blend. Its
factor/configuration must travel with the intended fragment/frame. The texture
ownership rewrite does not itself complete the attribute interpolation and
surrounding renderer integration. [S17]

Do not charge every Fog/geometry cost to texture merely because it is adjacent,
and do not omit that cost from the whole-console ledger. This brief does not
restart terrain or projection redesign. Their budgets and integration still
belong in the final count-once product model.

9.5 MHz alone is not pixels per frame
-------------------------------------

Use a workload ledger with independently measured service demand. For the current
architectures, useful necessary lower bounds on cycles are:

  RCP:      4 * number_of_reciprocals, at one multiplier launch per cycle.
  Bilerp:   4 * number_of_filtered_samples, for four RGBA channel jobs through
            the existing one-channel-per-cycle lane.
  COMBINE:  number_of_paired_phases, at the implemented phase issue capacity.
  Memory:   accepted fill beats divided by actual serviced beats per cycle.

These are lower bounds, not additive predictions of total elapsed cycles.
Independent units can overlap, and dependencies, queueing, context shortages,
AUX latency, and bandwidth can make the real answer larger than their maximum.
The reciprocal and bilerp demand statements follow the current code, not an
assumption that all mathematical multiplications map to one physical DSP each.
[S07, S09, S23]

For each meaningful workload report:

  admitted and retired fragments, elapsed steady-state cycles;
  sample counts by class/format and material recipe;
  filter channel jobs, reciprocal launches, COMBINE phases;
  cache hits/misses and actual external beats;
  stalls by the stage that owns the constraint;
  high-water marks for owner/context/join/posted-response reservations;
  exact output stream and error outcomes.

The feature-live throughput requirement should be the same before and after an
optimization. A 100-MHz core that adds enough bubbles to draw fewer fragments
than the 82-MHz baseline has not necessarily improved the game.

13. INDEPENDENT CHECKS AND THEIR EXACT LIMITS
============================================

The accompanying Python program uses only the standard library and has been
executed successfully in this review. It is not a replacement for the project's
RTL tests. Its role is to test the arithmetic/protocol claims underlying this
brief and demonstrate selected bad alternatives.

C1 -- Overflow-monitor litmus
-----------------------------

Enumerates the Boolean ready/accept/full relation and proves the new predicate
is identically false. An off-by-one FULL threshold permits a fifth accepted word
while the shared-predicate monitor remains false. A separate occupancy-range
check detects the resulting invalid state. This is a finite algebraic result,
not a statement that a physical upset was injected into an FPGA.

C2 -- Ordered completion with an unanswered environment
-------------------------------------------------------

An abstract queue places 24 incomplete older records ahead of 40 complete zero-
work records. A correct ordered consumer emits none. A clean 300-record zero-
work queue drains. A deliberately wrong skip-head model appears to recover by
violating order. This explains the environmental confound; it does not reproduce
the repository's exact 16-admission trace. The agent's clean-reset RTL test is
separate, repository-reported evidence.

C3 -- Palette event equivalence and delayed accounting
------------------------------------------------------

Checks all 16 combinations of lookup-valid, generation mismatch, old residency,
and accepted same-slot BEGIN. The captured stale/resident flags encode the old
lookup/stale/cold event partition exactly. Runs 100,000 abstract event cycles,
including reset and 32-bit counter wrap, checking one-cycle delayed accounting
and equality after the pending event drains. A recheck against later palette
state is shown to produce a different classification.

This does not model RAM contents or Quartus timing. It verifies the precise
counter-equivalence statement proposed in section 4.

C4 -- Credited metadata join
----------------------------

Runs 32 schedules of 10,000 cycles using capacity four, fixed read latency,
random/adversarial output stalls, and complete packets with distinct payload,
sample metadata, and palette binding. The runs transfer 139,695 packets without
loss, reordering, or reservation overflow and drain fully. An implementation
that ignores reads in flight exceeds its reservation capacity. A packet with
another transaction's palette binding is distinguishable from the correct one.

This is a protocol model, not the final SystemVerilog packet layout, generation-
validation implementation, collision proof, or RAM-inference result. The old
brief's encoding tests and the new RTL tests must cover those separate layers.

C5 -- Reserve-at-admission preparation
--------------------------------------

Runs a 1,000-cycle eight-context preparation/execution model. A context reserved
at acceptance cannot be reused while its preparation is in flight. Delaying
reservation until publication permits aliasing, and the deliberate mutant is
caught. Reciprocal arithmetic and actual service throughput are not modelled.

C6 -- Live priority selection under stall
----------------------------------------

Demonstrates a state-level case where a new lower-index DONE record changes an
unlocked priority output from context 5 to context 0 while the consumer is not
ready. A held selection remains stable. It is NOT an established reset-reachable
repository trace or proof that the present downstream consumer is corrupted.
Its purpose is to identify the exact protocol obligation that a targeted RTL
test must resolve before changing the completion architecture.

What was NOT executed here
---------------------------

No Quartus invocation, Verilator/Icarus repository simulation, board run, or
unbounded formal proof was performed. No implementation patch was applied to
GitHub. No exact ALM/Fmax benefit is claimed for any proposal in this brief.

Large full-detail hold/setup reports were not independently readable through
the available retrieval path. Their compact summaries and the multicorner STA
report were read. The hold endpoints, detailed path hops, actual inferred RAM
inventory, and per-entity current physical cost remain named follow-through
requirements rather than guessed conclusions.
