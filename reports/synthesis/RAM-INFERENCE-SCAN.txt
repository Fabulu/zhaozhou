WHY THIS FILE WAS REGENERATED, AND WHAT THE PREVIOUS COPY WAS TELLING YOU TO DO

    The previous copy was 972 lines cut before rule 6 existed, and it repeated
    the following remedy TWENTY-PLUS TIMES:

        "One flat array per element inside a generate, outer index a genvar."

    THAT IS THE FOURTH QUARTUS 17.0.2 INFERENCE KILLER, STATED AS THE CURE.
    An array declared inside a genvar-indexed `generate for` block is not a RAM
    candidate for Quartus 17.0.2. Generate-IF infers; module scope infers; THE
    LOOP IS THE KILLER. `zhao_geom_arenabin` followed exactly that advice --
    fourteen flat one-dimensional arrays inside a generate-for -- and every one
    went to flip-flops: 146,414 registers against 1,010 for the identical
    circuit, map time 1,025.7s against 37.1s.

    The correction was made by ARENAINFER on 2026-09-26 and written into
    `check_ram_inference.py`'s RULE 4 DOCSTRING. It was never made in the
    string the checker actually PRINTS, so every reader of this report kept
    getting the killer. Found by SWAPBUILD, 2026-09-27. Both are fixed now.

    THE CORRECT REMEDY: one flat array per element AT A MODULE'S OWN SCOPE --
    its own module, instantiated inside the loop. `zhao_dc_sdp_ram` is that
    module.

    Note the shape of this failure, because it is the campaign's signature one:
    the knowledge was written down, correctly, in the same file -- and nothing
    read it back into the code path that produces the output people read.
