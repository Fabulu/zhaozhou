1. WHAT I GOT WRONG, FIRST
==========================

1.1 The RAM diagnosis over-generalised. The addendum is right.
-------------------------------------------------------------
I wrote that the arrays which stayed in flops are "read from several places"
and that the fix is to reduce each to a single read address. The addendum's
correction stands: several suspect arrays have ONE logical read address, and
`rob_m[seq_head_r]`'s three output slices all read the SAME word. Absence from
the RAM inventory does not by itself establish a flop count or its cause.

What survives from my finding, and it is narrower: `fsc_m` and `rob_tag_m` are
the only two of their families that inferred, and the RAM Summary names them.
That is a fact about the inventory. The MECHANISM I attached to it was a guess
dressed as a conclusion, and PERSPUV had already taught this exact lesson once.

The correct statement is the addendum's: a named per-array attribution needs the
fitter's resource-by-entity section, and until then the organisation should be
designed from the ACCESS STRUCTURE the block actually needs -- captured UV bank,
captured material/context bank with one registered post-perspective read,
per-sample metadata with one validated read, final result bank with a
synchronous head read -- rather than from an inferred cause.

1.2 What the PERSPUV evidence does support
------------------------------------------
FIXED, and this one is exact rather than inferred. `e_q_u`/`e_q_v` had TWO write
addresses: `e_q_u[tail_q] <= 0` at allocation and `e_q_u[p3_i_q[0]] <= q_c[0]`
at P4. An M10K simple-dual-port has one write port.

The allocation-time zero is also REDUNDANT: `e_q_u[head_q]` is read only when
`head_done` holds, which requires `e_have[head_q] == 2'b11`, and `e_have[i][0]`
is set only in the same P4 branch that writes `e_q_u[i]`. No reader can observe
the initialised value. Removed; both perspuv tests pass unchanged (8 and 12
checks).

This is the same rule the COMBINE brief states for scratch -- "Do NOT initialize
scratch on admission: that creates a second writer" -- appearing in a second
block. It is worth stating as a general law for this codebase.

`e_sat` KEEPS its clear: it is a sticky flag that P4 only ever sets, so without
the clear a saturation leaks into the next fragment reusing the token. It is 16
bits and was never a memory candidate.

Remaining PERSPUV work, and it is now aimed correctly: `e_num_u`/`e_num_v` have
one write address and one read address and still did not infer, so they are the
genuine QUARTUS_GOTCHAS 14 case -- the read feeds a multiplier combinationally.
That is where the registered-read experiment belongs, and it is the ONLY array
it fits. `e_mant` has two read addresses (`pk_i[0]`, `pk_i[1]`) because the
per-axis split was applied to `e_num` and `e_q` and MISSED it.


2. CACHE: THE LOST RESULT IS REAL, LIVE, AND SILENT
===================================================
VERIFIED and MODELLED. This is the most serious finding outside COMBINE.

2.1 The mechanism
-----------------
  zhao_texture_cache_pipe.sv:300  rs_n     = rs_wp - rs_rp
  :307                            rs_room  = (rs_n != REQN)
  :321                            c3_retire = c3_all_hit && rs_room
  :328                            c1_go     = rq_issuable && !fb_busy_r
                                              && !c3_miss && rs_room

`rs_room` is a snapshot of TODAY's occupancy and accounts for nothing already in
C1 or C2. The file's own comment at :324-326 states the intended property --
"Holding issue on rs_room keeps the pipe from producing results it cannot
place" -- and that property is false.

When `c3_retire` is 0 because the FIFO is full, NOTHING HOLDS C2:
  :439  c2_v <= c1_v;              unconditional, outside any `if`
  :440  if (c1_v) c2_rdat[k] <= ram_dat[k];   payload replaced whenever C1 is
                                              occupied, with no reference to
                                              c3_retire or rs_room
`rq_rp` (:458) does not advance while `rq_ip` (:426) already passed the request.

2.2 Independently reproduced
----------------------------
The control logic was transcribed into a cycle model -- pointers, c1_v/c2_v and
their payloads, with the exact c1_go/c3_retire expressions -- and reproduces the
addendum's numbers exactly:

  accepted  0 1 2 3 4 5 6 7
  returned  0 1 2 3     6 7
  LOST              4 5

Warm line, all lanes hit, smp_ready_i low, REQN=4. At t=7 `rs_room` falls, req 4
sits in C2, and :439 overwrites it with req 5. At t=8 `c1_go` is 0 so :439
clears C2 and req 5 is destroyed. When the consumer resumes, probes 6 and 7
issue and retire, and EACH RETIRE BLINDLY INCREMENTS rq_rp (:458), freeing
requests 4 and 5's slots while returning 6 and 7's src_id.

2.3 Why it is worse than the addendum says
------------------------------------------
The header at :5 says "Nothing instantiates this yet". THAT IS STALE. The block
is instantiated at zhao_texture_island_top.sv:781-783 with REQN(4) and in
zhao_prod_top.sv:4348, and its smp_ready_i is real backpressure, not a stub:
island_top:813 `cache_smp_ready = disp_rsp_ready` and rsp_dispatch:109
`rsp_ready_o = (raw_n != RAWN)` -- a FIFO-full check that deasserts whenever
anything downstream backs up.

It does not deadlock. It returns correct-looking data under a mismatched tag,
which is worse.

The miss path is NOT an accidental rescue: `c3_miss` requires `!fb_busy_r` and
so does `c1_go`, so the pipe is provably empty during a fill. There is no
escape hatch.

2.4 The repair: reserve at issue
--------------------------------
Invariant: rs_n + non-cancelled probes in flight <= REQN.

  logic [RQW:0] rs_resv;
  assign resv_room = (rs_resv != REQN);
  assign c1_go     = rq_issuable && !fb_busy_r && !c3_miss && resv_room;
  assign c3_retire = c3_all_hit;           // room was reserved two stages ago
  assign squash_c  = c2_v + c1_v;          // probes killed by a miss
  if (c3_miss) rs_resv <= rs_resv - squash_c - rs_pop;
  else         rs_resv <= rs_resv + c1_go   - rs_pop;

`rs_wp++` must NOT decrement rs_resv: retirement TRANSFERS the reservation from
the pipeline into the FIFO, and only the pop frees it. That is the mechanism.

The replay refund is safe by construction: `c1_go` contains `!c3_miss`, and a
miss implies `!c3_all_hit`, so a miss and a retire are mutually exclusive. The
queued `rs_n` reservations stay held while the squashed probes' are refunded.

DO NOT take the fully-stallable C1/C2 alternative in this file. `rd_idx` and
`rd_daddr` (:331-337) are combinational off `rq_ip`, and `ram_tag`/`ram_dat`
(:363-364) reload every clock with NO ENABLE, deliberately, per :231-235. Adding
a read enable is exactly what the M10K inference work at :150-183 fought to
avoid. The counter costs three bits.

2.5 The test
------------
tests/texture/texture_cache_pipe_directed.cpp case 3 already stalls the consumer
at :150 and misses the defect for two reasons: the working set is COLD, so
fb_busy_r serialises everything and two hit results never coexist in C1/C2 with
a full FIFO; and it asserts only `accepted >= REQN` (:162), never that responses
came back. Warm a line first, then stall, push 8 accesses with distinct src_id,
release, and assert every issued src_id returns exactly once and in order.


3. FRAGROB: THE AUX CONTEXT IS ALWAYS WRONG, NOT SOMETIMES
==========================================================
VERIFIED, and this is the sharpest escalation over the addendum.

3.1 The mismatch
----------------
  zhao_texture_fragrob.sv:648-654  pop: ax_slot_q <= axq_m[..]; ax_pend_q <= 1
  :525                             ax_ctx_r <= ctx_m[ax_slot_q];   UNCONDITIONAL
  :416-419                         aux_valid_o = ax_pend_q;
                                   aux_ctx_o   = ax_ctx_r;
                                   aux_slot_o  = ax_slot_q;

Line 525's address is `ax_slot_q` itself -- the register the pop overwrites.
Both are nonblocking, so on the pop edge `ax_ctx_r` loads ctx_m[OLD slot] while
ax_slot_q takes the NEW one.

3.2 Why it is not a window
--------------------------
island_top.sv:1102 `fr_aux_ready = aux_req_ready`, and aux_pipe.sv:165
`req_ready_o = 1'b1`. **aux_ready_i is permanently asserted**, so the
wrong-context cycle is the ONLY cycle every request ever gets. The corrupted
word is consumed as geometry at island_top.sv:1107 --
`.req_wx_i(fr_aux_ctx[31:0]), .req_wz_i(fr_aux_ctx[63:32])`. Every AUX sheet
lookup uses the PREVIOUS AUX fragment's world X/Z under the current fragment's
slot and generation. Identity checks all pass.

Why no test caught it: fragrob_differential.cpp:182 records aux_slot_o and
aux_gen_o on the handshake and NEVER COMPARES aux_ctx_o -- the one observable
that would fail.

Also: ax_slot_q and ax_gen_q are not in the reset list (:549-563), so the first
AUX request after reset reads ctx_m[0].

3.3 Response validation and issue capacity
------------------------------------------
:389-393 checks valid and generation. MISSING on the TMU side: sample-index
range, requested, issued, not-already-arrived. There is no issued mask in the
file. An unrequested sample sets arr_q, so `arr_q != req_q` forever and, because
retire is strictly allocation-ordered, THE WHOLE BLOCK WEDGES.

One correction to the addendum's wording: `sidx==3` does not index into other
storage -- the write and the bit-select are silently dropped. The harm is
different and arguably worse: accepted as valid, no id_error counted, sample
never arrives, same permanent head-of-line deadlock.

Issue capacity: slot capacity is properly reserved (:340), but the WORK QUEUE is
checked after the fact. The three `wq_m[..] <= ..` writes at :605-614 are
unconditional and `wq_overflow_o` is raised AFTER them -- a flag, not
backpressure. Worse, the assertion at :329 compares occupancy against `DEPTH*3`
and NOT against `WQN=64`: at DEPTH=32 that is 96 > 64, the address aliases, and
the assertion passes while entries are overwritten. The invariant that matters,
`WQN >= DEPTH*3`, is asserted nowhere.

Two independent `id_errors_o <= id_errors_o + 1` in one always_ff (:665, :672)
means simultaneous TMU and AUX faults count as ONE.


4. AUX: A NON-STALLABLE PRODUCER DOES NOT MAKE ITS SINK INFINITE
================================================================
VERIFIED, all three claims, with three distinct loss modes.

`sheet_ready_i` appears in exactly ONE place in the whole file -- the evidence
counter at :279. It has zero influence on a7_v_q or any a7_* payload. :272-278
is an unconditional one-cycle shadow of div_ov, so the offer's lifetime is one
clock regardless of acceptance.

  MODE 1  offer evaporates: sheet_ready low, div_ov low next cycle, a7_v_q
          clears, token never issued, FRAGROB slot waits forever. A HANG.
  MODE 2  offer mutates mid-handshake: valid held while payload changes -- a
          ready/valid protocol violation in its own right.
  MODE 3  a degenerate result at the next cycle drops sheet_valid_o AND pushes
          itself to the return queue, completing ahead of the request it just
          destroyed.

The return queue (:285-307) has no full term, no admission gate, no reservation.
Peak push is 2/cycle (a sheet response and a degenerate together) against a pop
of 1. There is NO sheet_rready_o port at all, so the leaf must sink every
response. And `rqcnt` is 4 bits for an 8-deep queue: it can reach 15, wrap on
+2, and land on 0 with entries resident, at which point out_valid_o goes false
and the queue silently stops delivering.

The dual-push case has NEVER been exercised: the test harness makes
sheet_rvalid_i a combinational loopback of sheet_valid_o, and those two are
mutually exclusive by construction. In silicon, where a response has latency, it
happens routinely.

There is no sheet backpressure anywhere in the suite: texture_aux_pipe_directed
ties sheet_ready_i and out_ready_i high for the entire run, and
island_composed_directed ties sheet_ready_i high with a zero-latency loopback.

Also: the ordering comment at :215-216 claims degenerates enter the return queue
"in the same order". They do not -- a degenerate completes in one cycle while an
earlier non-degenerate waits an unbounded sheet round trip. Harmless today
because FRAGROB rejoins by token, but it is a documented property the RTL does
not hold. And `rq_tok[rq_wp] <= sheet_rtok_i` accepts ANY response token.

Repairs: a held offer (a bounded FIFO whose head IS the offer, so valid and
payload are stable to the acceptance edge by construction), a credit on
req_ready_o released only at terminal acceptance, a return queue sized to the
credit with the sheet responder given absolute priority for the free slot
because it has no ready line. THE DIVIDER AND ITS NUMERICAL LAW DO NOT CHANGE.

5A.7 The repair: typed sample completions
------------------------------------------
THE INVARIANT, stated so it can be tested: every request accepted into the
sample path produces EXACTLY ONE terminal completion, carrying the identity it
was issued under, and that completion is either valid data or an explicitly
enumerated refusal. No path may consume a request without producing one.

  1. ONE RESOLVED SAMPLE DESCRIPTOR, formed once at planner acceptance from the

  2. ONE metadata read after the raw FIFO, before class dispatch. Today
     sampmeta_m is read independently by the bilinear path (:850-851) and the

  3. A TYPED COMPLETION and a merger that carries it:
       COMPLETE_OK       + rgb888 + alpha8

7. A LAW THIS CODEBASE HAS NOW LEARNED THREE TIMES
==================================================
Do not initialise a per-entry store at allocation. It creates a second write
address, which is the one thing an M10K simple-dual-port cannot have.

  COMBINE   the prior brief states it for scratch, in as many words
  PERSPUV   e_q_u/e_q_v had it, and it was redundant as well as costly
  COMBINE v2  the draft reintroduced the FLAG half of it -- phase 0 inheriting
            the previous occupant's saturation

Where the initialisation is genuinely needed -- a sticky flag like `e_sat` --
keep it and keep the array in flops, deliberately, because the array is small
and the alternative is a correctness bug. State which of the two applies at
every such site.
