0. THE DECISION IN ONE PAGE
==========================

The current island is not one coherent production texture machine. It contains
several locally repaired execution blocks connected through another layer of
large, frequently asynchronous, fragment-indexed stores and lifetime conversion
logic. Functional repairs made more of the intended machine real. They also
exposed the cost of the surrounding organization. [R01-R07]

The latest completed fit is 16,192 ALMs, 28,490 registers, 17 DSP blocks, 32 M10Ks,
and a reported 67.57 MHz. The nominal product clock remains 100 MHz. The existing
architecture document's island area and register limits are much lower. This is
not acceptable production closure. [R01, R02, R08]

The response is NOT to rewrite COMBINE again, lower the clock, or add a register
to a RAM write-enable without accounting for the new in-flight state.

The production decision is:

  A. Allocate one owner handle immediately after Early-Z, before reciprocal or
     texture work. Keep it until the final output handshake. Preserve the
     existing end-to-end owner-credit repair; make the owner the actual storage
     address throughout the island instead of merely a wrapper safety limit.

  B. Replace the ingress-table / FRAGROB-slot / final-ROB lifetime chain with a
     single 64-owner transaction file. Partition that file by physical writer,
     physical reader, and lifetime. Do not build one enormous multiported RAM.

  C. Store persistent payload in synchronous M10K-backed banks. Keep only small
     scoreboards, queue pointers, valid bits, and genuinely bounded pipeline
     registers in fabric. Every bank gets an explicit port and collision law.

  D. Replace FRAGROB's return-to-RAM-write-enable cone with a real completion
     pipeline: capture, validate and claim, commit payload, publish completion.
     Preserve stale, unsolicited, duplicate, and out-of-range rejection. A
     delayed write-enable alone is not this pipeline.

  E. Queue readiness events exactly once. Remove the intermediate globally
     ordered FRAGROB retirement barrier. Execute ready material jobs out of
     order and restore externally required order only at final retirement.

  F. Use one resolved sample descriptor as the sole authority for format,
     filtering, byte/nibble selection, palette identity, and error status.
     Delete the independent class bits from the request identity. Resolve
     actual bindings rather than using late global base/mode pins.

  G. Preserve COMBINE V2's paired phases and exact eight-recipe arithmetic.
     Preserve the repaired cache's response reservations and static RAM banks.
     Do not trade known correctness fixes for a smaller misleading fit.

  H. Replace PERSPUV's independently scheduled U/V context tables with one
     paired, streaming arithmetic pipeline. Preserve one complete U/V pair per
     clock. Split shifts, adds, and saturation by actual register boundaries.

  I. Replace RCP's free/ready/done scans with queues and bounded execution
     contexts. Replace its wide multiplier with an exact 32x32 product plus a
     signed-wrap correction. The proof does not assume the Newton correction
     is always positive and does not require a new reciprocal approximation.

  J. Add completion credits before non-backpressurable palette or external
     response launches. Only after doing that may the merger become fair and
     independently stallable.

  K. Make the final result bank synchronous and give its read pipeline an
     explicit output reservation. Free an owner only when its result leaves
     the island, not when the result is written or prefetched.

  L. Prove structure with cheap synthesis and microbenchmarks before another
     multi-hour composition fit. Publish the actual fitted source snapshot,
     not merely the Git HEAD that happened to exist when a runner started.

The useful change is a physical contract, not a new slogan. The repository
already contains earlier advice about RAMs and tokens. This specification makes
that advice concrete enough that the next agent cannot implement another large
asynchronous table, call it a transaction file, and declare the architecture
complete.


1. WHAT THE FIT ACTUALLY ESTABLISHES
==================================

1.1 The two comparison rows
---------------------------

                                    Transitional V1       Repaired V2
                                    ---------------       -----------
ALMs                                      16,193              16,192
Registers                                 27,097              28,490
DSP blocks                                    17                  17
M10K blocks                                   25                  32
Reported Fmax                              63.54               67.57 MHz

The V2 delta is minus one ALM, plus 1,393 registers, unchanged DSPs, plus seven
M10Ks, and plus 4.03 MHz, approximately 6.3 percent. [R01, R02]

The fitter summary records successful placement/routing, not successful timing
closure at the product target. It also records 1,484 virtual pins and 743 ALMs
containing virtual pins. The logical block-memory contents total only 36,024
bits. The target device has 41,910 ALMs, 553 M10Ks, and 112 DSP blocks. [R01]

Do not call seven additional M10Ks intrinsically bad. Moving state from fabric
into embedded RAM is explicitly the intended recovery. The concerning facts are
that the register count still rose and the island remains far outside its area
and timing allocation. A memory-block count going up can be evidence of the
right trade, not evidence of a catastrophe.

1.2 What the timing analysis says, with its evidence boundary
------------------------------------------------------------

The author's analysis reports 3,904 summarized timing paths. Of those, 3,715
start at virtual pins and 189 start internally. The reported worst virtual-pin
path is -4.800 ns; the worst internal path is -2.936 ns. The latter endpoint is
inside FRAGROB and reaches an inferred RAM write-enable. Of the 189 internal
paths, 136 end in FRAGROB, 35 in PERSPUV, and 18 in RCP24. COMBINE appears on none
of the summarized paths. [R02, R03]

These observations justify investigation of FRAGROB's return and allocation
control, the surrounding transaction stores, and the arithmetic service tables.
They do NOT establish that FRAGROB owns most ALMs or registers. Endpoint timing
attribution is not hierarchical area attribution. They also do not prove that
COMBINE has no problematic paths anywhere outside the sampled reports.

The familiar conversion 1000 / (10 + 2.936) = approximately 77.30 MHz is a useful
diagnostic under the assumed 10 ns, single-cycle timing relationship. It is not
a new fitted design and not a measured integrated operating frequency. Removing
virtual pins changes placement, routing, and timing relationships. Their effect
cannot be subtracted as a fixed 9.7 MHz coupon.

Likewise, 67.57 to 100 MHz requires roughly 48 percent more frequency. Expressed
as effective period, approximately 14.8 ns must become 10 ns, a 32.4 percent
reduction. Even the 12.936 ns internal diagnostic needs about a 22.7 percent
period reduction. Those are structural targets, not a plausible seed-only plan.

Vendor guidance treats Fmax summaries as benchmarking information; constrained
slack reports are the sign-off authority. Setup, hold, recovery, removal, clock
relationships, minimum pulse width, and unconstrained paths all matter. [V05]

1.3 The V2 measurement is deliberately confounded
------------------------------------------------

The run log says the V2 swap and W9b decode repairs were present in the frozen
15-source closure. The composed test was watched passing 108 checks before the
launch. W9b made nearest decoding live, carried format, restored real alpha,
and expanded filtered samples to four channel phases. [R03, R04, R15]

The net ALM result does not isolate COMBINE's savings. It also does not precisely
prove that a certain number of combiner ALMs were replaced by exactly as many
decode ALMs. Synthesis sharing, packing, and placement are nonlinear. The honest
statement is that the net design has essentially unchanged area; the individual
contributions were not separately measured.

COMBINE's disappearance from the reported critical-path sample is encouraging
local evidence. Calling the whole island a performance success would be wrong.
Calling the whole project impossible would also exceed the evidence.

1.4 Fitted snapshot versus recorded source commit
-------------------------------------------------

The report identifies sourceCommit 064d5fad, while the run log describes later
working-tree V2/W9b bytes captured in a frozen directory and subsequently
verified after commits. This is consistent with a runner recording the launch
HEAD rather than a clean commit containing every fitted byte. It is not enough
for clean-clone reproducibility. [R02, R03]

This review verified that the pinned current top really instantiates COMBINE V2
and contains the repairs. The claim that the historical fit used them rests on
the published closure verification and report. The next runner must eliminate
that ambiguity by recording per-file SHA-256 hashes and the full QSF/SDC closure.

1.5 Functional completeness is still a separate gate
----------------------------------------------------

The current test intentionally uses fully drained mode phases because binding
base/mode are global live ports. CLUT4 nibble selection remains absent at the
composed decode point. The top still interprets opaque context bits as AUX world
coordinates and supplies a fixed envelope. Different sample bindings are not
actually used by the planner's address selection. [R04, R13, R15]

Consequently this fit is a valid measurement of a transitional implementation,
not evidence that a complete production material system merely needs a faster
clock. The new architecture must close those semantic gaps while changing the
physical organization. Otherwise another smaller number will measure a missing
piece of the intended machine.


2. REPOSITORY DIAGNOSIS: THE REAL IMPLEMENTATION, NOT ITS COMMENTS
================================================================

2.1 Four lifetimes are currently being confused
-----------------------------------------------

The top has a 64-owner end-to-end credit, 64-entry ingress attribute tables,
local reciprocal and perspective contexts, a 16-slot FRAGROB, eight COMBINE V2
execution contexts, and a separate 64-entry final reorder buffer. Local
execution capacity is legitimate. Multiple translations of persistent fragment
identity and duplicated ordering responsibilities are the avoidable part.
[R04-R07, R09-R11]

The owner credit fixed a real overwrite risk: FRAGROB retires upstream of the
final output, so FRAGROB capacity alone cannot bound completed fragments waiting
at the output. That repair must survive. V3 changes the rest of the design to
agree with it: the owner is the persistent record address from admission to
emission. Execution-context IDs never become replacement fragment identities.

2.2 Capturing inputs is necessary but not a physical architecture
---------------------------------------------------------------

The top now captures u/w, v/w, context, base colour, binding, LOD, class, palette
identity, count, recipe, weight, and sequence. That fixes late reads of many
fragment pins. However, several consumers still use asynchronous indexed reads
from those tables, sometimes at different pipeline points. [R04]

Examples include uvw_m indexed by the reciprocal token, attributes indexed by
the perspective tag at FRAGROB admission, and material fields indexed by the
FRAGROB token at COMBINE admission. The final result array is also read directly
at the output head. A clocked write and no explicit payload reset do not make an
asynchronous read a cheap M10K port.

Some arrays have only one logical read address and still need a synchronous
read stage. Other arrays, such as sample metadata, really have multiple class
consumers. Do not describe both cases as the same multiport problem. They need
different fixes: register the former; centralize or explicitly replicate the
latter.

Vendor documentation is explicit about synchronous memory inference and the
unsupported reset/control patterns that turn intended RAM into ordinary logic.
Registered-address-only styles can also require bypass logic or fail to infer;
the preferred template has a registered read output. [V01, V02]

2.3 FRAGROB's payload is already partly banked; its control is not harmless
-------------------------------------------------------------------------

FRAGROB has real clock-only payload processes and sample-indexed result banks.
It also validates an incoming sample by selecting slot state, checking the
generation, clamping/checking sample index, testing requested and issued bits,
and checking that the result has not arrived. That combinational decision
immediately drives the result-bank write. [R05]

This is the plausible mechanism behind a path ending at a RAM write-enable.
The published endpoint supports the investigation, but this review has not
independently established the detailed startpoint, fanout, or delay breakdown
of the worst path. The architecture therefore breaks the entire dependency
chain rather than asserting an unmeasured exact culprit cell.

The current sample issue FSM uses IDLE, READ, and HOLD. Its normal handshaken
sequence is not a one-descriptor-per-clock issue pipeline. Work storage accepts
up to three sample entries on allocation, then reads them through a serialized
issue machine. There is also a nested queue-to-generation lookup. This is a
poor fit to the stated production throughput objective. [R05]

The new return design must retain the existing six-part identity rejection and
the issued-bit repair. Removing those checks to shorten the write-enable cone
would reintroduce stale results, duplicate overwrites, and unsolicited returns.

2.4 Metadata is being recovered too late and through too many readers
-------------------------------------------------------------------

The current 20-bit sample metadata word contains format, filter fractions, and
a byte selector. Bilinear, nearest, and palette consumers independently index
it after dispatch. Palette slot and generation are recovered from additional
FRAGROB-slot tables. [R04]

V3 performs one metadata read before class distribution. The resulting packet
contains all decode information needed downstream. A raw response no longer
causes several independent lookups of persistent owner state.

2.5 Binding identity is not yet address identity
------------------------------------------------

FRAGROB emits a binding value, and the top constructs per-sample binding
variants. The planner nevertheless receives bind_base_i and bind_mode_i directly
from the top-level live pins, not a descriptor addressed by that binding. The
composed test's drained-mode phases are an explicit workaround for this fact.
[R04, R13, R15]

A production fit must contain a real binding resolver and the registered
configuration interface it requires. A token field that is carried, counted,
and never influences the requested address is not a completed feature.

2.6 Class is a second, disagreeing authority
------------------------------------------

The planner emits resolved format, effective filtering, and error information.
The top computes a derived class for comparison but still routes by the class
carried in the source token. That is redundant authority, not useful metadata.
[R04, R13]

V3 makes class a derived routing result. The compact sample token uses the two
freed class bits for the larger canonical owner slot. The token describes who
owns the request, not how its payload is interpreted.

2.7 Palette completion cannot currently wait
-------------------------------------------

The palette lookup produces a pulse without response-ready. Its request is
issued unconditionally when the CLUT class queue is nonempty. The merger gives
it absolute priority, and its safety depends on FRAGROB being unconditionally
ready. The top itself documents this cross-module invariant. [R04, R14]

Adding backpressure to FRAGROB without first giving palette returns reserved
storage drops responses. Replacing priority with round-robin before that repair
has the same failure. The result is not just a wrong colour: one incomplete
owner can stop strict final retirement forever.

2.8 Error colours are not an error-status plane
-----------------------------------------------

The current top converts several sample failures into a counted magenta sample
so that the fragment can retire. This is better than dropping the transaction.
However, the sample failure is not carried into FRAGROB as an independent typed
status. The final refused output is primarily COMBINE's own refusal. Material
math can alter the magenta and hide the diagnostic nature of the sample.
[R04, R15]

V3 preserves terminal completion and preserves the declared fallback pixels
where required for compatibility, but separately accumulates a status word.
Colour is data. A failure flag must not be inferred from colour.

2.9 PERSPUV still pays for an unnecessary second scheduler
--------------------------------------------------------

The current service correctly added two product lanes and separate arithmetic
stages. It still allocates a token table, maintains one queue per axis,
duplicates reciprocal mantissas for independent reads, writes separate U and V
result tables, then joins them at a head. Both axes are actually issued from the
same admitted pairs and use the same reciprocal. [R09]

V3 does not reduce the lane count. It removes the independent scheduling that
created the storage ports. A paired packet enters, both products advance under
one valid/credit contract, and a paired packet leaves. The arithmetic remains
separately registered, including the depth-zero bypass.

2.10 RCP24 is still the scan-based wide-operand implementation
------------------------------------------------------------

The inspected reciprocal service scans for a free context, scans for a ready
micro-job, and scans for a completed context. The selected context feeds the
operand mux and a 32-by-64-bit multiply expression. c_w is stored as 64 bits,
although every MW write is a 24-by-32-bit product shifted right by 24. [R10]

That last fact supports an unconditional width proof: w fits in 32 bits. It does
NOT by itself prove that 2^31-w is nonnegative. Section 10 retains the negative
case exactly while removing the unnecessary wide multiplier operand.

2.11 The dispatcher is still copying wide payloads
--------------------------------------------------

The dispatcher contains a raw FIFO plus four per-class FIFOs, with separate
64-bit payload arrays and token arrays. It has a useful unknown-class terminal
queue and honestly documents raw-FIFO head-of-line blocking. It is not yet the
single-payload-store / narrow-ticket organization previously proposed. [R12]

V3 keeps class decoupling and the terminal path. It stores each prepared payload
once in a small shared pool, queues pool indices, and reads the pool through a
single scheduled port into class-local holding registers.

2.12 The cache repairs are worth preserving
-------------------------------------------

The current cache explicitly accounts for queued responses plus probe results
in flight. It reserves a response slot at issue and refunds squashed probes on
a miss. It has static generated tag/data banks and a fabric capture stage after
RAM. These are exactly the kinds of physical and conservation rules V3 needs.
[R11]

Do not tear out these repairs simply because the entire island is being
reorganized. The cache is a retained component with a revised surrounding
contract, not an excuse for another unverified rewrite.

2.13 AUX and Mosaic are not complete production connections
-----------------------------------------------------------

AUX still receives world X/Z by slicing fr_aux_ctx, which is otherwise described
as opaque context, and receives the hardcoded envelope 0..65536 on both axes.
The resulting tag/strength is packed as a colour-like third sample. Mosaic is
exercised and counted, but its selection must actually affect the selected
material/binding before the feature can be claimed as semantically integrated.
[R04]

V3 provides explicit world coordinates and an immutable envelope descriptor.
It keeps opaque context opaque. It gives Mosaic's selection a named consumer
and a reference-visible consequence rather than accepting a moving counter as
proof of use.

2.14 Comments are historical evidence, not current truth
-------------------------------------------------------

Several inspected files still say that nothing instantiates them. They are
instantiated. Several top-level comments describe one or three bilinear phases
while live code uses four. A FRAGROB comment still discusses an unfrozen sample
zero combiner although the top uses COMBINE V2 with real sample banks. [R04-R14]

The new spec and verification matrix must be generated or checked against live
ports, instances, counters, and manifests. Keeping old narratives in source is
not a substitute for a precise current contract.

One additional audit item deserves a focused test: in the inspected bilinear
collector reset branch, bil_expect_r is not visibly initialized alongside the
other collector state. Treat this as an unverified source-level reset concern,
not a reproduced failure. A four-state/reset-reuse test must decide it. [R04]


3. ARCHITECTURAL LAWS AND ACCEPTANCE TARGETS
===========================================

The following are design requirements of V3, not observations of current RTL.
They become binding implementation rules when adopted by the owner.

LAW 01: One fragment owner from admission through external emission.
LAW 02: Owner credit is returned only at the external output handshake.
LAW 03: Execution contexts are not new fragment lifetimes.
LAW 04: Every accepted required request has one terminal completion, including
        declared errors. Rejected duplicate/unsolicited packets do not create
        additional terminal completions.
LAW 05: A completed bit means its payload is already committed and readable.
LAW 06: A claimed bit means a valid return is reserved for commitment; a second
        copy must already be rejected even before the RAM write occurs.
LAW 07: Every persistent bank has enumerated physical writers and readers.
LAW 08: Wide persistent arrays have clock-only payload processes and
        synchronous read outputs. Valid/control state is reset separately.
LAW 09: A result RAM write-enable is registered; it is not a table lookup,
        priority scan, arithmetic decision, and memory enable in one cycle.
LAW 10: Work is queued when it becomes available; no table-wide work scan.
LAW 11: One resolved descriptor determines format and routing.
LAW 12: A token carries identity, not a second copy of mutable interpretation.
LAW 13: Palette/other pulse responses have storage paid for before launch.
LAW 14: No field is reread from ingress after its acceptance handshake.
LAW 15: Independent opaque context, world coordinates, material attributes,
        palette identity, and binding identity are not packed into each other.
LAW 16: One global ordering boundary, at final externally visible retirement.
LAW 17: Exact integer arithmetic, width, overflow, saturation, and rounding
        remain the repository reference's law.
LAW 18: Throughput is specified in fragments, samples, channels, phases, and
        memory beats separately. A faster clock does not excuse more work.
LAW 19: No physical gate passes on a fixture that leaves a claimed feature dead.
LAW 20: No result is reproducible without the fitted source and constraint
        closure, tool version, parameter set, and report provenance.

Product and closure targets:

  Product clock                         100 MHz
  Full-composition acceptance floor     105 MHz
  Full-composition objective            110 MHz
  Full-composition stretch              115 MHz
  Standalone island headroom objective  115-120 MHz

These preserve the earlier architecture's clock policy. A standalone island
that barely reaches 100 MHz has not earned permission to consume composition
margin. A 115 MHz leaf fit is also not proof that the shell will reach 105 MHz.
[R08]

Resource allocations for the actual production island:

  ALM working objective                 5,500-6,600
  ALM architecture redline              7,500
  Register working objective            6,000-8,000
  Register architecture redline         9,000
  M10K working range                    32-56
  M10K escalation threshold             64
  DSP working objective                 10-13 or lower without throughput loss
  DSP architecture redline              14

The 64-M10K threshold is retained here as an explicit escalation limit, not as
a reason to reject useful movement from fabric to RAM within the working range.
The detailed 55-block planning inventory in section 21 is a width/port budget,
not a Quartus prediction. Every objective remains subject to measured mapping.

Do not solve an area overrun by deleting status, alpha, CLUT4 selection,
independent sample coordinates, configuration lifetime protection, or owner
retention. Reallocate or redesign; do not make the measured machine incomplete.

===========================================

The production topology is:

  Early-Z survivors / material descriptors
                  |
          [A0 admission + credits]
                  |
        +---------+-----------------------------------------+
        |          ONE 64-OWNER TRANSACTION FILE             |
        | ctx | material | sample desc | geometry | status   |
        +---------+-----------------------------------------+
                  |
            owner ticket
                  v
        [RCP context queue + exact shared multiplier]
                  |
        reciprocal committed by OWNER
                  |
        [sample-owner queue + narrow ticket expansion]
                  |
        one (owner, sample, u/w, v/w, reciprocal, binding) job
                  v
        [paired PERSPUV pipeline, one pair/clock]
                  |
        [binding read + registered planner]
                  |
        resolved metadata committed by (owner, sample)
                  |
        [retained banked cache + response reservations]
                  |
        [raw capture + single metadata read]
                  |
        [shared response payload pool + class ticket queues]
             /                 |                 \
      [palette]            [nearest]         [RGBA bilerp]
             \                 |                 /
           [credited holding queues + fair completion merge]
                              |
               [capture -> validate/claim -> commit]
                              |
             sample-result banks + completion status
                              |
       AUX: geometry read -> retained arithmetic -> same owner
                              |
               [once-only ready-event queues]
                              |
             [COMBINE V2 paired-phase execution]
                              |
               final-result bank[owner] + final_done
                              |
           [ordered synchronous prefetch + output queue]
                              |
                     external handshake
                              |
                       owner is freed

Physical module boundaries proposed for new code:

  zhao_texture_owner_v3
  zhao_texture_records_v3
  zhao_texture_sample_expand_v3
  zhao_texture_completion_v3
  zhao_texture_ready_events_v3
  zhao_texture_binding_resolve_v3
  zhao_texture_response_pool_v3
  zhao_texture_decode_v3
  zhao_texture_retire_v3
  zhao_raster_rcp24_queue_v3
  zhao_raster_perspuv_pair_v3
  zhao_texture_island_v3_top

Names are proposals. They do not claim that those files already exist.

Retained or adapted components include the cache's static bank/probe machinery,
the integer TMU address law, the bilerp arithmetic, the palette protocol in its
compatibility mode, AUX arithmetic, Mosaic's reference hash, and COMBINE V2's
paired phase execution. The architecture does not depend on replacing every
leaf at once.

The transaction file is a logical collection of banks. It is NOT a single
physical centralized RAM with every pipeline stage demanding a port. Banks
should sit near their owning producer/consumer pairs. The owner handle gives
them a common address space, not a common location or a broadcast data bus.

The control plane similarly is not a 64-entry centralized scheduler. Small
per-owner masks are updated by bounded event ports, and queue heads provide
work. Counters and assertions describe the conservation law; they do not scan
wide payload tables every clock to reconstruct it.


5. OWNER IDENTITY, ALLOCATION, RETIREMENT, AND GENERATION WRAP
============================================================

5.1 Canonical identity
----------------------

The baseline owner capacity is 64. A fragment owner handle contains:

  owner_slot       6 bits
  owner_generation 8 bits

A texture-sample handle adds sample_index[1:0], giving exactly 16 bits:

  sample_handle[15:10] = owner_slot
  sample_handle[9:8]   = sample_index
  sample_handle[7:0]   = owner_generation

Sample indices 0, 1, and 2 are valid texture sample identities. Encoding 3 is
reserved and must be rejected before indexing a three-bank array. AUX uses a
separate typed port with the 14-bit owner handle; it is not smuggled into sample
index 3 on an interface that promises only three texture banks.

The old token used two class bits, a four-bit FRAGROB slot, two sample bits, and
eight generation bits. V3 removes class from identity and spends those two bits
on the canonical six-bit owner slot. There is no silent token widening, no
truncation of a 64-owner slot into a 16-slot namespace, and no conversion table.

All token layouts belong in a generated cross-language ABI definition. Tests
must pack and unpack all slot values, all sample values, and generation boundary
values in C++ and RTL. Compile-time checks reject inconsistent parameters.

This compact layout is a baseline interface choice, not a mathematical claim
that eight generation bits defeat an arbitrarily late response. Section 5.5
supplies the necessary lifetime rule.

5.2 Allocation
---------------

Use a 64-entry circular owner ring in admission order. Keep allocation_tail,
emit_head, and a seven-bit live count. A request is accepted only if:

  - an owner slot is available;
  - its admission/payload write can occur;
  - the appropriate initial work/event ticket has reserved storage;
  - the configuration epoch is valid and not being drained for replacement;
  - the reset/drain controller permits new work.

The corresponding valid presented to an upstream execution service must be gated
by exactly the same admission decision. Gating ready alone while allowing an
RCP valid to fire recreates an unowned request.

At an accepted admission edge, write the persistent input planes at tail, stamp
the owner handle, initialize only the narrow scoreboard, enqueue initial work,
and advance tail. The owner payload is not reset and is never zero-filled merely
to make simulation look initialized.

Do not implement a free-list scan over the owner table. Because owners are
allocated and externally retired in order, a ring is sufficient. A conservative
full-cycle policy that declines admission when full even if an output will leave
that edge is acceptable initially. A same-cycle full replacement optimization
requires a separate collision proof and does not belong in the first recovery.

5.3 What the owner controls
---------------------------

A live owner reserves its own result rows, material row, opaque context row,
metadata rows, and final-result row. It can also reserve at most one ticket in
each phase-specific owner queue. It does not reserve a multiplier forever and
does not imply that every execution block needs 64 local contexts.

RCP has its own bounded latency-hiding execution contexts. COMBINE retains eight
contexts initially. Response-pool slots have their own shorter leases. Each
lease carries the owner handle but is released at its local consumption event.
Only the owner lease lasts through output emission.

The global invariant is:

  accepted_fragments - emitted_fragments - explicitly_acknowledged_aborts
      = number_of_live_owners
      <= 64.

In the baseline normal-operation profile there are no per-fragment aborts;
therefore the third term is zero. A diagnostic timeout does not silently invent
an abort or free an owner.

5.4 Retirement and slot reuse
-----------------------------

The only ordinary owner-free event is out_valid && out_ready for that owner at
the final output. It clears live, advances emit_head, and returns owner credit.
Writing final_result does not free it. Enqueuing its result does not free it.
Prefetching context and colour does not free it. COMBINE completing does not
free it. RCP and sample completion certainly do not free it.

A new admission may overwrite a slot only after the previous occupant's external
emission or a defined global reset/drain operation. Thus the output queue may
hold data from a live owner without exposing that owner's backing rows to reuse.

Payload and generation checks must agree on the exact accepted edge. Never
write a payload using next_tail while stamping the handle with current_tail.
Tests must intentionally run more than 64 admissions under prolonged output
backpressure and verify that ready falls before any live row is overwritten.

5.5 Generation wrap is a protocol issue, not a bit-width incantation
------------------------------------------------------------------

With eight generation bits a slot returns to the same generation after 256
reuses. A sufficiently delayed duplicate can then match again. The same issue
exists in the present palette-generation discussion: increasing four bits to
eight postpones wrap; it does not abolish wrap.

The baseline compact-token contract requires one of these enforceable policies:

  BASELINE POLICY: before the owner namespace wraps, stop new admission, drain
  all live owners and all external outstanding transactions, empty return and
  execution queues, obtain the relevant memory/sheet transport drain
  acknowledgements, and only then reuse the wrapped namespace.

  ALTERNATIVE POLICY: use a wider end-to-end generation/epoch and a formally
  bounded response lifetime proving that namespace reuse cannot overlap that
  lifetime. This changes the token ABI everywhere; widening only one module
  does not solve anything.

V3 selects the baseline drain policy unless the surrounding shell already
provides a stronger verified epoch contract. Its cost is included in frame
throughput measurement. It must not be optimized away because normal tests do
not retain a stale packet for 16,384 admissions.

A drain acknowledgement is meaningful only if the external producer promises
not to emit another packet from the old epoch. Waiting a guessed number of
clocks is not equivalent. Arbitrary malicious or indefinitely delayed packets
cannot be made harmless by any finite internal generation field alone.

5.6 Opaque context and output compatibility
-------------------------------------------

Keep the full 64-bit opaque context in a dedicated two-M10K plane and return it
at the final output. A legacy 16-bit tag can be derived from its low bits in a
compatibility wrapper, but the upper bits must remain observable in the
production conformance wrapper. Otherwise synthesis may erase supposedly
preserved context, and the fit will not cost the promised interface.

Do not reuse context bits for sequence, AUX coordinates, palette generations,
or a binding. Those are different types with different lifetimes. The owner
handle is the sequence identity; context is caller data.


6. THE TRANSACTION FILE: BANKS, PORTS, AND PHYSICAL GEOMETRY
===========================================================

6.1 Physical partitioning rule
------------------------------

Group fields that are written by the same event and read by the same scheduled
consumer. Split fields whose write or read ownership differs. Replicate a small
read-only field only when it is explicitly cheaper than adding another port,
and record the replication in the resource inventory.

Do not group fields just because they belong to a fragment. Conversely, do not
split every two-bit field into its own forced M10K. Narrow control is often
better in flops. A physical port diagram is the deciding artifact.

The following is the baseline persistent-bank contract. Widths are allocation
budgets; the generated packed ABI must define every reserved bit and reject
unsupported records. A width change requires updating the physical inventory.

 BANK                  DEPTH x WIDTH       SINGLE WRITER       SINGLE READER
 --------------------  ------------------  ------------------  -----------------
 OWNER_CONTEXT             64 x 64         admission           ordered retirement
 MATERIAL                  64 x 48         admission           combine admission
 AUX_GEOMETRY              64 x 80         admission           AUX issue
 SAMPLE_DESC_0             64 x 80         admission           sample expansion
 SAMPLE_DESC_1             64 x 80         admission           sample expansion
 SAMPLE_DESC_2             64 x 80         admission           sample expansion
 RCP_RESULT                64 x 32         RCP final commit    sample expansion
 SAMPLE_RESULT_0           64 x 40         TMU commit bank 0   combine admission
 SAMPLE_RESULT_1           64 x 40         TMU commit bank 1   combine admission
 SAMPLE_RESULT_2           64 x 40         TMU commit bank 2   combine admission
 AUX_RESULT                64 x 40         AUX commit          combine admission
 FINAL_RESULT              64 x 40         combine completion  ordered retirement
 SAMPLE_METADATA          256 x 40         planner accept      response preparation

SAMPLE_METADATA uses {owner_slot, sample_index} as an eight-bit address. The 64
rows with sample_index 3 are intentionally unused. A 256x40 shape matches a
native simple-dual-port M10K width/depth geometry. Do not compress it to 192 rows
through a multiply-by-three address calculation unless a measured benefit
justifies the added address logic.

A result word is RGBA32 plus STATUS8. The status width is a deliberate ABI budget.
A material word holds base RGBA32, recipe3, count2, weight8, and three source-map
or compatibility bits, totaling 48. Expanding material semantics beyond those
bits must be explicit; it must not be hidden in a context or tag.

Each sample descriptor budget is numerator_u32 + numerator_v32 + binding_id8 +
LOD_Q4_4_8. This supports independent sample coordinates and bindings instead
of silently copying sample zero three times. If the caller explicitly shares
coordinates, its adapter may submit identical values; that does not make the
storage contract ambiguous.

AUX_GEOMETRY's 80-bit budget is world_x32 + world_z32 + envelope_selector8 +
configuration_epoch8. Envelopes themselves live in a small separately budgeted
configuration store. The current unit-square envelope is represented by an
actual configured descriptor, not hardcoded arithmetic wiring.

6.2 Why capacity-in-bits is the wrong M10K estimate
--------------------------------------------------

Cyclone V simple-dual-port M10K modes include 256x40 and 512x20; true-dual-port
modes have different width limits. A shallow 64x64 independent store does not
cost ceil(4096/10240) = one block simply because its bit count is small. Its
width and port structure require a width-compatible tiling, typically two
simple-dual-port blocks for this contract. [V03]

Similarly, a supposed 1R2W scratch array is not rescued by having only 512 bits.
It either needs a different schedule, banking/replication with an explicit
coherence rule, or fabric logic. ramstyle cannot give an M10K an extra port.

The section 21 inventory counts width slices and independent port ownership.
It deliberately allows underfilled blocks. Saving thousands of flops and wide
muxes is more important here than maximizing the percentage of bits used inside
each M10K.

6.3 Access stages
-----------------

For every bank, distinguish these events:

  RQ: an address and response-destination credit are accepted;
  RR: the synchronous memory output register captures the requested row;
  RC: a fabric register captures the row and its aligned identity/valid;
  USE: the consumer performs selection, comparison, or arithmetic.

A bank may merge RR and RC only after the exact Quartus 17 microbenchmark proves
that the intended output register maps and the remaining consumer path meets
timing. The first production implementation uses an explicit capture boundary
where a broad consumer otherwise hangs from an M10K output.

Do not consume a fresh bank read using a tag delayed by a different number of
cycles. The read token, valid, status, bank selector, and bypass flags are a
single pipeline packet. Every stall preserves the whole packet.

6.4 Read-during-write laws
-------------------------

For each physical memory instance publish one of:

  - collision impossible by lifetime/schedule;
  - old-data semantics explicitly required and supported;
  - new-data semantics implemented by an explicit, verified bypass;
  - undefined data permitted because a separate valid guarantees no use.

Do not leave collision semantics as whatever Verilator and Quartus happen to
agree on in a friendly test. Vendor guidance requires matching the HDL behavior
to the actual memory mode. [V04]

For owner input planes, allocation cannot overwrite a live owner's row. For
sample-result planes, COMBINE eligibility is published after commitment and a
sample cannot be committed twice. For FINAL_RESULT, a committed result becomes
visible to retirement only after its write edge. For SAMPLE_METADATA, the cache
request cannot become externally visible before metadata is committed, and the
response pipeline must enforce the minimum separation or add a bypass.

Those laws eliminate most same-address conflicts without expensive forwarding.
The narrow scoreboard is different: it has genuine concurrent updates and needs
explicit event merging and recent-update forwarding, described below.

6.5 Reset separation
--------------------

Payload memory processes have only posedge clk. Reset clears valid/ownership
state, queue occupancy, outstanding reservations, and pipeline-valid bits.
It does not clear all payload arrays. A sweep used to initialize a free queue
is control initialization, not a reset loop over every pixel or descriptor.

Every bypass must avoid reading invalid old payload. The inspected PERSPUV
service already documents a bug where removing initialization exposed old
coordinates for a depth-zero reused slot. V3 keeps an explicit zero-coordinate
bypass and tests it after nonzero data has occupied the same slot. [R09]

Reset deassertion is synchronized to the island clock. External producers are
held in the reset/drain protocol until old responses cannot be misinterpreted
as new work. Clearing local valid bits while an old untagged fill stream remains
active is not a complete reset protocol.

6.6 Locality and control fanout
------------------------------

The common owner address does not require one giant global bus. Place input
planes beside descriptor expansion, result planes beside COMBINE admission,
and the final/context pair beside retirement. Carry narrow owner handles
between them. Register local write enables and bank selects near each bank.

A replicated local register carrying a write enable is acceptable when it is
measured and preserves exactly the same commit event. A replicated 64-entry
payload table because three modules want asynchronous access is not the same
trade and must not happen accidentally.


7. ADMISSION, CAPTURED ATTRIBUTES, AND DESCRIPTOR EXPANSION
=========================================================

7.1 Admission captures meaning, not just pins
--------------------------------------------

The production request record contains independent material data, opaque
context, three sample descriptors, optional AUX geometry, and the required-source
mapping. All of them are captured on the owner admission handshake. The source
may change every input on the next cycle, even while the island is stalled far
downstream. No subsequent stage reads those live pins again.

The legacy top lacks all of these independent fields. A compatibility adapter
can replicate the single U/V pair and translate its old AUX flag. That adapter
must be identified as a restricted interface, not the full production fixture.
The production testbench must drive different U/V numerators and different
bindings in the same fragment, with nonzero upper context bits and unrelated
world coordinates.

Configuration data is a separate concern. A binding ID is captured at admission;
the binding table it will resolve against must remain immutable for that owner's
configuration epoch. Section 12 defines the baseline drain/version policy.
Capturing an ID while allowing its referenced table entry to change arbitrarily
is another late-input bug in disguise.

7.2 Required logical inputs versus physical requests
----------------------------------------------------

For ordinary three-texture materials, required texture mask is 001, 011, or 111
for sample counts one, two, or three. Count zero follows the existing explicit
untextured base-colour behavior. An AUX substitution is a declared source for
a logical material slot, not an extra hidden fourth material input.

The compatibility phase preserves existing request accounting until a scalar
reference test establishes exactly which fetches are unnecessary. In particular,
do not silently stop requesting sample two merely because AUX later replaces
its colour without checking the contract, counters, and exception behavior.

The production source map should state, for each logical input used by the
recipe, whether it comes from a texture result, AUX, or the count-zero base
bypass. Once that law is accepted, a physically unused texture request may be
removed with a documented counter change and exact output equivalence. That is
an explicit optimization, not a side effect of the rearchitecture.

Invalid records become typed terminal outcomes. They must not issue partial
work that leaves a required bit impossible to satisfy. The validation order
must agree with the material reference, especially count-zero versus
missing-sample refusal.

7.3 RCP ticket and result
-------------------------

An owner requiring perspective work enqueues one 40-bit RCP_PENDING record:
owner_handle14 + raw_denominator24 + two reserved bits. This short-lived operand
is captured on admission, not reread from a live denominator pin when a context
becomes free. RCP_PENDING is a single-write/single-read 64x40 memory, not a
64x14 ticket queue with an unaccounted denominator table beside it. The reserved
bits are zero. The queue is counted explicitly in section 21.

An AUX obligation independently enqueues a 14-bit handle in AUX_PENDING, another
64-entry single-writer queue. Its consumer reads AUX_GEOMETRY with a reserved
AUX admission slot. RCP and AUX enqueue to different physical stores, so an
admission needing both does not create a two-write-port queue.

RCP execution uses its own contexts but writes a result associated with the
canonical owner. The
result contains mantissa24, exponent6, depth_zero1, and a validity/status budget.
The final result write precedes publication of the sample-expansion ticket.

The RCP result bank has one writer. Depth-zero/bypass work joins the same final
commit stream rather than creating an admission-side second write port.
Requests that need no reciprocal can enter a separately bounded initial-ready
path, with explicit accounting for their absence from RCP job counts.

7.4 Expand narrow tickets before the wide memory read
-----------------------------------------------------

SAMPLE_OWNER stores owner_handle14 plus the frozen three-bit texture-required
mask, for a 17-bit queue row. At RCP publication, capture that immutable narrow
mask from owner control into the queue; do not add a second MATERIAL read port.
The queue is one writer/one reader and still occupies one M10K.

A small current-owner sequencer emits at most one sample handle per clock from
that mask. Two narrow owner-head registers provide lookahead so the next owner
can replace the current one without a bubble on an all-one-sample workload.
This is a three-bit local mask walk, not a priority scan of 64 owner records.

Only AFTER choosing the sample handle does the expander launch the wide reads:
read SAMPLE_DESC_0/1/2 at the selected owner and RCP_RESULT at the same owner.
The three descriptor banks are static independent RAMs. The registered sample
index selects the one matching 80-bit output into a fabric capture. Re-reading
the 32-bit reciprocal for each of an owner's samples spends its single read
port once per issued sample; it does not require replication or multiple ports.
No multiplication or binding lookup sits in this output-selection stage.

Thus one issued ticket becomes one 80-bit descriptor plus reciprocal/token
packet, rather than prefetching all three descriptors into multiple 272-bit
owner bundles. This explicitly reduces wide pipeline state. It also avoids the
incorrect claim that two destination credits can sustain a three-cycle read
round trip at one one-sample owner per clock.

The read path has bounded elastic capture stages or reservations covering every
nonstallable memory read in flight. Its one-sample-per-clock target is tested
with all-one-sample owners as well as three-sample owners; throughput cannot be
inferred merely because the local sample-index counter increments every cycle.
Owner selection, bank read, and packet transfer each have separately defined
handshakes. A ticket leaves the sequencer only when its read-stage capacity has
been paid for.

The expansion queue receives RCP completion events, not original admission
order. An unfinished older reciprocal must not prevent a ready younger owner
from expanding its samples. Final emission remains the only global ordering
barrier.

7.5 Work conservation and pre-cache errors
-------------------------------------------

The architectural texture-issued event occurs when the captured sample packet
is accepted into the sampler service, before binding validation and cache
access. The normal path reaches that event at the credited paired-PERSPUV input;
its explicit zero-coordinate bypass uses the same accepted-service event.
The issued bit is not postponed until a cache request, because an invalid
binding or unsupported descriptor must be able to terminate before any cache
request exists and still satisfy the completion validator's issued check.

Address-planning, cache acceptance, replay, decode, and architectural sample
acceptance have separate counters. A pre-cache error produces one terminal
sample outcome under that already-issued handle. It does not fabricate a cache
response or increment a cache-access counter. Replaying a probe does not create
a second architectural sample obligation.

The same rule applies to AUX: its architectural service begins when a credited
AUX_PENDING ticket enters geometry/envelope resolution. An invalid envelope
may terminate before the arithmetic leaf or sheet is invoked. Preserve distinct
wrapper-service, leaf-admission, and sheet-request counters so that those paths
cannot be mistaken for lost work.

Required masks are frozen before any issue. Completion does not discover how
many samples the owner intended by counting whatever happened to return.
An invalid material record rejected before any service admission must have an
explicit zero-work terminal/refusal path; it must not leave required bits set
for work that the validator prevented from ever being issued.


8. COMPLETION CAPTURE, VALIDATION, CLAIM, COMMIT, AND PUBLICATION
================================================================

This section is the direct replacement for the most important FRAGROB timing
cone. It must be implemented as a protocol, not as an isolated pipeline patch.

8.1 State per owner and source
------------------------------

For three texture samples plus AUX, keep narrow masks:

  required[3:0]  source is architecturally required;
  issued[3:0]    a request was actually accepted downstream;
  claimed[3:0]   a validated return owns the right to commit;
  committed[3:0] its payload/status has been written;
  ready_claimed  an eligibility event has reserved the one ready ticket;
  combine_issued;
  final_claimed;
  final_done;
  live and generation.

Final COMBINE return has its own final_claimed bit for the same reason sample
returns have claimed: two final packets arriving before final_done must not
both acquire the right to write. It is set by the validated final-result claim,
retained through the write/publication, and cleared only at owner reinitialization.

The four source bits are an internal scoreboard convention. They do not change
the three-sample texture-token ABI or allow sample_index 3 on that port.

Keep these masks as small fabric state. They have genuine concurrent events and
are not the place to force an impossible multiported M10K. Do not mix the wide
RGBA payload into the same scoreboard word.

8.2 Return pipeline
--------------------

The baseline timing partition is:

  C0 CAPTURE
     Accept a return packet into a credited local register/FIFO. Capture its
     entire owner handle, source index, RGBA, typed status, and origin.

  C1 READ CONTROL
     Register the addressed narrow owner-state snapshot and a safe static bank
     selection. No payload RAM write occurs. Out-of-range indices are detected
     before they can select outside a declared array.

  C2 VALIDATE AND CLAIM
     Apply identity, required, issued, duplicate, and recent-update checks.
     An accepted first return atomically sets claimed and produces a registered
     commit packet. A rejected return increments the appropriate diagnostic
     and never asserts a result-bank write.

  C3 COMMIT
     The registered commit packet drives exactly one static sample bank, or the
     separate AUX bank. Write the complete RGBA+status row. No generation table
     lookup is in the RAM write-enable cone at this edge.

  C4 PUBLISH
     Publish the committed bit/event after the payload write is complete.
     Evaluate fragment readiness through the event machinery in section 9.

C3 and C4 may be encoded as adjacent edge effects if the consumer cannot issue
its read until the following edge. The initial implementation keeps the stages
explicit to make the data-before-done rule obvious and testable.

8.3 Validation predicate
------------------------

A first completion is eligible only if all of the following hold:

  live(owner)
  generation(owner) == packet.generation
  source index is legal for this typed input port
  required(owner, source)
  issued(owner, source)
  not claimed(owner, source)
  not committed(owner, source)

The last two tests overlap in normal operation but are useful invariants.
Committed implies previously claimed. Keeping both in a checker catches a
broken state transition. An implementation may compress a redundant bit only
after proving the complete transition system and retaining equivalent checks.

A genuine service failure with a valid owner is still a first completion. Its
status is nonzero and its declared fallback payload is committed. A stale,
duplicate, or unsolicited packet is not a second completion for that owner.
Do not confuse these two classes of error.

8.4 The duplicate window introduced by pipelining
------------------------------------------------

Suppose sample (owner 7, generation 12, index 1) arrives on cycles n and n+1.
If arrived is not set until the RAM write at n+3, two validators reading only
arrived can accept both. Registering tmu_ok without a claimed state therefore
reopens the very duplicate-overwrite bug the existing issued/arrived checks fix.

C2 claims the source before C3 writes it. The second return must observe that
claim through either current scoreboard state or an explicit recent-update
bypass. Because C1 registers a snapshot, the implementation needs forwarding
for claims made after that snapshot was read.

The required forwarding window equals the number of cycles from scoreboard
snapshot to claim publication, including any elastic holding stage. It is not
assumed to be one forever. A fixed-latency C1->C2 implementation uses a bounded
recent-claim register; a variable-latency validator needs a reservation entry
that remains live until the snapshot is no longer stale.

Forward by full owner handle and source index, not by slot alone. Treat two
same-edge candidates for the same source as one claim and one duplicate, with
an explicit deterministic winner. The baseline has only one TMU candidate per
clock; AUX has a different source bit. Fault injection should still exercise
the generalized collision rule.

8.5 Allocation, retirement, and snapshot races
---------------------------------------------

A C1 snapshot can also become stale because an owner is retired/reused. Forward
recent allocation/retirement events, or revalidate the narrow live/generation
at C2 through a separately timed control port. Do not permit a stale live bit
to authorize a write into a newly allocated generation.

Normal ownership already prevents an accepted required completion from racing
its owner's retirement: the owner cannot be final until that completion has
committed. The remaining dangerous cases are duplicates, malformed traffic,
and reset/epoch transitions. They still deserve explicit rejection rather than
an argument that a well-behaved producer would not send them.

C3 never reevaluates a broad live table to decide its write. C2's accepted claim
holds the owner's outstanding obligation until the commit is published. Reset
or global abort flushes C0-C3 valid bits before any new epoch is admitted.

8.6 Concurrent TMU and AUX completions
--------------------------------------

TMU and AUX have separate payload banks and may commit on the same clock. Their
scoreboard updates may name the same owner. Merge masks with OR; do not place
two nonblocking assignments to the same scalar in unrelated branches and hope
both increments survive.

For an owner with both events:

  committed_next = committed_old | tmu_commit_mask | aux_commit_mask
  status_next    = status_old | tmu_status | aux_status

Status may instead remain in per-source result words and be combined at COMBINE
admission, avoiding a multiwriter wide status table. V3 prefers that arrangement:
the scoreboard needs only masks; the result-bank read provides per-source status.

Diagnostics that count both invalid inputs on one edge use one explicit delta
of zero, one, or two. The repository has already fixed this class of lost-update
bug elsewhere. It must not be reintroduced in the new controller.

8.7 RAM write-port implementation
---------------------------------

Instantiate sample-bank writes under static generate indices. Each bank sees:

  wr_enable_q, wr_owner_q, wr_payload_q.

The bank's process is clock-only. wr_enable_q is true for that static bank only
when the preceding C2 packet was validated and selected it. There is one whole
row write, not independent RGB/alpha/status writes from different processes.

The same bank's read belongs only to COMBINE admission. No debug port may read
it asynchronously on the hot path. Debug inspection must use a scheduled read
while quiescent, a separately budgeted read replica, or a captured trace stream.

8.8 What this repair does and does not promise
---------------------------------------------

It removes an entire class of incoming-token -> owner-table -> predicate -> RAM
write-enable path. It preserves throughput by accepting a new return every
clock once the pipeline is filled, with a separate AUX lane. It adds latency
and a small number of pipeline registers.

It does not guarantee 115 MHz. The actual control read, forwarding comparisons,
registered bank decoder, physical fanout, and placement still need synthesis and
routing. If C1 or C2 remains slow, split the narrow control work further without
letting claims become invisible to subsequent packets.


9. READY-EVENT SCHEDULING AND EXACTLY-ONCE FRAGMENT READINESS
============================================================

9.1 No all-owner readiness scan
-------------------------------

A source commitment changes only one owner's readiness. Admission can create a
zero-work ready owner. Therefore readiness is driven by these events, not by a
64-entry combinational search every clock.

Evaluate only the owner handles carried by TMU publication, AUX publication,
and initial/bypass publication. For each affected owner:

  eligible = live
          && ((committed & required) == required)
          && !ready_claimed
          && !combine_issued.

The required mask is frozen. A depth-zero coordinate result does not silently
clear a required texture sample; it takes the defined zero/error path and
produces the appropriate terminal records.

9.2 Same-owner event coalescing
-------------------------------

TMU and AUX may publish the last missing pieces together. Coalesce their masks
before deciding eligibility, or evaluate after both writes have reached the
scoreboard. If both candidate events name the same owner, exactly one claims
the ready ticket. A fixed source priority is acceptable for choosing that one
ticket because it does not prioritize the fragment's eventual execution.

ready_claimed is set when the ticket is reserved, before a pipelined queue write
can be duplicated by another event. As with completion claims, a registered
scoreboard read requires recent-update forwarding or an equivalent hazard rule.

An error completion uses the same readiness path. There is no separate scan
that tries to rescue failed owners later.

9.3 Physical queues, not a hidden multiwrite FIFO
------------------------------------------------

Use three producer-owned ready FIFOs:

  READY_TMU      produced by the TMU publication path;
  READY_AUX      produced by the AUX publication path;
  READY_INITIAL  produced by validated zero-work/bypass admission.

Each stores a 14-bit owner handle and has one writer and one reader. Baseline
depth is 64 for each. This deliberately spends three small M10Ks to avoid a
multiwrite queue. Total occupied ready tickets across all three can never
exceed the 64 live owners, because every owner claims only one ticket.

Do not reduce every FIFO to 21 entries by dividing 64 by three. A legal workload
can make every ready owner originate from the same producer. Shallower queues
require upstream reservation/backpressure proofs and must not strand an owner
whose payload has already completed.

A round-robin arbiter among the three queue heads supplies COMBINE admission.
The arbiter selects only handles. Wide material and sample data are read after
the selection is registered.

9.4 COMBINE admission read reservation
--------------------------------------

Before popping a ready ticket, reserve a COMBINE input holding slot or execution
context. Then read MATERIAL, SAMPLE_RESULT_0/1/2, and AUX_RESULT at the same owner
address. Align the read token with all outputs, perform the declared source-map
selection in a fabric register, and present one stable COMBINE input packet.

Do not pop a ready ticket merely because COMBINE ready is high now if the memory
read will return several cycles later. The destination credit must cover that
latency. A two-entry input holding queue plus an explicit in-flight-read count
is an acceptable baseline.

The owner remains live throughout. COMBINE execution context release is local
and does not affect owner allocation or output ordering.

9.5 Why removing the FRAGROB ordering barrier helps
---------------------------------------------------

The existing FRAGROB waits for its admission-order head before supplying a
combiner that itself executes out of order, followed by another order-restoring
buffer. V3 allows a fully ready younger fragment to use otherwise idle COMBINE
capacity. The final ring still enforces raster/blend-visible order.

This does not make an old missing request harmless: it still blocks final
emission. It does let useful internal work continue until the 64-owner window
is exhausted, instead of inserting another unnecessary head-of-line stall
before COMBINE. The window size, not an unbounded queue, bounds that behavior.


10. RCP24 EXECUTION ARCHITECTURE AND EXACT MULTIPLIER REDUCTION
=============================================================

10.1 Preserve the reciprocal, replace its execution organization
----------------------------------------------------------------

The reference law is unchanged: normalize a 24-bit denominator, use the existing
RCP24 seed ROM, perform MW0, MX0, MW1, MX1, then perform the final rounded rescale
and 24-bit clamp. Preserve zero-input behavior and the exponent convention.
The inspected service sets k = leading_zero_count + 1 for nonzero input, hence
reachable nonzero k is 1..24. [R10]

Do not replace the two Newton steps with a different reciprocal table, float,
approximate divider, shortened iteration count, or a higher-quality reciprocal
that changes the integer outputs. Bit-exact equivalence includes truncation and
wraparound, not just an error bound.

10.2 Queues and execution contexts
----------------------------------

Use 16 RCP execution contexts initially. This is larger than the current eight
because the explicit product/recombination/commit pipeline has a longer feedback
latency. The capacity is still independent of the 64 fragment owners.

Use a free-context FIFO, a NEW queue, and a CONTINUATION queue. Admission and a
returning phase may both enqueue in one clock, so NEW and CONTINUATION have
separate single writers. A small fair arbiter selects a context/phase ticket.
There is no context-wide free scan, ready scan, or completion scan.

Each context has a read-only payload plane written at admission and a scratch
plane written only by phase writeback. The payload holds normalized m, seed x0,
owner handle, exponent, and zero flag. The scratch holds current x and w as two
32-bit values. Phase MW0 ignores old scratch and initializes the whole scratch
row through its ordinary writeback. Admission must not also initialize scratch.

A final phase writes the owner's RCP_RESULT and publishes a sample-owner ticket.
That global row and ticket are reserved by the live owner, so the final result
need not occupy another 16-entry completion table. Execution context release
occurs only when that final commit has been accepted. If an implementation keeps
a local output buffer for modularity, its credits and RAM blocks must be counted.

The context count must satisfy the actual feedback latency, not a comment saying
that three contexts ought to be enough. Measure product launches per cycle under
saturated independent work and check the four-jobs-per-nonzero-reciprocal law.

10.3 Normalization and seed pipeline
------------------------------------

Separate denominator capture, leading-zero count, normalization/index formation,
and ROM output capture as needed by the measured path. A balanced leading-zero
network is preferable to a long priority dependency, but its result must match
the current zero/nonzero convention exactly.

Reserve an execution context before admitting work into a nonstallable seed
pipeline. The ROM result is not allowed to appear without a payload write slot.
The seed table is the existing generated table; no hand-edited replacement is
part of this architecture.

10.4 Unconditional proof that w needs only 32 bits
--------------------------------------------------

In an MW phase:

  0 <= m <= 2^24 - 1
  0 <= x <= 2^32 - 1
  P = m*x < 2^56
  w = P >> 24 < 2^32.

Therefore c_w can be stored as an unsigned 32-bit value for every reachable MW
result. This proof does not depend on the quality of the seed, convergence of
Newton's method, or a simulation sample. It follows from the operand widths and
the defined shift. It remains true even for deliberately extreme x values.

The wrong next step would be to assume t = 2^31-w is always positive and simply
truncate the existing 64-bit t to 32 bits before multiplication. V3 does not do
that. The negative case is handled exactly below.

10.5 Exact replacement for the 32-by-64 MX multiplication
---------------------------------------------------------

The current arithmetic is:

  t64 = (2^31 - w) mod 2^64
  P64 = (x * t64) mod 2^64.

Let:

  b32 = (2^31 - w) mod 2^32
  neg = (w > 2^31).

Because w is unsigned 32-bit, the mathematical difference is in
[-(2^31-1), 2^31]. Its 64-bit modular representation is:

  t64 = b32                      when neg == 0;
  t64 = b32 + (2^64 - 2^32)      when neg == 1.

Multiplying by x and reducing modulo 2^64 gives the exact identity:

  P64 = (x*b32 - (neg ? x*2^32 : 0)) mod 2^64.

This replaces the wide operand multiplication with one full unsigned 32x32
product and a correction. The correction affects only the high 32 bits:

  low  = product32x32[31:0]
  high = product32x32[63:32] - (neg ? x : 0), modulo 2^32
  P64  = {high, low}.

There is no lower-half borrow because the subtracted term has 32 zero low bits.
The high-half subtract is its own registered 32-bit stage. The boundary w=2^31
is not negative and gives b32=0. The boundary w=0 gives b32=2^31 and remains
representable as unsigned 32-bit; do not accidentally cast it to signed 32-bit.

This proof preserves the uint64 wrap law for every 32-bit x and every possible
32-bit w. It is stronger than a claim that the actual ROM probably keeps w in
a friendly range.

10.6 Exact 32-bit Newton rescale without a 64-bit add
----------------------------------------------------

The reference then computes:

  x_next = uint32(((P64 + 2^29) mod 2^64) >> 30).

Only bits 61..30 and the rounding carry from bit 29 survive the final uint32
conversion. Therefore:

  x_next = P64[61:30] + zero_extend(P64[29]), modulo 2^32.

Bits below 29 cannot create an additional carry when adding exactly 2^29.
Bits 62 and 63 are discarded by the defined uint32 result. Carry out of bit 63
is also discarded by the original modular 64-bit addition. The 32-bit formula
therefore retains every observable bit, including wraparound at x_next.

For MW, w is simply P[55:24] under its proven width bound. The final reciprocal
rescale remains (zero_extend(x)+64)>>7 followed by the existing 24-bit clamp;
use sufficient width for x+64, rather than accidentally wrapping at 32 bits.

10.7 The shared product unit
-----------------------------

A simple exact implementation decomposes each unsigned 32-bit operand into two
16-bit halves:

  a = a0 + 2^16*a1
  b = b0 + 2^16*b1

  p00 = a0*b0
  p01 = a0*b1
  p10 = a1*b0
  p11 = a1*b1.

All four 16x16 products are launched in parallel. Recombine with explicit carry:

  cross   = p01 + p10                         // 33 bits
  low_sum = p00 + ((cross & 0xffff) << 16)    // 33 bits
  high    = p11 + (cross >> 16) + carry(low_sum)
  product = {high[31:0], low_sum[31:0]}.

Register partial products, cross sum, low/carry, high, correction, and rescale
at separate boundaries as required. Keep the owner/context/phase/negative tags
aligned through every stage.

Cyclone V has independent small-multiplier modes within a variable-precision
DSP block. Four 16x16 products are a candidate for packing into two physical
DSP blocks using the two-18-bit-multiplier mode. That is a mapping target, not
a promise that an arbitrary inferred expression will pack that way. Register,
clock-enable, signedness, and mode compatibility must be checked in the exact
Quartus 17 microbenchmark. [V06]

The architecture budget allows a measured alternative using more DSP blocks up
to the global 14-DSP redline. It does not allow serializing these four partial
products over four clocks: that would reduce the one-micro-job-per-clock rate
and therefore the reciprocal throughput.

10.8 Suggested execution stages
--------------------------------

  Q  choose a NEW or CONT ticket; reserve its downstream pipeline position
  R  synchronous payload/scratch read
  O  choose a/b, compute t_low and negative flag, register operands
  M  four parallel 16x16 partial products
  X  cross sum
  L  low sum and carry
  H  high sum
  C  high-half negative correction, bypass for MW
  E  exact MW extraction or MX rounded 32-bit rescale
  W  one scratch write or accepted final-result transfer; publish continuation

For a terminal MX1, register x_next before the final (x_next+64)>>7 and clamp.
Use a separate terminal rescale register stage when necessary; do not combine
two rounded adds and a clamp into E while claiming the diagram removed that
cone. All terminal outcomes, including the zero-product phase, pass through
the same credited final commit stream. Their extra terminal latency does not
extend the nonfinal scratch-feedback loop.

An implementation may combine cheap adjacent stages only after timing evidence.
If a stage is added, revisit execution-context occupancy and every nonstallable
pipeline reservation. With approximately ten clocks around the feedback loop,
16 contexts are a defensible starting point, not a measured optimum.

Zero-input handling uses one zero-product scheduled phase through the same
final pipeline as ordinary phases, preserving its result, exponent, and
depth_zero flag. It does not create an independent unqueued bypass writer that
can collide with a normal RCP final write. Its product counter explicitly
counts zero jobs, while a separate scheduled-phase counter includes this phase,
rather than pretending four products occurred. The reference
comparison checks values and flags; the new service counter contract checks the
new intentional work count.

10.9 What was checked in this review
-------------------------------------

The full modular MX expression and the corrected 32x32 expression matched for
250,256 boundary/random (x,w) pairs, including 124,679 negative-correction cases.
The 24x32 MW width/product identity was checked on 250,000 random pairs. These
are independent Python integer checks in addition to the algebra above.
They do not establish a Verilog implementation's signed-cast correctness or DSP
mapping. The future paired RTL test must still compare the actual old and new
modules under stalls, repeated context reuse, zero inputs, and all denominators.

An exhaustive sweep of all 2^24 denominator values is practical as a repository
regression once the implementation exists. This review did not run that sweep
against the compiled repository reference or the new RTL.


11. PERSPUV: ONE PAIRED STREAM, NOT TWO INDEPENDENTLY SCHEDULED TABLES
==================================================================

11.1 The problem is not too many arithmetic lanes
-------------------------------------------------

The production throughput ruling requires a complete U/V pair to start every
clock. Three-sample materials make one shared product lane insufficient for the
stated sample workload. Keep two axes in parallel. [R08, R09]

The waste is the independent U queue, V queue, duplicated mantissa reads,
per-axis result stores, per-token have mask, and later join when both axes were
available together from the beginning. Both axes have the same reciprocal,
exponent, owner, sample index, and lifecycle.

Replace that arrangement with one paired input packet and a valid/tag pipeline.
Both products advance together. The result is inherently a pair, not two events
that need another token table to rediscover their relationship.

11.2 Input and output packets
------------------------------

Input:

  sample_handle16
  numerator_u signed32
  numerator_v signed32
  reciprocal_mantissa24
  exponent6
  depth_zero1
  binding_id8
  LOD_Q4_4_8
  status budget / configuration epoch as required by the interface

Output:

  sample_handle16
  u signed32, v signed32
  binding_id8, LOD_Q4_4_8
  saturation and depth_zero flags
  propagated status.

Do not build a new 64-entry payload FIFO containing this entire record at every
stage. The descriptors remain in the transaction file; a bounded input register
and arithmetic pipeline hold only active work. At the output, reserve capacity
in the planner-input queue before launching a nonstallable arithmetic packet.

11.3 Exact arithmetic
----------------------

For each axis, preserve:

  product = signed(numerator32) * unsigned(mantissa24)
  shift   = 32 - exponent
  sum     = product + 2^(shift-1)
  scaled  = arithmetic_shift_right(sum, shift)
  output  = clamp_to_signed_32(scaled).

This is the repository's round-half-up convention, including negative values.
Do not replace it with round-to-nearest-even, symmetric rounding away from zero,
or a floating-point operation. Depth zero explicitly returns zero coordinates
and the same flags as the reference, without reading old result storage.

For the reachable nonzero RCP exponent 1..24, shift is 8..31. The signed 32x24
product fits in 56 signed bits. Even after the largest applicable positive
rounding bias, the valid-domain result remains within the 56-bit signed range.
That makes a 56-bit stored product/sum a possible exact narrowing. The first
migration can retain signed64 to isolate scheduling from width changes; the
56-bit version needs an explicit bound and differential test.

Do not apply that valid-domain narrowing to an arbitrary standalone leaf input
exponent without checking its contract. Keep the old general-purpose leaf as
an oracle if its interface admits values outside the composed RCP domain.

11.4 Split the barrel shift, do not change the function
------------------------------------------------------

For a signed value s and nonnegative shift k:

  (s >>> (k & 7)) >>> (8 * (k >> 3)) == s >>> k.

Use a fine shift of 0..7 in one stage and a coarse shift of 0,8,16,... in another,
with arithmetic sign extension at both stages. This turns one wide variable
shift cone into two bounded mux networks. The order can be reversed if the
same signed-width law is preserved.

The shift amount is captured with the product, not reread from a context table.
Bias generation can be prepared in a parallel exponent-decode stage before the
product returns. The rounding addition, variable shift, and final saturation
must not be folded back into one large expression between registers.

Saturation is a sign-extension test or equivalent signed comparison followed
by the exact min/max selection. Compare the full scaled width; testing only
the final 32 bits misses overflow.

11.5 Exact product implementation and DSP packing
--------------------------------------------------

One option is a native explicitly sized signed32-by-unsigned24 expression,
with registered operands and results. A second is a controlled partial-product
implementation. For the latter, take an unsigned 32-bit magnitude, including
0x80000000 for the magnitude of INT32_MIN, multiply it by the unsigned 24-bit
mantissa using 16-bit partial products, then apply the sign in a separately
registered sufficiently wide result.

Two independent axes require eight such small partial products if four are
used per axis. Four Cyclone V DSP blocks in the two-18-bit-multiplier mode are
a plausible packing target. The actual mapping may instead use more blocks;
the accepted implementation is whichever preserves II=1, exact values, and the
global area/DSP budget after measurement. [V06]

Do not share the U and V multiplier over alternating clocks to hit the DSP
number. That resurrects the throughput deficit already identified by the
repository. Do not assume that writing one multiplication operator means one
physical DSP block.

11.6 Suggested stages and credits
----------------------------------

  P0 paired packet captured with output capacity reserved
  P1 operand sizing/sign preparation or native DSP input registers
  P2 product partials/native products
  P3 partial recombination, if used
  P4 exact product assembled and rounding bias aligned
  P5 rounding addition
  P6 fine arithmetic shift
  P7 coarse arithmetic shift
  P8 saturation and paired output formation
  P9 enqueue reserved planner-input result

This is a timing partition, not a requirement to add nine stages to a path that
already meets timing in fewer. The invariant is one pair per clock at saturation
and no combinational backward-ready chain through all arithmetic stages.

A nonstallable implementation reserves an output slot at P0 and releases the
reservation when the output is consumed. Its output capacity must cover every
in-flight launched pair plus queued pairs. A nominal four-entry FIFO cannot
safely absorb a nine-stage pipe merely because the consumer is usually ready.

An elastic implementation is also valid, but ready must be broken into local
segments with skid capacity. The current bilerp source illustrates why a comment
saying ready is local is not enough: a chain of !valid || downstream_ready
assignments is still a combinational path when every stage is full. [R07]

11.7 Evidence required
-----------------------

Compare the new paired stream with the existing arithmetic oracle for every
output bit and flag. Test signed extremes, all reachable exponents, all-zero
and maximum mantissas, rounding boundaries, overflow boundaries, mixed zero and
nonzero requests, output stalls, and slot reuse in any compatibility wrapper.

This review's 250,576 perspective tests checked product reconstruction and split
arithmetic shifts with boundary/random inputs, including INT32_MIN. They did not
run a new RTL pipeline. That distinction must remain visible in the implementation
report.


12. BINDING RESOLUTION AND THE TMU PLANNER
========================================

12.1 One authoritative binding descriptor
-----------------------------------------

A binding ID must select the base address, sanitized format/filter mode,
dimensions, wrap modes, mip cap, palette identity, and configuration epoch that
actually determine the requested sample. Carrying an ID while the planner reads
unrelated global pins is prohibited.

Use a synchronous binding table with a baseline 256 logical IDs, preserving the
existing eight-bit binding namespace. A 128-bit per-binding budget occupies
four width slices at 256 rows in simple-dual-port organization. Define the
packed fields in the generated ABI and assert that reserved bits are zero.

The descriptor contains immutable per-binding invariants: base, format,
effective filter policy, wrap modes, base dimensions, maximum valid mip level,
palette slot/generation, version/configuration identity, and any defined material
source flags. Sanitization is performed at configuration acceptance or a clearly
registered resolver stage, not independently in three downstream consumers.

12.2 Configuration lifetime: a real policy with a real cost
-----------------------------------------------------------

The baseline recovery profile selects a simple safe rule: binding and envelope
configuration changes are committed only while the relevant island configuration
epoch is drained. Ordinary fragments from many preloaded bindings can interleave
freely without draining. Only mutation of the referenced configuration requires
a barrier.

This avoids adding a three-read/three-update per-binding reference-count table
at admission. It also avoids pretending that a version byte makes overwritten
payload reappear for an old owner. The command processor must backpressure or
queue configuration writes until the barrier is satisfied.

Measure the cost of these barriers on actual draw/material traces. If it exceeds
the frame budget, use an explicitly budgeted double-buffered or copy-on-write
binding store with epoch reference counts. That is an additional implementation
choice, not a silent change to the base four-M10K inventory. A double-buffered
full table may add roughly another four width-sliced blocks, depending on its
exact geometry; the fitter decides the actual count.

The existing palette BEGIN/WRITE/END protocol has its own defined concurrent
lookup behavior. Do not silently replace that behavior with the binding barrier
rule or with snapshot-preserving double buffering. Palette policy is handled
separately in section 15.

12.3 Do not build a giant all-binding/all-mip table by accident
-------------------------------------------------------------

Precomputing every invariant is useful; multiplying storage by 256 bindings and
16 mip levels can consume a substantial part of the M10K budget. V3 therefore
precomputes binding invariants and retains a registered exact selected-level
calculation in the planner. The small REP4 law and dimension shifts are not
replaced by a many-thousand-entry wide table merely to remove a few operators.

A hot descriptor cache can be added later only with a measured miss/conflict
rate and a throughput proof. A direct-mapped cache that thrashes on the real
three-material workload is not a free area optimization. The baseline planner
must remain able to start one sample each clock without a descriptor-cache miss
path becoming the hidden maximum term.

12.4 Preserve the current address law
-------------------------------------

Retain the repository's format encodings:

  0 CLUT8
  1 RGB565
  2 CLUT4
  3 ARGB1555
  4 ARGB4444.

Retain Q4.4 LOD at the interface. The current planner selects the integer mip
level from the high nibble; it does not implement trilinear interpolation.
Do not narrow the port to four bits or claim the discarded fractional nibble
is a new filtered-LOD capability.

Preserve repeat, clamp, and mirror behavior for negative coordinates, the
half-texel bias for filtered requests, rectangular mip-chain offsets, level
clamping, supported maximum dimensions, and exact byte addressing. The current
planner already has width-aware wrap logic and a registered pipeline; reuse its
verified law rather than deriving a plausible different one. [R13]

12.5 Resolve class once
----------------------

Class is a function of the sanitized format and effective filter mode:

  CLUT4/CLUT8                          -> PALETTE
  supported direct colour, filter off -> NEAREST
  supported direct colour, filter on  -> BILINEAR
  unsupported/unroutable descriptor   -> TERMINAL ERROR.

The current law suppresses filtering for paletted formats and reports the
invalid mode combination. Preserve the scalar contract's exact error/fallback
behavior rather than inventing filtered CLUT support during a timing repair.

Remove frag_class as an independent production input. A compatibility wrapper
may accept it only to check disagreement; it must not override the resolved
class. Derivation occurs before issuing the request, is recorded in metadata,
and is consumed at response preparation.

12.6 Resolved sample metadata
-----------------------------

Use the 40-bit baseline word:

  format3
  effective_filter1
  fu8
  fv8
  byte_select1
  nibble_select1
  palette_slot2
  palette_generation8
  plan_status8
  -------------------
  total40.

The owner/sample handle is the address, not another payload field. The global
owner generation is validated before using a returned packet to read reused
metadata. If a future cache may return before metadata is committed, add an
explicit dependency/forwarding rule; do not rely on today's incidental latency.

The metadata word is written exactly when the planned sample request commits
to the cache-facing interface. It is read once during response preparation.
Downstream class units do not reread owner tables or ingress pins.

12.7 CLUT4 position must be captured before the divide
-----------------------------------------------------

Let T be the final logical texel offset, including the exact mip offset and
wrapped row/column law. For CLUT4:

  byte_address = base + floor(T/2)
  nibble_select = T & 1.

If the cache returns the addressed aligned halfword, byte_select is the low bit
of the resulting byte address. Do not derive it merely from T bit 1 when base
alignment is not guaranteed by the binding contract. The nibble bit is not
recoverable from byte_address alone.

Decode:

  selected_byte = byte_select ? halfword[15:8] : halfword[7:0]
  index = nibble_select ? selected_byte[7:4] : selected_byte[3:0].

For CLUT8, index is the selected byte. For direct 16-bit formats, the cache
contract must state whether its returned halfword has already been selected;
do not apply a second unrelated byte selector to a normalized halfword result.

The test must cover all four nibble positions in a returned halfword, odd/even
texture coordinates, mip transitions, wrapping, and nonzero base offsets.
This review exhaustively checked the four-position extraction identity over
all 65,536 possible halfwords; that does not replace address-oracle testing.


13. THE CACHE: RETAIN THE REPAIRED BANKED CORE AND ITS RESERVATIONS
=================================================================

13.1 Do not discard the working repair
--------------------------------------

The inspected cache already has static lane RAM ports, a synchronous memory
read followed by a fabric capture, and a reservation counter accounting for
results still in the probe pipeline. These are the right structural ideas.
They are not the reason to restart the cache from an older implementation.
The prior loss of two warm-hit responses under a stalled output is documented
at the exact reservation logic in the source. [R11]

Keep the four static lane data banks and four static lane tag banks initially.
Keep the existing miss/replay law and single fill transaction, including its
address/beat sequencing. The production adaptation changes the echoed token
meaning to the canonical 16-bit sample handle; it does not change the tag or
texture-address law by accident.

This is not a claim that a four-lane replicated cache is the best possible
cache. It is the smallest-risk way to retain an already repaired banked core
while replacing the surrounding ownership machinery that currently obscures
its behavior. A different cache organization needs its own workload and
physical evidence, not inclusion in this recovery merely because it is new.

13.2 Reservation is acquired at probe issue
------------------------------------------

Let R be the capacity of the response queue. Maintain:

  queued_responses + noncancelled_probes_owing_results <= R.

Acquire one reservation before launching a probe into the nonstallable memory
read/capture pipeline. A hit transferring its result into the response queue
keeps the reservation. The consumer handshake releases it. A miss that squashes
probes refunds exactly those noncancelled probes that will be replayed later.

The current code counts the missing C2 probe and the following C1 probe in its
squash refund, and prevents a new issue on the miss edge. Preserve or rederive
that edge-level law if another pipeline stage is inserted. Copying the old
numeric refund after adding C0b or C2b would leak or over-return credits. [R11]

The conservation test must cover issue+pop, hit+pop, miss+squash+pop, and replay
with output backpressure. A response FIFO occupancy check alone is insufficient
because it does not include the results that will arrive next cycle.

13.3 Read-data identity and fill validity
----------------------------------------

Tag, data, valid, enabled-lane mask, and sample handle must describe the same
probe. Capture validity alongside the corresponding RAM read; do not observe
the old tag and the next cycle's new valid bit during a fill.

A line becomes valid only at the defined final fill beat. Until then, no probe
may interpret its partially written payload as a completed line. If a fill
writes several lanes through multicast, each written lane gets the same
explicit final-beat validity rule.

Disabled lanes are not validated texture taps. The response preparer must know
the effective footprint shape. A nearest request may carry arbitrary unused
halfwords in the physical response bus; they must never become inputs to a
bilinear operation merely because another field says class BILINEAR. V3 removes
that contradictory class authority at planning, rather than attempting to
sanitize arbitrary stale halfwords after the cache.

13.4 Keep the external fill contract honest
-------------------------------------------

The present island exposes a fill request and a halfword data stream without a
new transaction ID on every beat. The baseline preserves one outstanding fill
and its ordered eight-halfword line transfer. Do not add multiple outstanding
fills behind this interface without extending or proving its response identity.

The fill response is not automatically pausable. If its transport can emit a
beat without ready, space and bank access must have been reserved before the
request. A registered input stage is useful only if the next stage can always
consume or safely queue the delayed beat.

Reset or configuration drain waits for the complete fill transaction or obtains
a transport abort acknowledgement. Dropping local busy while an old stream is
still producing beats risks installing an old line under a new fill address.

13.5 Capacity and timing goals for the retained cache
-----------------------------------------------------

Demand one warm-hit sample request per clock at saturation, subject to the
explicit output reservation. Measure cold-line and mixed-footprint behavior
separately; a global fill stall is not hidden by quoting the warm-hit II.

The initial RAM inventory assigns eight M10Ks to the lane data/tag stores.
This is a proposed physical allocation based on the lane organization, not an
independently measured instance breakdown from the latest composed fit.
If Quartus merges compatible stores or uses additional blocks, publish that
actual mapping and update the allocation before claiming a closed budget.

Do not put a broad owner-generation check before the RAM address register.
Capture the request locally, and keep identity validation in the dedicated
completion/preparation stages. No cache tag comparison should feed an unbounded
island-wide ready chain.


14. RESPONSE PREPARATION AND CLASS DISPATCH
===========================================

14.1 Read metadata once, before class execution
------------------------------------------------

The old top performs separate asynchronous metadata reads for nearest,
bilinear, and palette paths. The dispatcher also copies wide raw response
payload through both a raw queue and per-class queues. [R04, R12]

V3 uses the following sequence:

  RP0: accept the cache response into credited raw holding storage;
  RP1: validate its owner/sample range and request ownership;
  RP2: launch one synchronous SAMPLE_METADATA read;
  RP3: capture metadata with the matching response data and handle;
  RP4: commit one prepared-response row and a narrow class ticket.

Do not index the metadata bank with an illegal sample_index=3 and then rely on
a later error flag. Range validation and a safe physical address are separate
defenses. A stale generation is rejected before consuming reused metadata.

Metadata is immutable while that sample is outstanding. Therefore it needs one
read port shared by response preparation, not separate read ports for every
consumer. The read request pipeline is itself credited: accepted raw packets,
metadata reads in flight, and prepared rows awaiting class dispatch all have
bounded destinations.

14.2 Shared prepared-response payload pool
------------------------------------------

Baseline pool:

  16 rows x 120 bits = raw_halfwords64 + metadata40 + sample_handle16.

This is three 40-bit width slices, budgeted as three M10Ks. There is one write
stream from RP4 and one read stream from the class-head scheduler. The scheduler
chooses only a four-bit pool index before registering the RAM read address.

Four class queues hold pool indices: PALETTE, NEAREST, BILINEAR, ERROR. Give each
capacity for all 16 indices, because all pool entries can belong to one class.
The sum of occupied class tickets plus pool-read leases never exceeds 16; the
four queues do not imply 64 independently allocatable payload rows.

These tiny index queues may remain explicit flop FIFOs. Their bits and pointer
logic are included in the register budget. Do not force four poorly utilized
M10Ks merely to make every declaration say RAM. Conversely, do not duplicate
120-bit rows into each queue because it makes a local interface convenient.

The free-pool FIFO is similarly narrow. A row is released only after the selected
consumer has received a stable local copy or another credited destination has
accepted it. It is NOT released merely when the read address is launched: a
new prepared response might otherwise overwrite the row before its data is
captured.

14.3 Class fairness requires destinations that can wait
-------------------------------------------------------

A round-robin scheduler among nonempty class heads may issue a pool read only
when the chosen class has reserved input holding capacity. The destination can
be one or two registered packet slots per class. Its reservation includes the
RAM read latency, so a temporarily high ready signal is not enough.

A busy bilerp sequencer does not prevent a ready nearest or palette class from
using the read port. It does prevent another bilerp packet from overwriting the
one whose four channels are still being issued. Multiple registered stages may
separate arbitration from execution; their valid bits travel with the pool
index and handle.

A shared pool still has finite-resource head-of-line effects: if a class retains
all 16 rows, no new raw response can acquire a row. The design promises bounded
storage and fair service, not perfect isolation under arbitrary infinite stalls.
Counters must distinguish this pool exhaustion from a cache miss or unavailable
COMBINE context.

14.4 Palette and completion credits
-----------------------------------

The existing palette result is a one-cycle pulse with no return-ready input.
The current top prioritizes it and depends on FRAGROB being unconditionally
ready. Changing FRAGROB ready without first changing this seam loses palette
answers. The source explicitly documents that cross-module dependency. [R04]

V3 reserves a palette-result holding entry before issuing a lookup. Let H be
the local return capacity:

  held_palette_results + lookups_in_flight <= H.

The pulse transfers its reservation into the holding queue. Only the accepted
completion-merge pop releases that reservation. Thus the palette result may
wait, the merge can become round-robin, and FRAGROB's old always-ready promise
is no longer a hidden correctness requirement.

Apply the same accounting to any newly nonstallable service. A register placed
on valid without corresponding payload storage and reservation is not a queue.

14.5 Reject stale/duplicate work at the correct boundary
--------------------------------------------------------

The terminal C2 claim in section 8 is the authority that prevents two results
from committing for the same issued sample. Earlier response preparation can
also reject already invalid handles and obvious duplicates to avoid wasted
work. It must not clear issued at that early point while a legitimate decoded
result is still in flight; that would make the later terminal claim reject its
own answer.

For the baseline internally trusted cache, a sample has one cache return and
terminal claim is sufficient for correctness. If duplicate raw returns are an
explicit transport fault model, either maintain an additional narrow
raw_response_claim bit or allow duplicate decode work to be discarded at C2.
The latter does not corrupt state but must remain bounded under the stated
fault assumptions. Do not claim progress against an infinite stream of injected
invalid packets without a separate fault-throttling mechanism.

14.6 Status is information, not a colour convention
---------------------------------------------------

A service can return a well-identified terminal failure. Preserve its handle and
an explicit status flag through the same response and completion machinery.
Magenta or black may be the compatibility pixel payload, but a downstream
material operation can change that colour. Therefore colour cannot serve as
the only evidence that the sample failed.

Binding/planner validation can fail before there is any cache return. Give that
producer a separate credited terminal-error holding path to the completion
merger. It does not write the prepared-response pool, whose only writer remains
RP4, and it does not read metadata that was never committed for a cache request.
Backpressure the validation stage when its error holding slot is occupied;
reserve enough slots for any already nonstallable validation stages.

Likewise, an invalid AUX envelope joins the AUX terminal merger with a reserved
wrapper obligation, rather than becoming a second unarbitrated AUX_RESULT writer.
The existing leaf credit is retained, and a wrapper credit covers work from
envelope-read launch through terminal transfer, including requests that never
enter the arithmetic leaf. Those are related but distinct lease intervals.

Invalid or stale identity is different: it is not a newly owed terminal result
for the current occupant. Reject and count it; do not manufacture a second
completion that changes current-owner masks.


15. PALETTE, NEAREST DECODE, CLUT4, AND FILTERED ALPHA
====================================================

15.1 Preserve the actual palette load protocol
----------------------------------------------

The inspected palette owns four resident slots of 256 RGB565 entries. It has an
explicit BEGIN/WRITE/END protocol, generation checking, distinct-entry coverage,
and CRC verdict handling. BEGIN makes the slot nonresident and advances its
generation. The existing comments that suggest old contents remain usable are
not a reason to change the observed protocol during a timing repair. [R14]

The V3 baseline preserves those visibility rules. This is deliberately NOT an
unannounced switch to an old-palette-remains-visible double-buffer protocol.
Such a protocol could be useful, but it changes what a lookup during reload is
allowed to return and needs its own reference and versioned contract.

The physical palette remains a single-write/single-read 1,024x16 memory, expected
to occupy two M10Ks. The 256-bit load coverage bitmap remains narrow control.
A count of 256 writes is not equivalent to 256 distinct entries: duplicates
must not disguise a missing index.

15.2 Register the control boundary without changing acceptance order
--------------------------------------------------------------------

The latest reported worst virtual-pin path involves palette load generation.
Register or queue the load command before generation checking and write control.
Then preserve the ordering of accepted load commands and accepted lookups.
A lookup concurrent with an accepted BEGIN must observe the same invalidation
rule as the chosen compatibility contract, even when a queue delays execution.

There are two safe baseline integration profiles:

  QUIESCENT CONFIGURATION: palette updates occur only after the relevant texture
  work is drained, so no data-plane lookup races a queued command.

  LIVE X6 COMPATIBILITY: the command/lookup arbiter serializes their accepted
  order and forwards a same-edge BEGIN invalidation to the lookup verdict.
  Lookup metadata and memory data remain aligned through the added stages.

V3's production loader starts with the first profile; its compatibility tests
retain the second protocol's defined corner cases. Do not claim that a delayed
BEGIN still invalidates at the original pin edge without implementing that
logical ordering.

The present leaf's ld_ready is always high, so the current top discarding it
is not by itself evidence of dropped load commands. If V3 adds a bounded command
queue that can deassert ready, expose and honor that ready in every caller.
This is a required interface adaptation, not a retroactive diagnosis. [R14]

15.3 Palette identity and generation wrap
-----------------------------------------

Palette slot/generation come from the resolved binding metadata, never from
bits borrowed out of the owner generation. A stale or cold lookup produces a
retirable sample failure with a status flag and defined compatibility payload.
The palette's raw memory bits are unusable when its verdict says nonresident.

Eight palette-generation bits also wrap. The configuration manager must not
reuse a slot/generation pair while an older binding can still name it. The
baseline drained configuration epoch provides that safety; a live-reload profile
needs reference tracking or an equivalent epoch barrier. A wider counter alone
is not a proof against an unboundedly retained stale binding.

15.4 One direct-colour decode law
---------------------------------

Retain the repaired shared decode for RGB565, ARGB1555, and ARGB4444. Use the
repository's exact bit replication rather than zero-fill. Nearest decoding and
bilinear tap decoding call the same generated or mechanically shared law.
An unsupported code must not alias a legal format by narrowing three bits to
two. The format field stays three bits. [R04, R13, R15]

For CLUT4, use the byte and nibble selectors captured before address conversion.
For CLUT8, use the addressed byte. The palette entry is RGB565 and therefore
opaque under the inspected contract. Do not invent index-zero transparency.
A later transparency-key feature must explicitly capture its rule and apply it
to the raw index before the palette replaces that index with a colour.

15.5 Retain the exact bilinear arithmetic
-----------------------------------------

The inspected channel lane implements, with signed intermediates:

  a = (t00 << 8) + (t10 - t00)*fu
  b = (t01 << 8) + (t11 - t01)*fu
  result = ((a << 8) + (b - a)*fv + 32768) >>> 16,

followed by the reference's eight-bit result conversion. The intermediate
u-direction values are not rounded to eight bits. There is one final rounding.
Changing to two ordinary rounded lerps would change pixel values. [R07]

Keep one channel pipeline with initiation interval one channel job per clock.
The current implementation has two u-direction product sites and one
v-direction site. It is NOT one multiplier merely because its interface is
one channel wide. Any future single-product time-sharing design changes the
resource/service equation and needs a separate throughput proof.

Each filtered RGBA sample emits four channel jobs: R, G, B, A. Thus a single
channel-per-clock pipeline has a best sustained rate of one full sample per
four clocks, not one RGBA sample per clock. Its job counter must show four
accepted jobs per filtered sample, including RGB565's constant opaque alpha
in the initial bit-identical schedule.

An explicit opaque-alpha bypass may later save one job for formats whose
reference alpha is constant. It must carry a format-proven constant, change the
job-count contract visibly, and preserve admission/collection ordering. It is
not included in the baseline numbers.

15.6 Channel collection and backpressure
----------------------------------------

The baseline sequencer issues all four channels of one sample contiguously.
Its local packet remains held until the fourth job is accepted. The collector
checks both expected channel and sample handle; R/G/B from one sample must
never be paired with A from another.

A completed RGBA result requires a reserved completion holding slot. The final
channel cannot be accepted merely because the intermediate colour registers
exist. Stalling the alpha channel must also preserve the collected RGB values
and prevent a later sample from overwriting them.

If the channel lane is ever changed to interleave samples or return them out of
order, replace the single collector with explicitly budgeted per-sample state.
Do not keep a single RGB accumulator under an undocumented order assumption.

15.7 Error and refusal compatibility
-------------------------------------

The old island turns some sample failures into a magenta sample and then allows
COMBINE to process that sample. COMBINE's output_refused concerns its own recipe
or missing-input validation; it is not a complete aggregate of sample-service
errors. Preserve this legacy signal meaning in the compatibility wrapper.

The production output additionally carries STATUS8. Define an aggregate error
indicator from its specified error bits, rather than silently broadening the
old refused bit. Exact legacy pixels can be preserved while richer status makes
previously invisible failures observable. Appendix B defines the baseline
status allocation and which conditions are informational rather than errors.


16. AUX, OPAQUE CONTEXT, AND MOSAIC INTEGRATION
==============================================

16.1 Geometry has its own record
---------------------------------

The present composition passes fr_aux_ctx[31:0] and [63:32] as world X/Z and
hardcodes a unit-square envelope. That is a restricted composition, not a
valid reason to reinterpret all opaque caller context as geometry. [R04]

V3 reads AUX_GEOMETRY for world X/Z, envelope selector, and configuration epoch.
The full caller context stays untouched until final retirement. A directed test
must vary context while holding geometry constant, then vary geometry while
holding context constant. Both halves are necessary to detect an accidental
alias between the fields.

The envelope store has a 160-bit allocation per entry: four 32-bit endpoints
plus 32 bits for version, validity, and reserved control. The baseline capacity
is 16 entries. This costs four 40-bit width slices in the budget, despite being
shallow. The captured eight-bit selector must be range-checked against 16;
upper bits are not silently truncated to pick an unrelated envelope.

Envelopes are immutable during the baseline configuration epoch. The decoder
checks the captured epoch before issuing geometry work. Invalid envelope
identity yields a defined terminal failure or the exact accepted degenerate
fallback; the compatibility contract determines which, not uninitialized RAM.

16.2 Keep the repaired AUX credit law
-------------------------------------

The inspected AUX pipeline was repaired to hold sheet offers and to bound its
entire lifetime with 16 credits. A credit is taken at admission and released
only when the terminal AUX result is accepted. It is not released when a sheet
request is issued. Its fixed-latency divider does not imply infinite downstream
storage. Retain this repair. [R16]

The six restoring quotient stages remain the arithmetic of record. Preserve
negative-coordinate clamping, upper saturation, and degenerate-envelope
handling. A degenerate request emits no sheet read but still produces exactly
one terminal owner-associated result.

AUX_PENDING is an independent 64-entry handle queue. Before its geometry and
envelope reads launch, reserve local AUX input credit. The returned descriptor
packet cannot be discarded because the divider became busy while memory was
being read.

16.3 External sheet response is a reserved obligation
-----------------------------------------------------

The sheet return interface lacks a ready signal. The request therefore reserves
a destination for its eventual return before being accepted by the sheet.
The present repair also gives the unstallable sheet result priority over a
locally held degenerate when they contend for a return write. Keep an equivalent
single-writer schedule; do not create two writes into one inferred FIFO. [R16]

AUX may complete out of order relative to submission because a younger
degenerate can finish before an older sheet access returns. This is safe with
canonical owner handles. It must not be described as submission-order return.
The final island output, not AUX itself, restores externally required order.

When adapting TOKW, carry all 14 owner bits end to end through the divider,
side metadata, sheet request, sheet response, return queue, and completion
validator. Widening only the AUX top port leaves an aliasing defect inside.

16.4 AUX colour source and sample accounting
---------------------------------------------

The existing composition turns sheet tag/strength into {tag8,strength8,0} RGB,
with alpha zero for the degenerate outcome and 255 otherwise. Preserve that
restricted mapping in the compatibility wrapper unless the material reference
explicitly specifies a different AUX-to-colour law. [R04]

The production source map says whether AUX replaces logical sample two. The
sample-result read stage chooses it there; it does not overwrite the texture
sample bank, create a second writer to that bank, or pass an unrelated earlier
fragment's auxiliary colour.

Source masks must remain consistent with request counters. The baseline can
preserve the old physical sample-two overfetch while adding source-map tests.
Removing it is a separate accepted optimization with an updated request oracle.

16.5 Mosaic must influence the selected descriptor
--------------------------------------------------

A Mosaic counter moving is not proof that Mosaic affected a texture request.
The production composition must route the selected tile/binding into the actual
binding descriptor consumed by the planner. The test should compare two legal
Mosaic selections that point at textures with provably different texel results.

Preserve the frozen modulo-2^32 hash, tie behavior, and selection law. If the
existing constant multiplications map expensively, use an exact shift/add or
signed-digit decomposition, with registers between add levels. Subtraction and
left shifts must use the same 32-bit modular semantics as the reference.
Do not replace the hash with another apparently random hash or narrow a seed.
The earlier architecture explicitly identifies this as an exact implementation
change rather than a change of visible behavior. [R08]

The proposed DSP allocation for Mosaic is zero. That is a target contingent on
synthesizing the exact constant arithmetic, not a claim that this review fitted
such a replacement. Keep a differential hash/selection test and fit the small
lane separately before its count is used in the island budget.


17. COMBINE V2: PRESERVE THE ARITHMETIC ORGANIZATION THAT WORKED
===============================================================

17.1 This is the retained material engine
-----------------------------------------

The latest published path summary no longer names COMBINE among its sampled
critical paths. That supports retaining its execution organization, not proving
that it has unlimited timing headroom or zero physical cost. [R02, R03]

Retain eight bounded execution contexts, the paired two-product schedule, its
NEW and CONTINUATION queues, and separate payload/scratch/completion storage
ownership. Preserve all eight recipes and the count-zero base-colour case.
The source's staged Q/R/O/M/F/W organization is materially different from V1's
record/job scans and scattered per-channel updates. [R06]

Do not fuse this back into a giant owner-indexed arithmetic table merely because
V3 has a global transaction file. Local execution scratch and global fragment
lifetime solve different problems and can coexist without duplicate ordering.

17.2 Phase costs and arithmetic law
------------------------------------

The initial phase accounting is:

  PASSTHRU, ADD_SAT, MASK, count-zero, refusal       one phase;
  MODULATE, MODULATE2X, LERP, DETAIL_MASK            two phases;
  DETAIL_LIGHT                                    three phases.

A zero-product phase still occupies scheduling/writeback resources. Do not omit
it from phase throughput just because no DSP toggles during that operation.
Keep the source's exact dependency order for DETAIL_LIGHT; a later-layer product
must not launch before its earlier-layer byte exists.

The unit multiplication law uses (a*b+128)>>8 with its defined clamp. It is not
a division by 255. For example, 255*255 under this law produces 254. Replacing
it with a normalized 255-based multiply would look cosmetically reasonable and
fail bit equivalence. Retain the exact signedness and rounding of LERP as well;
this document does not invent a replacement for the reference's recipe math.

17.3 Admission is backed by real rows
--------------------------------------

COMBINE gets its recipe, weight, count, base colour, three texture results, and
AUX selection from one owner-aligned registered read packet. The identity portion of the
tag is the 14-bit owner handle, not an arbitrary user tag that might repeat.
Propagated STATUS8 shares the tag transport, for TAGW=22 in the V3 adapter.

Keep missing-sample validation distinct from a sample that completed with an
error payload. A refused material and a texture-service error both terminate,
but their counters and status bits describe different failures.

The input read reservation in section 9 is mandatory. COMBINE's current ready
being high cannot promise that a several-cycle RAM read will find space later.
Either reserve an execution context at read launch or reserve a complete input
packet slot whose own transfer into COMBINE is lossless.

17.4 Completion and retained local stores
----------------------------------------

A final material result writes FINAL_RESULT at its owner slot, together with
status accumulated from the physically required terminal inputs and any
material refusal. Publish final_done only after that write is committed.

The baseline can retain COMBINE's local completion store and output staging,
because changing them at the same time as the island lifetime is unnecessary
risk. Its output handshake transfers ownership of the result to the global
final-commit path, then releases the local context according to the leaf's law.

Section 21 reserves six M10Ks for the local COMBINE storage organization. This
is a planning allowance, not a measured hierarchy extraction. If synthesis
maps small local queues to flops, count those flops. If the final local store is
later removed, prove that the global final writer accepts or credits every
final phase before reclaiming its execution context; do not simply tie ready
high because the owner row exists somewhere.

17.5 Do not infer savings from multiplier source count alone
------------------------------------------------------------

Two source-level product sites can map into zero, one, or more physical DSP
resources depending on implementation choices and packing; logic-based byte
multipliers cost ALMs and routing instead. The recovery should choose the
measured area/timing trade within the island allocation.

Keep a mapping microbenchmark for the two byte lanes using the exact register,
clock-enable, and reset style intended in production. A function-local synthesis
attribute is not evidence that the mapped result uses no DSPs. The V2 source
already records that lesson. [R06]


18. THE ONLY GLOBAL ORDERING BOUNDARY: SYNCHRONOUS FINAL RETIREMENT
==================================================================

18.1 Separate fetch progress from externally visible progress
--------------------------------------------------------------

Use two distinct positions when prefetching more than one output:

  fetch_head: next completed owner whose final/context rows have not yet been
              scheduled into the retirement read pipeline;
  emit_head:  next owner whose output must be accepted externally.

Keep unfetched_count = accepted_owners - final_reads_launched, bounded 0..64.
F0 requires unfetched_count>0, a live owner at fetch_head, and final_done.
This prevents stale done bits from being reread when the ring is empty.
The further invariant is live_count-unfetched_count = fetched outputs not yet
emitted, including the retirement read pipeline and output FIFO.

A read issue advances fetch_head only after reserving destination capacity.
An output handshake advances emit_head and frees owner credit. These are not
the same event and may be separated by arbitrarily long output backpressure.

An owner can be fetched at most once. Do not clear final_done merely to remember
that it was fetched unless an equally persistent, correctly reset state records
its output lease. Keeping a narrow fetched bit or using the two sequence
positions with bounded-distance assertions is acceptable.

18.2 Registered read sequence
------------------------------

A baseline output sequence is:

  F0: require unfetched work, live/final_done at fetch_head, and reserve output;
  F1: register the FINAL_RESULT and OWNER_CONTEXT read address and handle;
  F2: synchronous memory outputs become available;
  F3: capture the aligned result, full context, and status into fabric holding;
  F4: output queue presents its head until the external handshake.

The exact number of register stages may change with the chosen inferred memory
primitive, but the valid timing is defined relative to the actual read edge,
not an assumed zero-latency array. Payload memory output registers are not
asynchronously reset. Their valid pipeline is reset separately.

A two- or four-entry output queue is adequate only if its credit counts read
results in flight as well as queued rows. Reserving at F0 makes the proof
independent of whether the consumer unexpectedly stalls at F2.

18.3 In-order emission and sustained throughput
------------------------------------------------

Reads may issue for a contiguous run of final_done owners, one per clock after
startup. Stop when the next owner is incomplete; do not scan for a younger
completed owner to skip the hole. Internal work may continue out of order, but
external raster/blend-visible emission cannot.

With contiguous completed owners and an always-ready consumer, the pipelined
read/output path must sustain one fragment per clock after warmup. An FSM that
returns to IDLE after every handshake and takes three clocks to reread the next
row is not accepted as an equivalent throughput implementation.

The output tuple remains bit-stable whenever valid is high and ready is low.
This includes status and all 64 context bits, not only RGB. A memory address
that silently advances while a stalled output still refers to its old owner
violates the contract even if RGB happens to repeat.

18.4 Collision and reuse proof
-------------------------------

FINAL_RESULT has one write port from final material commit and one read port
from ordered retirement. A valid read for an owner starts only after its final
write is published. A duplicate final write is a protocol error and is rejected
by the narrow final_claimed/combine_issued state, not allowed to overwrite a
queued output. Final returns use a credited capture/validate/claim/write/publish
sequence analogous to sample returns; final_done is not used as a substitute
for the earlier claim while a final write is still in flight.

OWNER_CONTEXT is immutable from admission through output emission. Because
owner reuse occurs only after emission, a prefetched output cannot refer to
context that a younger admission has replaced. A deliberately stalled output
at ring wrap is the decisive regression test for this law.

A conservative allocator does not reuse a full ring slot on the same edge it
is emitted. The one-cycle bubble at exact fullness is preferable to adding
untested RAM collision and generation-forwarding behavior to the first V3.
Any later bypass is measured separately.

18.5 A slow head is not permission to discard it
------------------------------------------------

A missing sample can block the final output. That is a fault or an allowed slow
external service, depending on the transport contract. The watchdog records
which owner and obligation is blocking, how long it has been outstanding, and
which queue or external transaction owns it.

The watchdog does not release the owner, skip a sequence, fabricate a colour,
or reuse the slot. Recovery is a defined transport error completion or global
drain/reset operation. Quietly skipping a head would convert a visible stall
into silent order corruption.


19. BACKPRESSURE, CREDITS, RESET, CANCELLATION, AND LIVENESS
==========================================================

19.1 Two legal pipeline styles, not a mixture of assumptions
------------------------------------------------------------

For each stage segment choose one of:

  ELASTIC: the segment holds its valid payload until accepted. Any backward
  ready path is locally bounded and is cut by a correctly sized skid/credit
  boundary before it becomes an island-wide combinational chain.

  RESERVED FIXED LATENCY: the segment never stalls after launch. A destination
  credit is reserved before launch and covers every result still in flight.

Do not describe a backward ready equation as depending only on local occupancy
when it algebraically depends on downstream ready through several stages. The
current bilerp lane is a small elastic pipeline; its short backward ready chain
is visible in the actual equations. That is not the same as a registered-ready
boundary between large subsystems. [R07]

The baseline paired PERSPUV implementation uses short elastic segments with
skid storage at the segment boundaries. It does not assume a nine-stage
nonstallable pipe can spill into an uncredited two-entry output FIFO. A fully
reserved alternative is permitted only with its larger output capacity and
register/M10K cost entered in the inventory.

19.2 Reservation domains
-------------------------

Maintain separate, named conservation laws for:

  - global owner capacity, admission through final output;
  - RCP execution contexts, seed launch through final result transfer;
  - sample-expansion read slots, bank-read launch through packet release;
  - cache response capacity, probe issue through response pop or precise squash;
  - response pool rows, preparation reservation through completed pool read;
  - palette return capacity, lookup issue through accepted result merge;
  - AUX credits, input admission through terminal AUX result acceptance;
  - COMBINE input read slots and execution contexts;
  - final output slots, read issue through external output acceptance.

A single owner bound does not automatically prove all smaller local queues are
large enough. Conversely, a queue sized to the maximum outstanding owners may
have a simple conservation proof without a combinational full check on every
late stage. Write which argument applies; do not alternate between them to
justify incompatible queue sizes.

19.3 Request issued, response claimed, result committed
--------------------------------------------------------

These are three distinct moments:

  ISSUED: the service has accepted the request and owes a result;
  CLAIMED: the terminal response has passed identity validation and reserved the
           right to commit that sample exactly once;
  COMMITTED: its payload has actually reached the persistent result bank.

Readiness depends on committed, not claimed. Duplicate rejection depends on
claimed as well as committed. Ownership cannot be released while an uncommitted
claim remains. This distinction is the central requirement that makes pipelined
return validation safe instead of merely faster.

A service reporting a valid, identified error completes the issued obligation.
A response with wrong generation, illegal index, or no issued obligation is
rejected and counted. It must not complete another owner's obligation.

19.4 No accidental algebraic ready loop
----------------------------------------

Review the directed ready-dependency graph at composition time. In particular,
ensure that COMBINE input readiness does not depend combinationally on final
output readiness through owner-full, admission, sample expansion, cache, decode,
and completion signals that lead back to COMBINE.

A queue that only stores payload but computes ready from its downstream ready
can leave the long path intact. Cut it with registered credit or sufficient
skid capacity and verify the extra accepted beat after ready falls. A registered
ready without that extra capacity can lose exactly one packet at every stall.

19.5 Reset, abort, and transport ownership
-----------------------------------------

Reset has an externally defined sequence:

  1. stop new owner admission and new external requests;
  2. drain or explicitly abort/acknowledge outstanding external transactions;
  3. clear control-valid, claimed/committed state, queue pointers, reservations,
     and local pipeline-valid bits;
  4. initialize narrow free-context queues as needed;
  5. release reset synchronously and reopen admission only when transports agree
     that no old-epoch response can arrive as new work.

A hard board reset may enforce these guarantees by resetting the entire
transport together. A local island reset cannot assume that it does. State the
reset scope in the shell integration contract.

A future per-owner abort must account for outstanding cache, palette, sheet,
RCP, and COMBINE leases before freeing that owner. It also needs an ordered
external abort outcome. It is intentionally not part of the baseline recovery.

19.6 Liveness claims require service assumptions
------------------------------------------------

Under these assumptions:

  - every accepted external memory/sheet request eventually returns a terminal
    outcome;
  - the external output consumer becomes ready infinitely often;
  - internal arbiters are fair and finite queues preserve their contents;
  - fault injection is finite or has a separately defined admission throttle;

an accepted normal owner must eventually emit exactly once. A practical bounded
latency theorem additionally requires numeric bounds on those external services
and on consumer stall duration. Those bounds are not established by the latest
island fit and must come from the shell/transport contract.

The architecture can prove losslessness under unlimited finite backpressure.
It cannot promise finite completion time when an external device is permitted
to withhold a response forever. Distinguish safety from liveness in assertions
and in the project status.

19.7 Conservation counters as an executable accounting system
-------------------------------------------------------------

Every phase should reconcile admitted work, completed work, queued work, and
in-flight work. A frame-end zero-outstanding check alone is not sufficient:
a counter can lose an increment and still agree with another equally broken
counter. Use event-level assertions and independent scoreboard models.

Simultaneous TMU and AUX faults increment the error total by two. Simultaneous
admission and retirement produce a net owner-count delta of zero. Two event
branches writing separate nonblocking increments to the same register are
forbidden; calculate the delta once and assign the accumulator once.

Observe peak occupancy with a retained high-water mark. A statistic rebuilt
fresh on every query is current occupancy, not a historical peak. Current
occupancy, peak occupancy, cumulative stalls, and outstanding-service age must
have distinct names and tests.


20. THROUGHPUT AND LATENCY ACCOUNTING
=====================================

20.1 Count service demand, not boxes on a diagram
-------------------------------------------------

For a measured frame or bounded workload, record:

  F   accepted fragment owners;
  R   owners actually requiring a nonzero reciprocal;
  S   texture samples accepted by the architectural sampler service;
  T   address plans actually launched;
  C   sample requests actually accepted by the cache;
  B   filtered sample footprints;
  A   AUX requests;
  L   external cache-line fills;
  P   total accepted COMBINE phases;
  E   emitted fragments, normally equal to F after drain.

For the current maximum of three texture samples per owner, require S<=3*F.
AUX obligations satisfy A<=F. Replays are not additional architectural samples.
These cross-counter bounds expose population/scope mistakes in a workload table.

Basic service demands for the baseline are:

  reciprocal multiply launch slots       4*R
  paired perspective launch slots         S, excluding explicit zero bypasses
  TMU planning slots                      T, normally S for legal samples
  filtered channel launch slots           4*B
  COMBINE phase launch slots              P
  final output slots                      E
  fill halfword transfer slots            8*L.

For legal ordinary traffic, S, T, and C normally agree. A rejected binding or
other pre-cache terminal outcome can make T or C smaller; report that difference
rather than pretending an error consumed a cache request.

These resources overlap. The maximum of their demands is a lower bound on
completion time under ideal overlap; their sum is not the normal pipeline cost.
The maximum is also NOT a worst-case guarantee: finite credits, miss replay,
head-of-line blocking, external arbitration, and configuration drains can add
cycles beyond it.

In particular, the retained cache globally suspends ordinary probing while a
fill is handled. Its miss and hit service cannot be assumed to overlap as if
it were an unconstrained nonblocking cache. The trace model must reproduce the
actual C1/C2 squash, replay, fill, and response-reservation behavior.

20.2 Distinguish frequency from frame throughput
------------------------------------------------

At a 100 MHz clock, 60 Hz provides approximately 1,666,667 clocks per frame.
An 80 percent design allocation would be about 1,333,333 clocks. These numbers
are arithmetic, not a claim that the complete console already grants the
texture island that uninterrupted budget.

The inspected earlier PERSPUV rationale quotes 1,094,600 sample pairs against
1,333,333 clocks. At one pair per clock that uses about 82.1 percent of that
allocation before stalls; at one pair per two clocks it cannot fit. The earlier
276,480-fragment reciprocal example requires 1,105,920 product launch clocks,
about 82.9 percent of the same allocation. These are historical sizing examples,
not a newly captured current game benchmark. In particular, do not combine
1,094,600 samples and 276,480 owners into a single claimed three-sample trace:
the former exceeds three times the latter. Their original population scopes
must be reconciled before they can share one frame budget. [R08, R09, R10]

This is why V3 keeps paired U/V and a reciprocal product launch every clock.
It is not enough for a slower engine to say that it has many contexts. Contexts
hide latency; they do not create missing arithmetic service capacity.

Likewise, the old 180,000 filtered RGB channel-job example becomes 240,000 RGBA
jobs if it represented 60,000 filtered samples with the same workload. That is
a conditional recalculation, not a measurement of today's traffic mix. The
actual W9b phase count must be read from the current trace. [R07, R03]

20.3 Latency-hiding capacity
-----------------------------

If an engine issues one independent phase per clock and a context cannot issue
its next dependent phase until d clocks later, it needs roughly d independently
ready contexts to keep that resource full. Queue bubbles, arbitration, and
nonfinal/final competition may require more. Measure the exact feedback loop.

For RCP, start with 16 contexts against the explicitly staged product and
writeback path. For COMBINE, retain eight and verify its observed phase launch
rate. Do not multiply each context depth by the owner's 64-entry lifetime cap.

For an external service with average admitted request rate lambda and average
response residence T, lambda*T is a useful average occupancy estimate. It does
not size a queue against burst arrivals or worst-case memory arbitration. The
64-owner window has to survive the actual distribution of slow heads, not just
an average latency number.

Measure both maximum owner occupancy and the number of cycles admission was
blocked by owner exhaustion. If the latter dominates after the arithmetic
pipeline is fixed, first determine whether the cause is a real transport
latency, an avoidable extra ordering barrier, or a leaked reservation. Increasing
OWNER_DEPTH is not the first response to a leak.

20.4 Production workload acceptance set
----------------------------------------

Use at least these separately reported traffic profiles:

  WARM_DIRECT: one-sample RGB565 nearest, all cache hits, output always ready;
  WARM_FILTERED: nonuniform RGBA footprints and four channel jobs per sample;
  THREE_SAMPLE: independent coordinates and bindings for each material input;
  MIXED_CLASSES: interleaved CLUT4, CLUT8, direct nearest, and direct filtered;
  RECIPE_MIX: all eight recipes with deliberately different phase counts;
  AUX_MIX: normal, saturated, negative, and degenerate geometry;
  COLD_STREAM: measured miss/fill latency and line-sharing behavior;
  BACKPRESSURE: long independent stalls at each externally stallable boundary;
  SCENE_TRACE: the actual retained renderer/game request trace at the target
               frame rate and the agreed memory arbitration profile.

A warm-hit II test is not substituted for COLD_STREAM. A phased single-binding
fixture is not substituted for MIXED_CLASSES. A frame that contains no AUX
cannot establish the auxiliary credit or context law.

20.5 Configuration and generation barriers have a real cost
------------------------------------------------------------

The baseline binding/envelope configuration epoch is drained before mutation.
The compact owner generation also has a wrap-drain policy. Count the stop,
drain, command-update, and reopen intervals in scene throughput.

With 64 owners and eight generation bits, the same slot/generation namespace
can repeat after 16,384 normal ring admissions. Whether that barrier is cheap
or significant depends on the oldest external request and how the shell batches
work. Do not assert it is negligible without a trace.

The preloaded 256-binding baseline supports different bindings every sample
without a drain. Only mutation/reuse of the configuration requires it. If real
scene streaming needs frequent updates while old work remains outstanding,
activate a versioned binding profile with explicit old-version references and
an updated memory allocation. Do not use the late global binding pins as a
shortcut around a missing version protocol.

20.6 Stop/go thresholds based on evidence
------------------------------------------

A lower register count with half the pair or channel issue rate is not recovery.
A higher Fmax with untested CLUT4 or tied-off AUX is not recovery. A 100 MHz
island that misses the required scene deadline because of refill or barrier
stalls is not recovery either.

The performance gate is simultaneous:

  correct accepted workload + required issue rates + bounded storage + agreed
  clock timing + frame trace completion within the actual shared-system budget.

Record the maximum term and the observed stall additions, rather than attributing
every missed frame to whichever block most recently had a poor Fmax.


21. RESOURCE ALLOCATIONS AND NON-NEGOTIABLE PHYSICAL GATES
==========================================================

21.1 An allocation is not a prediction
--------------------------------------

No number in this section is a new fit result. The only newly executed numerical
experiments in this review are the integer identities in Appendix C. The purpose
of this inventory is to prevent uncounted state and to give the implementation
agent a physical contract before it writes more convenient arrays.

The earlier 5,500-6,600 ALM and 6,000-8,000 register objectives remain the goals.
The 7,500 ALM, 9,000 register, and 14 DSP redlines remain escalation gates.
A design exceeding them is reported as a failed allocation, not quietly accepted
because it is smaller than 16,192 ALMs.

The memory target needs a more explicit split than the earlier 32-56 range:
56 blocks cover the core planes and scheduled queues below. Real credited
elastic buffering can deliberately use another eight, for a 64-M10K planning
profile. This document recommends that fully accounted profile rather than
hiding the same storage in several thousand flops to preserve a headline of 56.
This is an explicit proposal to spend up to the escalation threshold, not a
claim that 56 already includes every queue in the machine.

21.2 Core bank inventory: 56 M10Ks
----------------------------------

  Group / independently ported store                  Blocks   Running total
  -------------------------------------------------  ------   -------------
  OWNER_CONTEXT, 64x64                                    2          2
  MATERIAL, 64x48                                         2          4
  AUX_GEOMETRY, 64x80                                     2          6
  SAMPLE_DESC_0/1/2, each 64x80                           6         12
  RCP_RESULT, 64x32                                       1         13
  SAMPLE_RESULT_0/1/2, each 64x40                         3         16
  AUX_RESULT, 64x40                                       1         17
  FINAL_RESULT, 64x40                                     1         18
  SAMPLE_METADATA, 256x40                                 1         19
  Cache: four static data + four static tag banks         8         27
  Prepared response pool, 16x120                          3         30
  Palette, 1,024x16                                       2         32
  Binding descriptors, 256x128                            4         36
  Envelopes, 16x160                                       4         40
  RCP local payload77 + scratch64, each 16 deep            4         44
  COMBINE local payload/scratch/completion/tag allowance   6         50
  RCP_PENDING, 64x40, includes denominator                 1         51
  SAMPLE_OWNER, 64x17                                     1         52
  AUX_PENDING, 64x14                                      1         53
  READY_TMU / READY_AUX / READY_INITIAL, each 64x14         3         56

The envelope selector is eight bits but only 16 envelopes are allocated. The
binding ID is eight bits and all 256 binding rows are allocated. Those are
explicitly different capacities.

The RCP payload width is m24+seed32+owner14+k6+zero1=77. Its scratch is x32+w32.
The RCP_PENDING record is where the raw denominator waits before a local
execution context is available. There is no omitted 64-entry denominator array.

The COMBINE allowance corresponds to approximately three width slices for its
110-bit payload and one each for scratch, completion, and tag. Its tag can carry
owner14 plus propagated status8 in the same 22-bit tag row. Final material
refusal is folded into status when writing the global final result. This uses
the existing generic tag transport rather than inventing another status table.

21.3 Explicit buffered profile: up to eight additional M10Ks
------------------------------------------------------------

The recommended physically conservative profile allocates:

  AUX offer FIFO, 16x32                             1
  AUX terminal-return FIFO, 16x40                  1
  Raw cache-return capture, 8x80                   2
  Final output FIFO, 4x120                         3
  PERSPUV side-metadata FIFO, 16x40                1
                                                  -
                                                  8

Total planned memory blocks: 56 + 8 = 64.

AUX offer32 covers owner14+u6+v6+degenerate1 with reserved bits. AUX return40
covers owner14+tag8+strength8+degenerate1+status8 with one reserved bit. These
queues remain separately written because divider offers and sheet results may
arrive in the same clock. Combining their declarations into one RAM would not
remove that port conflict.

The final FIFO's 120-bit row holds context64+result/status40+owner14 with two
reserved bits. The owner remains live until that row is emitted. Every RAM FIFO
uses a credited synchronous prefetch/head cache; replacing a flop FIFO with RAM
without adding its read-valid timing is not accepted.

The PERSPUV side FIFO is a specific reduction of pipeline register replication.
It holds sample_handle16+binding8+LOD8+status/flags8 once. The paired arithmetic
pipe is ordered and carries a four-bit local lease index through its stages,
plus only arithmetic controls needed at those stages. Before result transfer,
read the matching side row synchronously into a reserved output packet slot.
The side lease is returned only after that packet is safely transferred.
Depth-zero travels in the same ordered pipeline or has an explicitly ordered
join; it does not overtake the side FIFO and mismatch a following pair.

This is optional if the plain full-tag pipeline already meets the register
allocation. The eight-block profile is the maximum of these explicitly named
choices, not an entitlement to add eight unrelated memories later.

21.4 What is still in logic and registers
-----------------------------------------

Small owner control masks, per-class pool-index queues, free-context queues,
pipeline arithmetic registers, FIFO head caches, scalar counters, coverage bits,
and command arbitration remain in fabric. They are not free merely because
the big payload arrays moved to RAM.

The RCP generated seed ROM is retained as its exact table. The 64-block profile
budgets its current combinational lookup implementation in logic, with output
capture in the normalization path. If exact-tool synthesis instead maps that
lookup into one M10K, the result is a 65-block variant and must be reported as
such or the allocation revised. Do not hide it under the four RCP context
blocks or assume its bit capacity fits an unrelated port-occupied memory.
A dedicated seed-ROM M10K may be a sensible trade; the important point is honest
counting, not refusing one useful block on principle.

Likewise, a live double-buffered binding or palette version profile adds storage
unless another existing bank can legally be reused. Its extra read/write ports
and version retention must appear in the inventory before fitting.

21.5 Register sanity bounds
-----------------------------

The narrow owner scoreboard is not tiny: a representative 29-bit per-owner
control allocation already costs 1,856 flip-flops for 64 owners. Removing one
mask may save registers only if another invariant genuinely makes it redundant;
it must not remove the distinction between issued, claimed, and committed.

The paired arithmetic and iterative execution pipelines need another substantial
set of registers. A useful preliminary implementation envelope is approximately
3,000-4,000 arithmetic/associated-control registers, plus roughly 2,000-3,000
registers for remaining small queues, captures, decode/planner stages, and
counters. Together with the owner state, that suggests roughly 6,900-8,900
registers as a sizing envelope, not a fitted forecast.

That envelope intentionally exposes the risk: the first correct V3 may land
above the 8,000 objective even while staying below the 9,000 redline. The
side-metadata FIFO and explicitly RAM-backed AUX/raw/output queues are the
planned response to that risk. An agent must not claim 6,000 registers by
counting only persistent record planes and omitting all their read pipelines.

Before place-and-route, the synthesis report must identify every remaining
wide flop array and every register-dense hierarchy. Review duplicated payload
before shaving a two-bit state machine. Do not reduce the owner window or
sample throughput merely to pass the count.

21.6 ALM working allocations
-----------------------------

One workable allocation sheet, to be replaced by measured attribution, is:

  owner/control/completion/ready/retire machinery          1,800
  RCP, including seed logic and correction                  600
  paired PERSPUV arithmetic/recombination                    950
  retained cache control and interface                      800
  binding resolver and planner                              650
  response preparation, class control, decode                450
  retained COMBINE organization                              450
  AUX, envelope handling, and exact Mosaic glue              600
  configuration, counters, and remaining top-level control   200
                                                           -----
                                                           6,500 ALMs

These are budgets assigned to implementation owners, not source-derived estimates
of achieved utilization. In particular, the 450-ALM COMBINE entry is not a claim
about the isolated V2 fit; its full body and mapping were not independently
measured in this review. If one row exceeds its allocation, the total must be
reconciled before integration, not padded with negative savings from another
unmeasured block.

21.7 DSP allocation and exact mapping experiments
-------------------------------------------------

  RCP unsigned 32x32 product tile               candidate 2; allow measured 2-4
  two simultaneous PERSPUV products            candidate 4; allow measured 4-6
  one channel/cycle bilerp pipeline             allow measured 2-3
  paired COMBINE byte products                  logic or measured 0-1
  cache, descriptor arithmetic, AUX, Mosaic     target 0

The combined range is a mapping study, not a license to sum whichever favorable
endpoints are needed for a report. Select one actual implementation and publish
its total. The working goal is 10-13 DSP blocks or lower with the same service
rate; 14 is the architecture escalation gate.

The Cyclone V independent-multiplier mode makes small-product packing plausible,
but reset, clock enables, register positions, signedness, and fitter decisions
can prevent the hoped-for packing. The exact Quartus 17 microbenchmark is the
authority. A synthesis attribute or a count of asterisks in the source is not.
[V06]

21.8 Failure rules
-------------------

Stop before another long fit if synthesis shows a supposedly banked 64x80 payload
as thousands of registers, a multiwriter array behind a ramstyle attribute,
a forgotten service FIFO outside the budget, or a full decode path stripped
because its valid/format inputs are constants.

Stop before production integration if the composed design exceeds 7,500 ALMs,
9,000 registers, or 14 DSPs without an explicit revised allocation; if the
memory count exceeds its adopted profile without attribution; or if any claimed
throughput/functional capability is absent from the observable wrapper.

A resource gate is a decision point. It is not an excuse to call a smaller,
slower, or semantically incomplete design the same architecture.


22. TIMING ARCHITECTURE AND TRUSTWORTHY FIT EVIDENCE
===================================================

22.1 What the register boundaries are intended to remove
--------------------------------------------------------

The architecture removes these combined cones:

  returned identity -> broad live/gen/mask selection -> RAM write enable;
  scheduling scan -> wide operand mux -> multiplier;
  memory output -> asynchronous metadata lookup -> arithmetic -> writeback;
  context-array output -> variable rounding add -> variable shift -> saturation;
  output ready -> several service ready chains -> upstream admission state;
  virtual configuration pin -> generation lookup -> palette control.

The replacement stages separate address selection, memory read, fabric capture,
small control decisions, arithmetic, and final commit. Whether each stage fits
within the desired clock period remains a physical result to be measured.
The document does not assign invented nanosecond delays to source expressions.

22.2 Three distinct physical evidence configurations
-----------------------------------------------------

A. LEGACY-COMPARABLE ISLAND WRAPPER

   Retain a wrapper that makes the same functional subsets and observability
   visible as the current fit where comparison is meaningful. Clearly mark
   interface additions and remove no active feature simply to match area.
   This helps distinguish architectural savings from virtual-pin changes.

B. REGISTERED PRODUCTION-CONFORMANCE WRAPPER

   Use real registered producer/consumer boundaries, all supported formats,
   full context, actual bindings, nonconstant geometry, and the adopted
   configuration protocol. Virtual I/O may still exist outside those boundary
   registers, but the functional island paths are measured register to register.
   Separate wrapper resources from core resources while publishing both.

C. REDUCED RENDERER + TEXTURE ISLAND COMPOSITION

   Integrate the actual interface and clock/reset/memory service assumptions.
   This is where the standalone timing margin is spent. Passing B cannot stand
   in for C; routing and control paths change in composition.

Do not subtract 743 virtual-pin-containing ALMs from the current report and
call the remainder a measured core count. Those ALMs may contain other logic,
and the fitter's packing changes when the boundary changes. Measure a wrapper
with explicit hierarchy attribution instead. [R01]

22.3 Constraints and signoff
----------------------------

The adopted product clock remains 100 MHz. Use a correctly constrained clock,
clock uncertainty appropriate to the actual source, and the relevant I/O or
registered-boundary constraints. Check generated clocks and CDC boundaries
rather than assuming every port is synchronous to the island clock. [V07]

Require setup, hold, recovery/removal where applicable, and unconstrained-path
reports. A reported Fmax is not complete timing signoff. The vendor's Fmax
summary is a summary for relevant clock paths and is not a substitute for all
required timing checks. [V05]

Do not silence a violating valid, ready, generation, or payload path with a
false-path constraint. Do not add multicycle constraints merely because an
operation takes several pipeline clocks: the real launch/capture relationship
must justify the exception, including its hold counterpart.

The provisional device is 5CSEBA6U23I7. Successful placement on that part is not
board proof for a different MiSTer/SuperStation One FPGA, speed grade, memory
interface, PLL configuration, or pin assignment. Confirm the actual board
before claiming deployability.

22.4 Targets, not guaranteed forecasts
---------------------------------------

Retain these desired gates:

  standalone production-conformance island   115-120 MHz objective;
  full relevant composition                   105 MHz acceptance floor;
  full composition                            110 MHz objective;
  product operating clock                     100 MHz.

These are engineering margins inherited from the existing architecture goals,
not timings obtained by this review. A 100 MHz-only standalone island may be
useful progress but has not earned the planned composition margin. [R08]

At a declared target, report worst setup slack directly. Also report clock
period, path start/end hierarchy, data delay, clock contribution, logic depth,
and high-fanout nets for the dominant failing families. A MHz label alone
cannot tell whether another register or a different storage schedule is needed.

22.5 Path-origin and path-family reporting
------------------------------------------

For every physically meaningful run, separate:

  boundary-origin paths;
  internal register-origin paths;
  memory-output-origin paths;
  output-boundary endpoints;
  setup/hold and clock domains.

Then group paths by structural family and endpoint, not only by module name.
A FRAGROB endpoint can be driven by a cone originating in wrapper storage or
a different service. Endpoint dominance is not an area attribution and does
not prove that all remaining internal constraints are inside that module.

The earlier 189-path internal sample and derived 77.30 MHz estimate remain
useful diagnostics, but only the actual replacement run with its real boundary
can establish improved timing. Do not publish the estimate as a second fit.
[R02, R03]

22.6 Cheap experiments before a long composition
------------------------------------------------

Run these in increasing cost order:

  1. language/lint and deterministic model tests;
  2. exact Quartus analysis/synthesis on the small changed memory/arithmetic
     shapes, including RAM and DSP mapping checks;
  3. small physical fits of the completion bank, RCP tile, paired perspective,
     and synchronous output path;
  4. synthesis of the full feature-live island, with hierarchy counts;
  5. one replacement composed fit only after its functional and allocation
     prerequisites pass;
  6. a bounded seed sweep for a credible candidate, not repeated fitting of a
     known structurally incomplete design;
  7. actual renderer/island composition and board-specific closure.

A synthesis pass proves neither timing nor functional correctness. It does
prove enough about language support and memory shape to avoid discovering a
basic unsupported construct after another two-hour run. The repository's
Quartus 17 versus Verilator and stale-binary incidents make this gate necessary.
[R18]

22.7 Immutable source-closure manifest
--------------------------------------

Every fit run gets an immutable run directory containing:

  run ID and start/end timestamps with timezone;
  base commit and dirty-state description;
  a sorted list of every source/include/ROM initialization file;
  SHA-256 of each exact file copied into the run;
  top entity, parameter overrides, and relevant feature flags;
  Quartus executable/version/build and target device/speed grade;
  all QSF/SDC settings and their file hashes;
  fitter seed, optimization/effort settings, and timeout policy;
  semantic tests and exact binaries/source closures associated with them;
  map/fit/timing summaries, return codes, and terminal status;
  archived detailed reports or a durable artifact location and hashes.

Prefer a clean commit containing the entire tested closure. If a frozen working
snapshot is used, label it a mixed/dirty snapshot and archive its bytes. A Git
HEAD field alone does not identify source that was committed after the snapshot
was made. That is the specific provenance weakness of the current sourceCommit
field; it is not evidence that COMBINE V2 was absent from the latest run.
[R02, R03]

22.8 Runtime status and evidence retention
-------------------------------------------

Distinguish RUNNING, SYNTHESIS_FAILED, FIT_FAILED, TIMING_FAILED, TIMED_OUT,
CANCELLED_BY_OPERATOR, and SUCCESSFULLY_COMPLETED. Fitter success with negative
setup slack is not a completed timing gate. An intentional cancellation is
not a fitter failure.

Use CPU progress, process identity, and report-stage state to assess liveness;
log inactivity alone can misclassify a busy fitter. Keep a sufficiently large
explicit runtime budget. Do not start two expensive fits against a shared
mutable build directory or allow a watcher to kill a valid run under an old
unrelated cutoff.

The large raw map report need not live as a tracked multi-megabyte Git blob.
Store it as a compressed artifact with a hash and stable run reference. Retain
compact machine-readable hierarchy RAM/register/DSP attribution in the repo so
a reviewer can audit a result without relying on a prose summary. Removing a
large tracked file is compatible with good evidence only if its useful
attribution remains retrievable. [R19]


23. VERIFICATION ARCHITECTURE AND ADVERSARIAL TEST MATRIX
=========================================================

23.1 Four independent kinds of evidence
----------------------------------------

Keep these separate:

  INTEGER LAW: exact scalar arithmetic and address/format semantics;
  TRANSACTION SAFETY: ownership, identities, ordering, credits, and stalls;
  PHYSICAL SHAPE: inferred RAM ports, register arrays, multiplier mapping;
  PHYSICAL TIMING: constrained placement/routing and composition margin.

A green member of one category does not establish the others. The latest test
repairs are valuable precisely because they distinguish plausible output from
an address- and format-specific correct output. Preserve those checks and add
the missing production cases. [R15]

23.2 Independent owner/sample scoreboard
----------------------------------------

The C++ testbench keeps its own map keyed by full owner identity and a sequence
of expected externally visible outputs. It must not use the DUT's internal
head, masks, or live count to decide what should have happened.

At admission, record every captured field and all expected physical requests.
At each service handshake, match identity and record one obligation. At each
terminal result, record its exact success/error law. At emission, compare all
pixel/status/context fields with the independent scalar result in strict
admission order. Duplicate output is a failure even when its colour matches.

Use nonzero, nonuniform payload initialization in software models. Where the
simulator supports randomized/uninitialized-state modes, use more than one
initialization seed. Explicitly reuse slots that previously held different
coordinates and colours before testing zero/bypass cases.

23.3 Owner and lifetime tests
------------------------------

  O01: admit 64 owners, stall output, prove owner 65 is not accepted;
  O02: release one output, admit one replacement, verify no other row changed;
  O03: run thousands of wraparound admissions with randomized output stalls;
  O04: hold a final output across repeated internal completions and verify every
       bit of context, status, tag, alpha, and RGB is stable;
  O05: delay the oldest sample while every younger owner completes;
  O06: inject a stale generation after slot reuse; no current mask may change;
  O07: force namespace-wrap drain with an old packet still held externally;
  O08: prove admission cannot reopen before the transport drain acknowledgement;
  O09: reset while an untagged fill is mid-line and while sheet work is live;
  O10: verify zero-work owners still emit once, without fabricated service jobs.

The normal ring-reuse tests must exceed 64 admissions. The generation test must
exercise the actual rollover policy, not merely generation 1 versus generation
2. Tests that stop before the relevant boundary cannot establish the boundary.

23.4 Completion hazard tests
-----------------------------

  C01: matching owner but sample_index=3;
  C02: requested but never-issued sample;
  C03: matching issued sample returned twice on consecutive clocks;
  C04: duplicate arrives after claim but before RAM commitment;
  C05: duplicate arrives after commitment but before COMBINE admission;
  C06: last TMU and last AUX completion for the same owner on one edge;
  C07: TMU and AUX make two different owners ready on one edge;
  C08: two identity errors on one edge increment the total by two;
  C09: output retirement and next admission coincide while a stale response is
       already in the validation pipeline;
  C10: stop each completion destination in turn and verify reservations cover
       all packets already captured upstream;
  C11: emit a legal error completion and prove the required bit is satisfied;
  C12: reject an illegal identity without satisfying any current required bit.

At every edge, independently check claimed implies an existing reserved commit,
committed implies data was written, and ready_ticket_count(owner)<=1. A done bit
may not rise merely because a future RAM write was scheduled.

23.5 Memory-port and read-latency tests
----------------------------------------

  M01: each producer's event count equals its memory write count;
  M02: every read packet's identity matches the address launched for that read;
  M03: random stalls during RR/RC never mix a new token with an old RAM output;
  M04: a pool row cannot be reallocated while its read lease is live;
  M05: a final result is not fetched twice while the output head is stalled;
  M06: same-address collisions obey the declared old/new/impossible law;
  M07: invalid rows with arbitrary old contents are never consumed;
  M08: Quartus synthesis names the expected physical RAMs, widths, and depths;
  M09: removing or corrupting a read-valid stage makes the test fail;
  M10: turning one intended single writer into two is rejected by the structural
       gate or visibly changes the mapped register count.

The negative tests are important. A source linter that reports zero violations
because its pattern matched no arrays has not verified RAM inference.

23.6 Address, format, binding, and geometry tests
------------------------------------------------

  D01: all five legal format encodings plus all three illegal format codes;
  D02: every CLUT4 nibble position, odd/even byte positions, nonzero bases;
  D03: nonuniform 2x2 footprints with nearest, correct bilerp, swapped weights,
       and swapped taps producing distinguishable results;
  D04: ARGB1555 zero/one alpha and ARGB4444 nonuniform filtered alpha;
  D05: negative repeat, clamp, mirror and boundary crossings;
  D06: rectangular mip chains, maximum legal dimensions, oversized dimensions,
       maximum level clamping, and exact Q4.4 integer-level selection;
  D07: three distinct sample numerators/bindings within one owner;
  D08: CLUT and direct formats interleaved without fully drained phases;
  D09: binding ID reused only after the correct configuration epoch transition;
  D10: palette slot/generation deliberately unrelated to owner slot/generation;
  D11: context upper bits independent from world X/Z;
  D12: nonunit AUX envelopes, negatives, upper clamp, degeneracy, stale selector;
  D13: Mosaic selection changes the binding that actually reaches the cache;
  D14: change every live ingress pin immediately after each admission and during
       downstream stalls; outputs still match the captured record.

D14 includes configuration inputs and every prefix, not only frag_. The current
fixture explains why a prefix-limited capture checker missed global binding
inputs. A real resolved descriptor removes that source of ambiguity. [R15]

23.7 RCP and perspective arithmetic gates
------------------------------------------

Preserve the existing serial/reference implementations as independent oracles.
Do not replace the oracle with the same newly factored arithmetic before using
it to check the replacement; that would make a shared mistake self-confirming.

For RCP:

  - compare every generated seed table entry;
  - compare zero and every nonzero 24-bit denominator in a standalone scalar
    exhaustive run if practical on the development machine;
  - independently test the product/correction for deliberately arbitrary x and
    w, including negative correction cases outside friendly convergence paths;
  - compare every intermediate MW/MX state and final mantissa/exponent;
  - randomize local queue and output backpressure;
  - check exactly four product phases for each nonzero reciprocal;
  - check the declared zero-bypass job count and its ordered owner outcome.

For PERSPUV:

  - positive/negative numerator extremes, zero, sign boundaries;
  - every reachable k from 1 through 24;
  - rounding ties, just-below/above saturation, and reused zero-depth slots;
  - paired U/V under independent values, not merely U==V;
  - saturation and depth-zero flags as well as coordinate outputs;
  - continuous one-pair-per-clock load with downstream stall bursts;
  - side-metadata slot wrap and delayed read return if that profile is selected.

The full-denominator sweep is a required implementation gate, not a test claimed
to have run in this research session. Appendix C's million-scale Python cases
cover different, explicitly stated identities and are not a substitute.

23.8 Cache, decode, and palette stress
---------------------------------------

Reproduce the old warm-hit response-loss stimulus before accepting any cache
adaptation. Fill the response queue, keep probes in flight, then resume the
consumer and require every admitted token exactly once.

Exercise fills crossing request/response queue wrap, miss squashes with a queued
response pop, multicast masks, disabled lanes, and repeated tag replacement.
Feed class traffic that fills each class independently, then drain it while
other classes remain active.

For palette, test missing entry, duplicate index, CRC failure, same-generation
BEGIN, lookup on BEGIN, lookup during load, and cold/stale completion under a
stalled terminal merge. Hold multiple palette results in their new queue; a
single always-ready lookup does not test the repaired seam.

23.9 COMBINE and final ordering tests
--------------------------------------

Check all recipes against the unchanged material reference, with sample count
zero, valid counts, and missing-input refusals. Choose data that distinguishes
U(a,b) from division by 255, LERP sign handling, saturation boundaries, and
DETAIL_LIGHT dependency order.

Create deliberately different phase lengths so younger jobs actually complete
before older ones. Prove the internal ready/COMBINE path exploited that freedom,
then prove the final output is still exactly admission ordered. A strict-order
test in which no internal reordering occurred is incomplete evidence.

Use sample-service error status with a recipe that changes the magenta payload.
The final status must still record the service failure even though the final
colour is no longer the diagnostic colour. Legacy refused semantics must remain
separately checked.

23.10 Mutation tests for the testbench itself
---------------------------------------------

At least one deliberate mutation must make each critical family fail:

  remove a completion reservation;
  skip claimed in duplicate validation;
  publish done one edge before the write;
  swap owner/sample metadata indices;
  force format RGB565;
  drop nibble_select;
  force alpha 255;
  restore a live binding pin read;
  return pool credit at read issue;
  release owner credit at COMBINE completion;
  use unsigned perspective shift;
  remove RCP high-word negative correction;
  change /256-style multiplication to /255;
  allow the output fetch pointer to advance without an output reservation.

Record the mutation, expected failing assertions, actual failures, and the hash
of the restored source. A test described as adversarial but never shown to
reject the known bad implementation is weaker evidence than it appears.

23.11 Evidence records for every implementation change
------------------------------------------------------

Each accepted patch records: exact source revision; new/retained contracts;
actual test executable and rebuild status; count of comparisons; corner cases;
negative-test result; synthesis shape; measured resource change if available;
and which claims remain unmeasured.

A process that failed to invoke a tool, a stale executable, an empty report,
and a test listing without execution are not passes. The repo already documents
several forms of that trap. Do not let the new architecture inherit it. [R18]


24. REPOSITORY MIGRATION PLAN AND IMPLEMENTATION LANES
======================================================

24.1 Preserve a reproducible comparison point
----------------------------------------------

Keep the current V2 composition intact as the regression baseline. The new top
and replacement modules initially live beside it. Retain the source and build
lists required to compile both. Do not rewrite the golden leaf or remove its
test before the replacement has passed differential checks.

Before changing the running hardware branch, make a reviewed implementation
commit that records this architecture's adopted capacities, interface changes,
and exception policy. This research deliverable does not itself modify the
repository or claim those decisions have already been implemented.

The pinned review snapshot is d884ce01c2d02453e935c6bf33bfe85a5c4c7a1e. The
implementation agent must enumerate current branches and compare the live
hardware revision against it. Do not assume another agent's later terrain or
memory-contract work is already merged into this snapshot.

24.2 Stage 0: executable contracts and physical microbenchmarks
---------------------------------------------------------------

Deliver:

  - packed owner/sample/status/descriptor records and field-range checks;
  - explicit config-epoch, palette compatibility, reset/drain, and output rules;
  - a software transaction model independent of the old FRAGROB internals;
  - small exact-tool RAM probes for 64x80, 256x40, 16x120, and the proposed
    synchronous FIFO/head-cache forms;
  - small exact-tool product probes for RCP tile, perspective tile, and the
    retained paired byte multipliers;
  - a reproducible run-manifest generator and report extraction schema.

Gate: every proposed language/memory shape compiles under the actual Quartus
17 toolchain, and the intended RAM ports exist in synthesis. This stage does
not require a full-island multi-hour fit.

24.3 Stage 1: owner, completion, and retirement skeleton
--------------------------------------------------------

Build the owner ring, the banked result/context planes, C0-C4 completion, the
once-only ready queues, and synchronous final retirement. Replace texture/AUX
services with adversarial tokenized stubs and replace COMBINE with a checked
result producer temporarily.

The stubs must reorder, delay, duplicate, refuse, and stall within their defined
fault contracts. The purpose is to prove ownership and storage independent of
the complicated arithmetic. The temporary skeleton is explicitly not a
production fit; its stubbed arithmetic cannot become the reported island area.

Gate: O/C/M test families pass; illegal duplicate/late writes cannot change a
live owner's output; long output stalls cannot overwrite slots; simultaneous
TMU/AUX publication creates the right number of ready tickets; one output per
clock is sustained once contiguous final rows are available.

Then fit this skeleton as a structural experiment. Confirm that payload banks
are RAM and the return-to-write-enable path ends at the intended registered
commit signals. Do not infer full-island Fmax from this experiment.

24.4 Stage 2: resolve real bindings and finish format identity
--------------------------------------------------------------

Adapt the planner and introduce the immutable binding/envelope descriptor epoch.
Carry format, effective filter, byte select, nibble select, palette identity,
and status in the metadata row. Remove independent production class input.

Use the current cache initially behind its exact repaired interface. Add the
central metadata read, response pool, class queues, and palette-result credits.
Retain existing direct-colour/alpha mutations and add interleaved binding and
CLUT4 oracle tests.

Gate: D-series tests and cache-loss regressions pass. The legal nearest/decode
paths are genuinely active. All supported formats are represented in the
conformance wrapper. No global base/mode pin is read after the owner admission
or accepted immutable configuration resolution.

24.5 Stage 3: paired perspective service
-----------------------------------------

Introduce the paired ordered PERSPUV pipeline alongside the existing service.
First preserve the old arithmetic widths and change execution organization.
Then apply the proven width/split-shift/product implementation as a separately
reviewed change, retaining the unchanged oracle.

Add the optional 16x40 side-metadata FIFO only with its own lease and stall tests.
Compare performance and mapped registers with and without it; do not retain
extra indirection merely because this document allows it.

Gate: one U/V pair per clock under continuous work, exact values/flags across
all reachable exponents, stable output under stalls, depth-zero slot-reuse
coverage, and actual resource/timing attribution.

24.6 Stage 4: queued RCP and exact product correction
-----------------------------------------------------

First build a standalone arithmetic tile with arbitrary x,w inputs, full
corrected product visibility, and the exact rounded iterate. Prove it against
the current modular expression and run the exhaustive denominator comparison
through the actual seed and iterative control.

Then attach free/NEW/CONT queues, 16 execution contexts, payload/scratch RAM,
and the common terminal commit stream. Use zero-product scheduled phases for
zero requests rather than an independent second global result writer.

Gate: values and intermediate states match the independent oracle; nonzero
requests use four product jobs; saturated scheduling meets the intended issue
rate; context reuse and simultaneous admission/nonfinal writeback are safe;
exact-tool DSP count fits the adopted implementation allocation.

If the arithmetic mapping is worse than expected, keep the proven queued
control and evaluate a different exact product mapping. Do not change reciprocal
precision or serialize four products to manufacture a small count.

24.7 Stage 5: real AUX/Mosaic/COMBINE adapters
----------------------------------------------

Use separate geometry and full opaque context. Preserve the repaired AUX offer
and terminal-credit mechanisms. Extend its token width through every internal
and external side channel, not just its module signature.

Make Mosaic selection influence the binding actually consumed. Hook the
retained COMBINE V2 to owner-aligned result reads and carry sample status through
its tag metadata. Its output writes the reserved global final bank.

Gate: independent geometry/context tests, true AUX terminal reordering, all
recipes and sample counts, actual Mosaic-controlled texture selection, and
strict ordered final output.

24.8 Stage 6: feature-live synthesis, then one composed fit
-----------------------------------------------------------

Regenerate every source closure/build manifest that instantiates the island.
The inspected run log records a missing CMake source-list update that broke
build regeneration when V2 was first swapped in. Avoid repeating that exact
integration error. Check both legacy and V3 targets. [R03]

Run the complete semantic/adversarial suite on a verified rebuild. Produce a
feature-live analysis/synthesis report. Reconcile the actual RAM inventory,
wide flop arrays, DSP use, and adopted allocation. Archive the tested source
snapshot and constraints.

Only then launch the next long V3 fit. Its comparison sheet includes the old
16,193/63.54 row, the real V2 16,192/67.57 row, and the new row with explicit
capability/observability differences. A failed or timed-out run remains an
explicit result, not a missing cell filled with an estimate.

24.9 Stage 7: renderer composition and board-specific gate
------------------------------------------------------------

Integrate the actual reduced renderer, memory arbitration, reset, and full
output consumer. Run the retained scene trace under its agreed service budget.
Fit the composition under the actual clock constraints and then the exact board
part, speed grade, and interface settings.

A standalone successful V3 is not automatically the final console. Conversely,
a standalone failure should be diagnosed by the measured structural families
before the entire renderer is rewritten around it.

24.10 Parallel agent ownership and merge order
------------------------------------------------

Safe independent work lanes are:

  LANE CONTRACT: records, scalar transaction model, status/config/reset law;
  LANE OWNER: owner ring, bank wrappers, completion, ready events, retirement;
  LANE SAMPLER: binding/planner, metadata, response pool, decode/palette;
  LANE RCP: exact arithmetic tile and queued local execution;
  LANE PERSP: paired pipeline and side-metadata lease;
  LANE INTEGRATION: AUX/Mosaic/COMBINE adapters and build manifests;
  LANE EVIDENCE: independent tests, mutation scripts, fit manifests/reports.

Only one integration owner edits the composed top and shared build lists at a
time. Other lanes deliver reviewed interfaces and isolated tests. Do not run
concurrent CMake reconfiguration or competing fits in one mutable build directory.
An agent may work outside a frozen fit closure, but must derive that exclusion
set from the actual manifest rather than memory.

The reviewer lane should not merely restate the implementer's passing counters.
It must execute the independent tests and inspect the mapped memory/port
structure, including deliberate negative cases.


25. REJECTED SHORTCUTS AND DECISION RULES
=========================================

25.1 Another COMBINE redesign as the first response
---------------------------------------------------

Rejected. The available timing sample indicates that V2 removed the previously
observed COMBINE bottleneck. Start with ownership, storage, and return commit,
while preserving V2's local organization. Revisit COMBINE only when a real new
fit attributes a relevant bottleneck or allocation failure to it.

25.2 A registered FRAGROB write-enable without a claim protocol
---------------------------------------------------------------

Rejected. Delaying only the write permits duplicate acceptance, early readiness,
old-generation writes after reuse, or misaligned bank/data signals. Capture,
validate/claim, commit, and publish are separate state transitions.

25.3 One enormous multiported fragment RAM
-------------------------------------------

Rejected. The common owner address is logical identity, not permission to demand
several independent reads and writes from one M10K. Split planes by physical
port ownership and schedule the consumer that needs each plane.

25.4 A true-dual-port RAM label as a cure for arbitrary port counts
-----------------------------------------------------------------

Rejected. True dual port does not mean unlimited simultaneous readers/writers,
and its legal width modes differ from simple dual port. Count accesses and
collisions against the exact Cyclone V primitive. [V03]

25.5 Resetting every payload to remove unknown values
------------------------------------------------------

Rejected. Reset ownership and validity. Initialize payload only through a real
write or an explicit output bypass. Tests must catch invalid reads rather than
making all old data coincidentally zero. [V02]

25.6 Freeing owner capacity upstream of external emission
---------------------------------------------------------

Rejected. FRAGROB retirement, COMBINE acceptance, final-result write, and output
prefetch do not end the externally stalled fragment's lifetime. Only its final
accepted output or a fully acknowledged abort can do that.

25.7 Quiet format, alpha, source-map, or precision reductions
-------------------------------------------------------------

Rejected. No dead nearest path, CLUT4 treated as a byte, forced opaque ARGB,
collapsed three-sample material, changed bilerp rounding, approximate reciprocal,
or substituted hash. Such a design may fit well precisely because it no longer
implements the product.

25.8 Four-products-over-four-clocks arithmetic sharing
------------------------------------------------------

Rejected as the default recovery. It breaks the required reciprocal or paired
perspective launch rate. Only a separately accepted workload/capability change
could justify that service reduction; extra queue depth does not compensate.

25.9 Treating virtual-pin paths as automatically irrelevant
------------------------------------------------------------

Rejected. Some boundary cones represent real missing ingress registers; others
are artifacts of the fit wrapper. Build and measure the registered production
boundary. Do not erase the paths from the report and announce a replacement
frequency that was never fitted.

25.10 Chasing seeds before fixing structure
--------------------------------------------

Rejected. Seeds can measure variability around a credible candidate. They do
not give a two-write memory one port, capture a late binding, preserve a lost
palette pulse, or prove the source closure includes the intended module.

25.11 Calling the architecture doomed from a single bottleneck step
-------------------------------------------------------------------

Rejected. The current result is a serious failure against the product allocation,
but it is not a proof that Cyclone V cannot meet the intended design. Several
wide state organizations, extra lifetime conversions, and unregistered control
cones are still present. Their removal is a testable hypothesis, not a guaranteed
victory and not a reason to abandon the project before measuring it.

The earlier conversational claim that the next FRAGROB fit alone would decide
whether the whole island is salvageable was too strong. A single replacement
can expose another near-critical path without establishing a fundamental limit.
The correct decision uses a series of attributable physical results, full
functional coverage, and a reconciled resource/service budget.

25.12 Treating unchanged ALMs as proof of exact cost cancellation
----------------------------------------------------------------

Rejected. The V2 fit changed COMBINE and revived/extended decode together. The
net area is measured; the separate contributions are not. Synthesis packing and
optimization are nonlinear. The report can say the changes are confounded,
but not assign each a precise saving or claim that one exactly funded the other.

25.13 Rejecting useful RAM because the block count rises
--------------------------------------------------------

Rejected. The target FPGA has a separate embedded-memory resource budget. A
few dozen deliberately underfilled M10Ks can replace large mux/register fabrics.
The trade must be counted against the whole console, but more M10Ks and far
fewer ALMs/registers can be exactly the desired outcome. It is not intrinsically
a regression because the old incomplete fit used 25 or 32 blocks. [R01]


26. ACCEPTANCE CHECKLIST AND THE FIRST IMPLEMENTATION TASK
==========================================================

26.1 The first task is the completion-bank experiment
------------------------------------------------------

Do not begin with a giant top-level rewrite or another full-island fit. Build
one small V3 owner/completion/retire experiment with the real proposed capacities:

  64 owners and full generation identity;
  three statically banked 64x40 sample-result stores;
  one 64x40 AUX result store;
  required/issued/claimed/committed control;
  simultaneous TMU and AUX terminal inputs;
  once-only ready-ticket creation;
  a final 64x40 result store and 64-bit context path;
  synchronous credited ordered output;
  an adversarial testbench and exact-tool synthesis/fit wrapper.

This experiment directly tests whether the proposed structural replacement
removes the reported return-to-RAM-write-enable cone without introducing new
multiwrite payload state or losing correctness. It is small enough to inspect
and attribute, and it does not depend on speculative whole-island savings.

In parallel, the RCP arithmetic tile can establish its own exact-tool packing.
Do not merge those changes into the composition until the shared record and
credit contracts are fixed.

26.2 Definition of architecture-complete
-----------------------------------------

V3 is architecture-complete only when:

  one owner identity lasts from admission to output;
  payload bank ownership matches actual inferred memory ports;
  required, issued, claimed, and committed are separately enforced;
  no valid sample/result is destroyed under finite backpressure;
  all source identities, bindings, formats, nibble/byte selectors, and alpha
  reach the actual consumer that affects the output;
  full context and independent geometry remain distinct and observable;
  COMBINE sees the current owner's real samples and exact recipe law;
  only final retirement enforces global output order;
  phase/issue-rate tests meet the intended service demands;
  source snapshots, tests, synthesis, and fit results refer to the same bytes;
  resource and timing gates pass or are explicitly reported as unclosed;
  actual renderer composition and scene deadlines are separately demonstrated.

A completed architecture specification is not architecture-complete RTL. This
file provides the former and the acceptance conditions for the latter.

26.3 What success would actually look like
------------------------------------------

The next convincing result is not a sentence saying that another old monster
has disappeared from the critical path. It is a reproducible feature-live run
whose RAM report matches its port inventory, whose register count has genuinely
collapsed, whose constrained timing meets the adopted stage/composition gate,
and whose adversarial traces still produce every correct output exactly once.

The principal hypothesis is that the current island pays heavily for fragment
state that was organized for convenient simulation and then repaired locally,
rather than organized from the beginning around the FPGA's ports and lifetimes.
V3 replaces that organization without surrendering the material/texture laws.
The exact RCP identity and paired perspective stream address additional resource
and timing risks, but they do not replace the owner/commit reconstruction.

That is a credible path to test. It is not a fabricated promise of 120 MHz or
6,500 ALMs. The implementation's next evidence must decide those numbers.

B.3 Status allocation and legacy signal mapping
------------------------------------------------

Proposed STATUS8 bit flags:

    bit0 DESCRIPTOR_OR_ROUTE_ERROR
    bit1 PALETTE_COLD
    bit2 PALETTE_STALE
    bit3 TRANSPORT_TERMINAL_ERROR
    bit4 MATERIAL_REFUSED
    bit5 DEPTH_ZERO
    bit6 UV_SATURATED
    bit7 AUX_DEGENERATE.

Bits0..4 are the production aggregate-error set. Bits5..7 are explicitly
reported conditions; their existence alone does not change the compatibility
pixel or make legacy COMBINE refused true. A future policy may treat depth zero
as fatal at an upstream API boundary, but that is not silently added here.

The status for an owner is the OR of status on its physically required terminal
inputs plus its material outcome. This conservatively preserves errors in
legacy overfetched work even when AUX substitutes the final logical colour.
If physical overfetch is deliberately removed, those nonexistent requests no
longer contribute status or request counters; that change is versioned and tested.

Compatibility wrapper:

    legacy_refused = final_status[MATERIAL_REFUSED]
    production_error = OR(final_status[4:0])

Identity faults such as an unsolicited or stale-generation packet are counted
at the rejecting port; they do not set a new owner's sample status. An actual
service error with a valid issued identity does set its terminal status and
commits the declared compatibility payload.

The status field is new proposed observability. It is not claimed as already
implemented by the old island's refused bit.

B.4 Pipeline conservation equations
------------------------------------

For every reservation domain, specify events at one edge and update once:

    next_reserved = reserved + accepted_new_reservations
                             - accepted_final_consumptions
                             - explicitly_cancelled_reservations.

Transfers within that domain are not releases. Examples:

    cache hit -> response queue        transfer, not release
    palette pulse -> holding queue     transfer, not release
    owner final write -> output queue  transfer, not owner release
    RCP local final -> global result   release local RCP lease only
    pool RAM read issue                not yet a pool-row release.

For the global owner ring without aborts:

    live_next = live + admission_fire - output_fire.

For each source in a live owner:

    committed subset_of claimed subset_of issued subset_of required,

except that a deliberately defined local bypass may synthesize an issued/claimed
terminal obligation through the same formal event path. It may not simply set
committed without defining what establishes its payload.

Once-only readiness:

    eligible = live && ((committed & required) == required)
    make_ticket = eligible && !ready_claimed && !combine_issued.

The implementation computes committed after coalescing this edge's publication
events, and sets ready_claimed atomically with the queue reservation. Required
zero work has its own admission-origin event. A queue write delayed by a
register does not delay the claim that prevents a second ticket.

B.5 Completion-event coalescing algorithm
------------------------------------------

This is algorithmic pseudocode, not compiled RTL:

    validate TMU and AUX input packets against their captured/forwarded control;
    reject invalid identity/range/unsolicited/duplicate packets;
    reserve a first valid source's claim before creating its commit packet;
    register separate TMU and AUX commit packets;

    at commit:
        write the static texture bank selected by the registered TMU packet;
        independently write AUX_RESULT from its registered AUX packet;

    at publication:
        if both publications name the same full owner handle:
            merged_bits = tmu_source_bit OR aux_source_bit;
            calculate one next_committed mask;
            create at most one ready event for that owner;
        else:
            independently update the at-most-two affected owners;
            create at most one event for each, in their producer-owned queues.

    apply admission initialization and output release with explicit precedence;
    never combine events from different generations merely because slot matches.

This does not require a priority scan across 64 owners. A generated array of
narrow control banks may decode registered event addresses in parallel, while
wide payload is kept out of that update logic. A loop that creates independent
per-slot control is different from a sequentially dependent 64-way scheduler.
Its decode fanout still needs placement/timing review.

For a C1 snapshot implementation, forward relevant older C2 claims and C4
publications before validating/deriving eligibility. State the maximum forwarding
window from the actual pipeline depth; increasing that depth invalidates a
hardcoded two-entry recent-event assumption. A valid C3 write relies on its
prior claim lease, not on a new broad live-table lookup on the memory enable.

B.6 Clock-only synchronous RAM coding pattern
----------------------------------------------

The following is an ILLUSTRATIVE shape for an isolated synthesis experiment.
It has not been compiled in this review. Its caller must reserve output capacity
before rd_launch and must supply the registered address stage. It is not a
complete ready/valid FIFO and must not be pasted as one.

    module zhao_sdp40_shape_example (
        input  var logic        clk,
        input  var logic        rst_n,
        input  var logic        wr_en,
        input  var logic [5:0]  wr_addr,
        input  var logic [39:0] wr_data,
        input  var logic        rd_launch,
        input  var logic [5:0]  rd_addr,
        output var logic        rd_valid,
        output var logic [39:0] rd_data
    );
        (* ramstyle = "M10K" *) logic [39:0] mem [0:63];
        logic [39:0] ram_q;
        logic read_v;

        // Payload memory and its output register have no asynchronous reset.
        always_ff @(posedge clk) begin
            if (wr_en)
                mem[wr_addr] <= wr_data;
            ram_q <= mem[rd_addr];
        end

        // Fabric capture is also not reset; rd_valid controls its use.
        always_ff @(posedge clk) begin
            if (read_v)
                rd_data <= ram_q;
        end

        always_ff @(posedge clk or negedge rst_n) begin
            if (!rst_n) begin
                read_v  <= 1'b0;
                rd_valid <= 1'b0;
            end else begin
                read_v  <= rd_launch;
                rd_valid <= read_v;
            end
        end
    endmodule

This shape assumes any valid same-address write/read collision is prohibited
or separately specified. Invalid background reads may observe anything because
rd_valid is false. The ramstyle attribute expresses implementation intent; the
Quartus RAM report, not the attribute, establishes the physical result.

        -> assumption supplied by the external transport model, not a local

Check actual previous-cycle snapshots where a pipeline delay is involved.
A property that checks the new generation against the old owner's event can
fail for the wrong reason or accidentally pass a stale-write bug. Reset disable
and first-valid-cycle handling belong in the property, not in testbench folklore.

B.8 Arithmetic boundary identities
------------------------------------

RCP:

    w = (u24(m)*u32(x)) >> 24 fits in u32
    b = (2^31-w) modulo 2^32
    neg = w > 2^31
    corrected_product = u32(x)*u32(b) - (neg ? x<<32 : 0), modulo 2^64
    next_x = product[61:30] + product[29], modulo 2^32

PERSPUV on the composed valid domain:

    k in 1..24, sh=32-k in 8..31
    signed32(n)*unsigned24(mant) fits in signed56
    (s >> (sh & 7)) >> (8*(sh >> 3)) == s >> sh, arithmetic shifts

CLUT4:

    logical texel offset T -> byte offset floor(T/2), nibble T&1
    selected byte comes from final byte address low bit, not blindly T bit1
    all four halfword nibble positions remain distinguishable.

All carries, casts, and truncations must be explicit in SystemVerilog. Python's
unbounded integers do not validate an accidental signed32 cast of 2^31 or a
logical shift on a negative intermediate. That is why the RTL comparison is
still mandatory.

----- BEGIN architecture_numeric_checks.py -----
#!/usr/bin/env python3
"""Independent arithmetic checks for the proposed architecture; NOT RTL tests.
Only Python's standard library is required. No repository files are modified.
"""
from __future__ import annotations
import json
import random
from pathlib import Path

M32 = (1 << 32) - 1
M64 = (1 << 64) - 1
SEED = 0x5A48414F
RANDOM_CASES = 250_000

def tiled_u32(a: int, b: int) -> int:
    """Four 16-bit products and carry-explicit recombination."""
    a0, a1 = a & 65535, a >> 16
    b0, b1 = b & 65535, b >> 16
    p00, p01, p10, p11 = a0*b0, a0*b1, a1*b0, a1*b1
    cross = p01 + p10
    low_sum = p00 + ((cross & 65535) << 16)
    high = p11 + (cross >> 16) + (low_sum >> 32)
    return ((high & M32) << 32) | (low_sum & M32)

def mx_original(x: int, w: int) -> tuple[int, int]:
    t64 = ((1 << 31) - w) & M64
    p = (x * t64) & M64
    return p, (((p + (1 << 29)) & M64) >> 30) & M32

def mx_rewrite(x: int, w: int) -> tuple[int, int]:
    b = ((1 << 31) - w) & M32
    p = tiled_u32(x, b)
    hi = ((p >> 32) - (x if w > (1 << 31) else 0)) & M32
    corrected = (hi << 32) | (p & M32)
    iterate = (((corrected >> 30) & M32) + ((corrected >> 29) & 1)) & M32
    return corrected, iterate

def perspective_tiled(n: int, mant: int) -> int:
    sign = -1 if n < 0 else 1
    return sign * tiled_u32(abs(n), mant)

def saturate_i32(x: int) -> int:
    return max(-(1 << 31), min((1 << 31) - 1, x))

def main() -> None:
    if not __debug__:
        raise RuntimeError("Run without -O/-OO: these checks use assertions.")
    rng = random.Random(SEED)
    boundary = [0, 1, 2, 63, 64, 127, 128, 65535, 65536,
                (1 << 29)-1, 1 << 29, (1 << 31)-1,
                1 << 31, (1 << 31)+1, M32-1, M32]
    tested = 0
    negative_correction = 0
    for x in boundary:
        for w in boundary:
            assert mx_original(x, w) == mx_rewrite(x, w), (x, w)
            assert tiled_u32(x, w) == x*w
            tested += 1
            negative_correction += w > (1 << 31)
    for _ in range(RANDOM_CASES):
        x, w = rng.getrandbits(32), rng.getrandbits(32)
        assert mx_original(x, w) == mx_rewrite(x, w)
        assert tiled_u32(x, w) == x*w
        tested += 1
        negative_correction += w > (1 << 31)
    mw_checked = 0
    for _ in range(RANDOM_CASES):
        m, x = rng.getrandbits(24), rng.getrandbits(32)
        p = m*x
        assert p < (1 << 56)
        assert (p >> 24) <= M32
        assert (tiled_u32(m, x) >> 24) == p >> 24
        mw_checked += 1
    persp_checked = 0
    for _ in range(RANDOM_CASES):
        n = rng.randrange(-(1 << 31), 1 << 31)
        mant = rng.getrandbits(24)
        k = rng.randrange(1, 25)  # reachable nonzero RCP output: leading-zero count + 1
        sh = 32-k
        prod = perspective_tiled(n, mant)
        assert prod == n*mant
        summed = prod + (1 << (sh-1))
        split = (summed >> (sh & 7)) >> (8*(sh >> 3))
        assert split == summed >> sh
        assert saturate_i32(split) == saturate_i32((n*mant + (1 << (sh-1))) >> sh)
        persp_checked += 1
    # Include the signed extreme explicitly rather than hoping random data hits it.
    for n in [-(1 << 31), -(1 << 31)+1, -1, 0, 1, (1 << 31)-1]:
        for mant in [0, 1, (1 << 23), (1 << 24)-1]:
            for k in range(1, 25):
                sh = 32-k
                p = perspective_tiled(n, mant)
                assert p == n*mant
                s = p + (1 << (sh-1))
                assert ((s >> (sh & 7)) >> (8*(sh >> 3))) == s >> sh
                persp_checked += 1
    # Exhaust every direct-colour halfword. Cross-check bit replication against
    # its shift/OR formulation; not a comparison to a compiled repository oracle.
    decode_checked = 0
    for h in range(65536):
        r5, g6, b5 = (h >> 11)&31, (h >> 5)&63, h&31
        assert ((r5 << 3) | (r5 >> 2)) == (r5*8 + r5//4)
        assert ((g6 << 2) | (g6 >> 4)) == (g6*4 + g6//16)
        assert ((b5 << 3) | (b5 >> 2)) == (b5*8 + b5//4)
        # CLUT4 uses four texels per halfword, not just two byte positions.
        for lane in range(4):
            byte = (h >> (8*(lane >> 1))) & 255
            idx = (byte >> (4*(lane & 1))) & 15
            assert idx == ((h >> (4*lane)) & 15)
            decode_checked += 1
    result = {
        'seed': hex(SEED), 'random_cases_per_family': RANDOM_CASES,
        'u32_tiled_and_MX_pairs_checked': tested,
        'MX_negative_correction_cases': negative_correction,
        'MW_width_and_product_cases': mw_checked,
        'perspective_product_and_split_shift_cases': persp_checked,
        'CLUT4_halfword_position_cases': decode_checked,
        'status': 'PASS',
        'scope': 'Python integer identities and boundary/random tests only; no RTL simulation, no Quartus run, no claimed silicon proof'
    }
    Path(__file__).with_name('numeric_check_results.json').write_text(json.dumps(result, indent=2)+'\n')
    print(json.dumps(result, indent=2))

if __name__ == '__main__':
    main()

APPENDIX D. WORKED CYCLE TRACES AND FAILURE COUNTEREXAMPLES
==========================================================

D.1 Consecutive duplicate responses during a pipelined commit
-------------------------------------------------------------

Owner H, sample1 is required and issued, but not yet claimed or committed.
Response A is valid. Response B is a duplicate of A arriving one clock later.
The labels below name what occurs at each edge; actual HDL offsets must match
its registered interface timing.

  edge     A                           B
  ----     --------------------------  -------------------------------
   t0      captured C0                 absent
   t1      control snapshot C1         captured C0
   t2      validates and claims C2     control snapshot C1 may see old claim=0
   t3      payload write C3            C2 sees forwarded A claim; REJECT
   t4      completion published C4     no payload write; duplicate count moved

A design checking only committed at B's C2 accepts B incorrectly because A's
payload has not yet been published as committed. A design using the unforwarded
C1 snapshot also accepts B even though the scoreboard now has claimed=1.
The claimed distinction and the recent-event rule are both necessary.

The correct terminal count is one, the correct payload write count is one,
and the correct duplicate count is one. It is not sufficient that the second
write happened to contain the same colour.

D.2 Two last-source publications for one owner
------------------------------------------------

H requires sources 0,1,2,AUX. Before this edge:

  required  = 1111
  committed = 0011.

This edge publishes texture source2 and AUX for the same full owner handle:

  TMU event = 0100
  AUX event = 1000
  merged    = 1100
  next committed = 1111.

There is ONE eligibility transition and ONE ready ticket. Choose one producer
queue deterministically for this coalesced event, for example READY_TMU, and
suppress the other insertion. Both source payload writes already happened.

If the TMU event instead makes owner H ready and the AUX event makes owner J
ready, emit TWO tickets to their separate producer queues. Updating only one
shared ready-FIFO write pointer twice loses a ticket; forcing a single ticket
per clock without a holding/reservation stage also loses one.

D.3 Why a response reservation lasts through FIFO residence
------------------------------------------------------------

A cache response queue has capacity four. Three responses are queued and one
probe already owes a result:

  queued=3, in_flight=1, reserved=4.

The queue alone appears to have a free slot. Issuing another probe because
queued<4 is wrong: two future results would need the same final slot.
The fourth result arriving merely changes the representation:

  queued=4, in_flight=0, reserved=4.

It does not release a reservation. Only a consumer pop makes reserved=3 and
allows a new probe. On a miss, refund only actual squashed probes, never an
already queued successful result.

D.4 Palette pulse meets a stalled completion writer
----------------------------------------------------

At t0 a palette lookup is accepted with a reserved return entry. At t1/t2,
according to the adapted leaf latency, its result pulse appears while terminal
completion is stalled.

Correct: enqueue the pulse into the already reserved entry, keep its token and
status stable, and release the reservation only when the merger accepts it.
The producer is free to emit its next previously credited result.

Incorrect: deassert a newly added fr_tmu_ready signal and assume the palette
will try again. It has no return-ready interface. The pulse disappears, one
sample never commits, and final retirement eventually stalls at that owner.

Round-robin fairness becomes safe only after the formerly urgent pulse has a
place to wait. Arbitration alone does not create that place.

D.5 Pool lease released too early
-----------------------------------

At t0 the class scheduler launches a synchronous read for pool row7. It has not
yet captured that row's data. If it immediately returns row7 to the free list,
RP4 may overwrite row7 on t1 while the read pipeline still expects its old
payload. Depending on RAM collision/read timing, the result can be a different
sample's data paired with the old handle.

Correct: row7 remains leased through the actual memory/fabric capture and safe
transfer into the chosen class's reserved packet storage. Only then can it be
reused. The free-list pop/push counters must express that interval.

D.6 Final-result write does not free the owner
-----------------------------------------------

Owner H finishes COMBINE while the output consumer is stopped. FINAL_RESULT[H]
is written and its row may even be prefetched. H is still live.

If credit is returned at that write, the ring can wrap and a new owner can
replace OWNER_CONTEXT[H] before the old output context is read or before its
identity is validated. The displayed colour can remain correct while the
context belongs to the new owner, making a colour-only test miss the fault.

Correct: H is released only at its accepted output. Both context and result
remain protected through output storage residence. Stall through wrap and use
unique high context bits to detect this independently of RGB.

D.7 CLUT4's lost bit
---------------------

Let an aligned halfword hold 0xABCD, with ordinary little-endian byte selection
under the cache's halfword contract. Its four logical nibble values are:

  nibble position0 -> D
  nibble position1 -> C
  nibble position2 -> B
  nibble position3 -> A.

The two first positions share a byte address; the two last share the next byte
address. Once a logical texel offset has been divided by two to form a byte
offset, its low nibble-choice bit is gone. A later byte selector cannot recover
it. Carrying only byte parity can at best distinguish two positions, not four.

The fixture must choose palette colours that distinguish all four indices.
A palette with equal entries or a texture containing repeated nibbles can let
the wrong extraction pass even when the expected index calculation is wrong.

D.8 RCP negative correction is not a theoretical nicety
--------------------------------------------------------

Choose x=1 and w=0xFFFFFFFF. Then the mathematical correction is:

  2^31-w = -2147483647.

Its wrapped 64-bit representation is 0xFFFFFFFF80000001. Multiplying by x=1
leaves that same value. Merely multiplying by the low32 value 0x80000001 would
instead produce 0x0000000080000001, which is not equivalent.

V3 computes the 32x32 product and subtracts x from its high32 word because
w>2^31. The result is exactly 0xFFFFFFFF80000001. The next rounded/truncated
iterate is then computed from bits61:30 and bit29 under the original law.

At w=0x80000000 the correction is zero, not negative. At w=0, its low32 value
is 0x80000000 and must remain unsigned. These adjacent cases expose careless
sign casts that a friendly converged-Newton sample may never hit.

D.9 Zero reciprocal and ordinary final phase on the same clock
--------------------------------------------------------------

An independent zero shortcut can finish on the same edge as an ordinary MX1.
If both directly write the single RCP_RESULT port or SAMPLE_OWNER queue, one
result is lost or the storage becomes multiwriter.

The baseline avoids this collision by scheduling the zero request as one
zero-product terminal phase in the same phase stream. Phase-valid remains true
while multiply-job-valid is false. It traverses the common terminal rescale/
commit machinery, so at most one terminal write is presented per stream cycle.
The product counter counts zero, the scheduled-phase counter counts one, and
the owner still receives one exact zero result.

A separate shortcut is legal only if it has an explicitly budgeted arbitration
and holding path. That path is not free because its arithmetic is constant.

D.10 Error before cache acceptance
------------------------------------

A sample packet is accepted into the sampler and its issued bit is set. Its
binding is then found invalid before any cache request exists.

Correct: the binding resolver transfers a typed error into its reserved terminal
holding path. Completion validates the already-issued handle and commits the
error result. Cache access/response counters do not increment.

Incorrect alternative one: set issued only at cache acceptance. The error now
looks unsolicited and is rejected, leaving the owner stuck forever.

Incorrect alternative two: inject the error into RP4's payload RAM as another
uncoordinated writer. This destroys the supposedly single-write memory contract.
A separate error holding queue to the completion merger avoids both defects.

D.11 Wide prefetch does not make credits disappear
---------------------------------------------------

Suppose a bank read takes three admitted cycles before the destination can use
its packet, and each owner has one sample. Two total destination credits cannot
support one read per clock indefinitely: both are spent before the first returns.
Quoting a two-entry prefetch buffer without counting read stages is insufficient.

V3 expands narrow owner/sample tickets first, then reads only one selected
sample descriptor packet per clock. Its read/capture stages have explicit
elastic capacity or reservations. No throughput claim is derived solely from
the local sample-index loop, and no uncounted 272-bit owner bundle is replicated
into every read stage.

D.12 Distinguishing a drained configuration from a live-mutation promise
------------------------------------------------------------------------

Bindings A and B are preinstalled in one immutable epoch. Samples can alternate
A,B,A,B every clock without any configuration drain. Their descriptors differ,
and each resolves the correct base, format, palette identity, and address law.

Updating A's base while an old A sample is pending is a different operation.
The baseline stops admission and drains that epoch before mutation. A future
copy-on-write profile can preserve both versions, but it must pay for their
storage, references, and collection. It cannot simply capture binding_id=A and
read whichever version happens to be live several cycles later.
