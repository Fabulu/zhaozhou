# T2's owner fit — the generation table's 512 flip-flops, measured

`zhao_texture_v3own`, source commit `d722f085`, digest `96772668c27c`, 3904 s.

## Like-for-like, established before the comparison was made

The ledger holds two `v3own` rows and neither matched the note I had written
down, so the baseline came from the previous run's own log rather than from my
note. `fit-v3own-t4-fence.log` — same target, same three sources from
`design/fit_targets.yml`, same script, one commit earlier — reports
`RULE zhao_texture_v3own: ALM 5709`. That is the immediate predecessor.

The other row, `zhao_texture_v3own@v3-full` (ALM 5678, 75.79 MHz, commit
`0f5ce601`), is an OLDER labelled run of the same target and is **not** the
baseline. Comparing against it would have understated the ALM change and
overstated the frequency change.

## The structural prediction, which was the only one made

Recorded before the fit: *"`gen_q` should appear in no path."*

Every `*gen_q` node in the top-200 path report is a pipeline register
(`c0t_`, `c1t_`, `c1a_`, `c1f_`, `c3t_`, `c3a_`, `c3f_`, `c4a_`) or a shared
allocator counter (`sh_alloc_gen_q` ×14, `sh_retire_gen_q` ×4). **The bare 64×8
`gen_q` table appears zero times.** `ftc_q` also appears zero times — Quartus
dead-code-eliminated it exactly as §13.1 predicted when `!ftc_q[fetch_q]` left
`fetch_fire_c`.

The new worst internal path is `req_q[2][1] -> iss_q[18][1]` — the per-owner
request and issue bitplanes. The previous worst path ran out of the queue's
write pointer through a wide mux; the generation table is not in the new one
because it is not in the design.

## M6 APPLIED TO THIS REPORT'S OWN FMAX CLAIM

Added later the same session, after docket M6 established that a fit-to-fit
Fmax delta is attributable only if the GATING PATH FAMILY is the same on both
sides.

**It is not, here.** The baseline's worst path was `fence_open_q ->
fence_open_q` (recorded in `V31-T1-FENCE-FIT-20260907.md`: *"fence_open_q ->
fence_open_q is still the worst path with a similar Mux9"*). This fit's worst
path is `req_q[2][1] -> iss_q[18][1]`. Two different families.

So **core→core 91.32 → 98.18 is movement whose cause these two numbers do not
establish**, exactly as with the island's +12 MHz.

**This case is stronger than the island's, and the difference is worth stating
rather than glossing.** The island's palette family moved with ONE file changed
and no structural connection — placement roulette. Here the change deleted 512
flip-flops and 41% of the block's ALM, which is a structural upheaval that would
plausibly move many families at once. Plausible is not established, and the
honest form is: the block got faster, the change was large enough to explain it,
and no measurement here isolates the two.

**What is unaffected**, because it is structural rather than comparative:

* ALM 5,709 → 3,348 on identical scope (same pins, M10K, bits, DSP);
* registers: MAP predicted −560 and measured −560 exactly;
* `gen_q` in ZERO paths and `ftc_q` in zero paths — a claim about the netlist's
  contents, which no gating-family argument touches.

## What did NOT happen

**The ALM gate still fails: 3348 against `max_alms: 1800`, status
`failed:structure`.** The gate is not relaxed and is not moved. A 41% reduction
that still misses the budget by 86% is progress, not arrival.

Core→core 98.18 is **below the 100 MHz product clock**, and reported 94.05 is
further below. This block does not yet close.

## On predictions

The register prediction was made against the MAP stage and landed exactly:
4,310 → 3,750, predicted −560, measured −560. The FIT stage moved by −910
instead, because MAP and FIT count different things — which is the same
distinction, not a miss.

ALM and Fmax were deliberately not predicted. Today's record is three structural
predictions confirmed against four magnitude predictions falsified, and −41% ALM
is a number I would not have guessed in either direction.
