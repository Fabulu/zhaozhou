1. DECISIONS AND SCOPE
======================

FH01 -- ONE FABRIC, NOT FIVE ENGINES.
Keep zhao_field_v3_engine as the shared arithmetic fabric. No private Warp
executor, no resurrected v1 sequencer, no per-profile copies of the multiplier,
root, curve, noise or trig services. Common missing opcode support is repaired
at the shared service/dispatch layer, not hidden in an adapter. [S01,S05,S06]

FH02 -- A PRODUCTION HOST, NOT THE SCALAR TEST DRIVER.
Replace the production behavior of zhao_field_host with a versioned,
association-aware front. Retain the old transaction behavior as a named test
oracle/compatibility instrument, not a second engine in the shipping hierarchy.
Use zhao_field_host_v2 or an equally unambiguous production name, and update
all selection/alias/generator sites together. A newer name alone is no evidence.

FH03 -- THREE IDENTITIES, THREE OWNERS.
A resident program, a prepared association, and an execution context are not
the same object. Do not keep the old equality "program slot == execution
context" as the new architecture. Section 9 defines all three lifetimes.

FH04 -- PROMOTE EXISTING WORK BEFORE INVENTING REPLACEMENTS.
Productionize the Translator, uniform broadcasts, and context refill discipline
already present in field_v3_earth_directed.cpp. Generalize its incomplete
opcode-shape handling and remove test-only assumptions. Do not import its
shadow register file, idealized timing, or non-gating diagnostics as hardware.
The production packer and the benchmark must call ONE lowerer. [S07,S08]

FH05 -- FULL DECLARED OUTPUTS, NOT "ANY OUTPUT".
Every runnable strict descriptor specifies a nonempty required-output mask,
its output count, and an output-source map. Successful completion proves every
required output is available for THIS point AND all its writes have retired.
A zero required mask is invalid in production. A real zero value is valid.

FH06 -- UNIFORM OUTPUTS ARE RESULTS.
A plan may return a prepared scalar with no vector write at all. Seed such
exports from validated association data; do not require a fictitious write.
Vector outputs are captured from actual granted writeback. Preserve both paths.

FH07 -- THREE DIFFERENT STATUS FAMILIES.
Canonical numeric Status{sat,rcp0}, adapter arithmetic status, and execution/
transport refusal are distinct. Legal numeric saturation is not a failed
execution. A missing output is not a numeric zero. [S03,S04,S19]

FH08 -- SKIP CLEAR ONLY UNDER A CHECKED INITIALIZATION CONTRACT.
Validated canonical code cannot read undefined scratch. Prepared native code
must carry the equivalent physical-register proof. Reload changing inputs,
restore association state when necessary, and reset validity/status bookkeeping;
never erase the entire RF per point just because that was the old loop.

FH09 -- ONE ACTIVE PREPARED-DATA DOMAIN, MULTIPLE RUNNING POINTS.
The initial production implementation may have several execution contexts
running distinct points of ONE active association. Tables and prepared-ring
scalars belong exclusively to that association until the fabric drains.
This deliberately avoids widening every existing service with a new program
namespace. It is not permission to run different associations against one
unqualified scalar/table bank. [S09,S10]

FH10 -- ASSOCIATION SWITCHES ARE COUNTED WORK.
To switch prepared data, stop issuing, drain internal work, preserve completed
responses in reserved storage, then activate the next association. Reuse only
explicitly matching table/code generations. Never assert that switching is free.
The scheduler quantum is a measured/proven envelope, not "run a whole draw
forever" or "switch tables after every point".

FH11 -- USEFUL LANES, EXACT STATUS.
At LANES=4 feed four distinct valid points where available. Carry a live mask
and per-point status. Replicated padding may occupy physical lanes only if it
cannot add logical outputs or contaminate live status/counters. The current
OR-reduced ALU flags are insufficient for exact per-point status. [S11]

FH12 -- LEGAL COLD DOES NOT MEAN INCORRECT OR SILENTLY DISABLED.
HOT admission is distinct from canonical legality. Preserve an exact route
for legal programs that fail the native prepared packing or rate certificate.
The default non-HOT hardware route is canonical code on the SAME v3 fabric,
with shared support completed for any missing canonical operations. It may be
slower. A software route is used only when explicitly selected under the
existing cost-class law and actually implemented; it is never substituted
silently in a hardware-completion test.

FH13 -- AUTHORITATIVE RESERVATION BEFORE PUBLICATION.
New loading uses reserve -> fill -> validate -> seal -> bind. The allocator
chooses the slot before writes. A binding becomes executable only after its
own bytes, maps and metadata are complete. The existing low-level commit/
re-header behavior remains an explicitly versioned legacy protocol, not an
accidental implementation of this new transaction.

FH14 -- OP 3 IS EXPLICITLY DECODED.
The old doorbell's catch-all LOAD arm currently catches post_op=3. Replace it
with exhaustive decoding before introducing the extension. Unknown operations
must return a counted refusal, never become a load. [S12]

FH15 -- BACKING STORAGE AND ACTIVE CACHES ARE DIFFERENT.
Keep immutable canonical/physical program images and prepared associations in
bounded, pinned HPS staging, reached through the real bridge. On-chip storage
holds descriptors, the working code, active tables/scalars, contexts and
credited queues. Do not automatically allocate four full tables for every
resident program in on-chip RAM. Memory traffic and activation costs count.

FH16 -- NO PER-POINT DIRECTORY LOOKUP.
Acquire and pin at association open. A live execution refers to a checked
association generation; raw cache-slot numbers are not a game-facing binding.
Program eviction or epoch changes cannot silently retarget an association.

FH17 -- ALL CONSUMERS SPEAK THE SAME RESULT CONTRACT.
Stamp and Flow migrate with the host; Earth and Warp enter through it; Formation
is supported by the same signature and program path. A missing actual Formation
caller is not disguised as a tied-off fifth active client. Semantic profile
support and physical client-port count are separately declared.

FH18 -- EARTH GETS ONE COMMAND-ORDERED REDUCER.
Resolve the existing field-major/vertex-major conflict explicitly. The selected
production Earth path is field-major within one patch working set, with the
existing terrain composition law preserved and exactly one accumulator owner.
This amends the MEANS of R91 and the old vertex-major port arrangement, NOT the
height/velocity/material/nav semantics or the content tier. See section 13.
It avoids a huge matrix of all per-field results merely to transpose streams.

FH19 -- WARP SEMANTICS STAY W01--W18.
Post-skin, view-independent deformation; exact normal representation; proper
culling bounds; identity preservation; both views reuse one deformation.
This directive replaces the shared-FIELD prerequisite discussion, not the
Warp application or visual laws. [S19,S20]

FH20 -- CREDIT BEFORE ACCEPTANCE.
Accepting work reserves a terminal-result location. Neither a stalled consumer
nor a queued maintenance command may prevent an already issued internal result
from draining. Contexts cannot be recycled while old writes can still arrive.

FH21 -- ONE GENERATED HARDWARE-CAPABILITY TABLE.
Opcode shape, service destination, supported execution forms, required operand
counts and result width are checked from one machine-readable source. Retain
the existing single-routing-table fix; do not recreate two diverging lists.
Generate or mechanically cross-check C++/SV tables. [S06]

FH22 -- PROGRAM SHAPE IS NOT INSTRUCTION COUNT.
The Warp ceiling stays 48 canonical instructions; the global canonical ceiling
stays 64. A physical code-store capacity is a separate field. Parameter values
may not silently truncate a six-bit canonical register index or a legal program.
Initial exact configuration uses REGS=64 and physical capacity >=64 words.

FH23 -- FREEZE PRICED TOPOLOGY, NOT INVENTED ALM LIMITS.
Publish physical memory shapes, arithmetic instances and marginal changes.
There is no proved ALM allocation for this repair. Do not promise one, count
an existing engine five times, or describe every RAM as bits/10,240 blocks.

FH24 -- FOUR GATES, NOT ONE GREEN NUMBER.
Report semantic conformance, composed functionality, workload deadlines, and
physical fit/timing independently. Passing the first two does not establish
that the complete console fits or sustains its guaranteed workload.

FH25 -- NO UNOWNED SHARED PREREQUISITES.
The integration owner owns loader, mappings, context control, export/status,
common parameters and both existing-adapter migrations. A worker may report
a new defect, but the coordinator assigns and closes it rather than sending
another Warp packet to discover the same absence.

FH26 -- LEGACY IS AN EXPLICIT MODE, NEVER THE STRICT DEFAULT.
Keep old raw-port fixtures usable only through a named compatibility decoder.
They must specify their actual output count. No production program is made
successful by omitting its output contract or taking an implicit zero-mask
compatibility escape.

FH27 -- BOUNDS AND SIGNATURES ARE CHECKED ABOVE NUMERIC EXECUTION.
A Field program's generic decoder validation is necessary but not sufficient
to bind it as a particular engine profile. Validate counts, lane types, map
indices, immutable input set and the chosen adapter signature as well.

FH28 -- CAPTURE EVERYTHING THAT SELECTS A RESULT.
Frame/epoch identity, canonical bytes, derived-plan versions, prepared values,
consumer selection and association ordering must be reconstructible from the
capture and its resources. Captures never rely on a mutable live HPS pointer
whose historical contents were not recorded.

FH29 -- FAIRNESS INCLUDES ACTIVATION AND MAINTENANCE.
Bound execution batches and maintenance slices; reserve bandwidth for mandatory
clients. A fairness argument omitting scalar/table loads, retries, result
storage, or consumer waits is not an admission proof.

FH30 -- IMPLEMENT THE ENTIRE COMMISSIONED SLICE.
End the campaign with strict real Stamp/Flow host traffic, real command-driven
Earth evaluation, and active DrawWarpedForm deformation through the repaired
service. Shared-library conformance for Formation is required; completion of
an unrelated missing Formation application must not be claimed by a test client.
Do not wait for a decreasing gap count to decide that a shared correctness
repair deserves a commit.


2. VERIFIED STARTING POINT -- WHAT IS REALLY WRONG
==================================================

2.1 The old host is narrower than its advertised generality
---------------------------------------------------------
The inspected host grants one client, clears REGS, writes IN_LANES, starts one
context, and waits for END and a single response. The core uses Stamp/Flow
clients and 13 input / 7 output transport lanes. The Warp profile needs 15
inputs and 6 outputs. The core's 32-word code and 32-register settings cannot
represent all legal canonical Warp programs. See [S01,S13,S20].

Widening those constants is necessary, but does not repair scalar operand
mapping, table ownership, output extraction, or throughput.

2.2 A 7-lane bus does NOT mean every program declares 7 outputs
------------------------------------------------------------
The current header gives an output base but no output count/mask. Its
cur_out_seen != 0 condition only proves that at least one position in the
transport window was written. At the baseline it cannot prove completeness because it
was never told which positions were required. R101 now adds a window mask;
the late reconciliation [S30] records that narrower repair. [S01]

Important correction to earlier commentary: a test using one actual output on
a four-word bus is NOT, by itself, proof that the program promised four
outputs and violated that promise. Transport width and declared arity differ.
The demonstrated defect is the inability to represent and enforce the true
output contract. Repair the metadata and test valid one-output and invalid
partial-multi-output cases separately. Do not "fix" the test by demanding all
padding lanes be written. The same distinction applies to inputs: the raw
add fixture uses R0/R1 and writes R2, even though the transport preloads twelve
words. A strict import must declare its actual two-input signature; the bus
width is not evidence that R2 was a canonical read-only input. [S29]

2.3 FPLAN already separates uniforms -- the production host does not use it
-------------------------------------------------------------------------
zfield::plan, prepare and execute_point already exist. They distinguish scalar
and vector sources and have an explicit OutTag map. The Earth benchmark already
broadcasts prepared scalar values into upper RF registers, maps native uops,
preloads different points and keeps contexts supplied. [S03,S07,S08]

Therefore "there is no useful fast-path machinery anywhere" is too broad.
The absent piece is the PRODUCTION transport/scheduler/lifetime implementation.
Promote the real lowerer and driving discipline, not a new approximate design.

However, its Translator is not a complete general Field lowering library:
its manually selected src_group_width and map_one cases cover its corpus, not
all op shapes. Mixed scalar/vector members may also break group adjacency.
Do not turn a test helper into universal production law merely by moving it.

2.4 The engine does not natively understand all FPLAN source tags
----------------------------------------------------------------
The executor uop store has op,dst,a,b,c,imm and its ordinary operands all come
from the RF. Prepared RING has a special scalar-bank path. A generic FPLAN
UopSrc{kind,index} cannot simply be written into those register-number fields.
The software-to-physical lowering must make that translation explicit. [S05,S08]

2.5 Global tables/scalars are not isolated by a program slot
-----------------------------------------------------------
zhao_field_v3_sbank is one 64-slot bank. zhao_field_v3_ring_svc caches prepared
descriptors and invalidates on sb_we. Table loading addresses a table id and
entry, not an independent program namespace. [S09,S10]

Eight program slots do not buy eight independently active table/scalar sets.
FH09 makes exclusive association ownership enforce this fact. Concurrency
between associations is a later priced option, not assumed behavior.

2.6 Canonical RCP and varying-radius RING need explicit execution coverage
-------------------------------------------------------------------------
The current ordinary ALU handles END/MOV/LDC, arithmetic/select/compare and
DOT2/3. The shared long-op table covers many other operations, including the
prepared RING uop, but not canonical RCP 0x17 or varying-radius RING 0x21.
The latter is explicitly called cold in the routing source. [S06,S14]

A legal program failing HOT preparation must not be handed to a supposedly
universal canonical path without checking these operations. Finish them as
shared service work or use an explicitly commissioned exact software route.
The full-silicon conformance endpoint in this brief requires the shared
hardware route; a deliberate cold classification remains a RATE distinction.

2.7 Skipping E_ZERO is justified by a real existing validator, not optimism
-------------------------------------------------------------------------
zfield::decode checks every source member is defined before use, every
instruction destination lies outside the input interval, and every declared
output is defined. [S04]

That establishes a useful canonical no-scratch-clear proof. It does not, by
itself, prove the physical prepared register assignment or the caller's claim
that an input remains constant over an association. Those need the checks in
section 6. In particular, a register that was uniform before lowering can be
reused/overwritten; inspect the lowered program, not only the canonical input.

2.8 Per-lane status is lost by the current vector ALU wrapper
-----------------------------------------------------------
The wrapper has per-lane saturation flags internally, then ORs them into group
flags. That is adequate for a group aggregate, not a returned Status for each
individual Warp or Flow point. Preserve the narrow flags before reduction and
carry them with actual context/lane identity through retirement. [S11]

2.9 The Earth consumer mismatch is not fixed by a fast host alone
--------------------------------------------------------------
FIELD.SEQ.EARTH requires field-major work and uniform preparation once per
association. The actual zhao_terrain_patch loop requests field results
vertex-major to avoid a lattice accumulator. Its own header describes the
trade and says a cache-backed implementation may transpose it. [S15,S16]

A globally shared table bank plus a vertex-major loop over different programs
can force an association switch at nearly every point. That destroys the
amortization this repair is supposed to buy. Section 13 chooses one bounded,
field-major TERRAIN.PATCH owner rather than ignoring the ordering mismatch.

2.10 A useful older rate is not the current whole-slice deadline
--------------------------------------------------------------
The familiar 10,416 clocks is an older comparison allowance. The amended Earth
contract states <=6,000 clocks per full association and <=850,000 for the
128-association stress slice. It also corrects UPDATE to 297 row-bounded quad
groups, while INIT/DRAIN use 273 flat groups. [S15]

The benchmark driver still contains a 273-group scaling assumption and can
separate gating from diagnostic failures. Its throughput is useful evidence,
not automatic proof of the amended full production slice. Correct the harness
scope before inheriting any pass label. [S07,S08]

================================

                  zfield::decode / plan / prepare
                              |

                              |
                  Pinned HPS host-image capsules
                              |

                              |
                Transactional FIELD capsule loader
                              |
        Program catalogue ----+---- Association descriptor/store
                              |
                    Resolve / acquire / pin
                              |
                 Bounded association scheduler
                              |
             ONE active table + prepared-scalar domain
                              |

                              |

                   several live point contexts
                              |
                  Granted writeback + END/drain
                              |

                              |
             Per-client ordered result delivery / adapters
                   /       |       |       \
                Earth     Warp    Flow     Stamp

Formation uses the same profile service when its real caller is introduced.
Do not instantiate an otherwise unconnected fake Formation producer for a
smaller gap number or for a claim of five live profiles.

3.1 Owners
----------
Canonical bytes and numeric semantics: zfield decoder/interpreter + frozen
Field IR and Q-format specifications. No new opcode semantics in host C++.

Physical lowering: new production library extracted from the current Earth
benchmark Translator and its proven contraction/preparation helpers, with
complete generated opcode-shape handling and explicit fallback classification.

Program catalogue: the FIELD residency layer, adapted from the existing
progcache/progdir implementation. It owns valid identities, ready state,
pins, eviction and publication. One authority, not two shadow directories.

Association state: new shared-host owner. It binds a program identity, prepared
uniforms, caller/frame identity, input variability contract, output contract
and scheduling position. A change of uniforms creates a new generation.

Active scalar/table stores: existing v3 stores behind the activation owner.
They are caches of the selected immutable association/program, not global
mutable registers that software may overwrite while any context executes.

Context feeder: tracks free/preloading/running/retiring contexts and owns all
preload/start writes. It observes all executor events on every clock, including
clocks spent loading a different context.

Export collector: captures actual committed RF writes, seeds uniform exports,
accumulates numeric status and fences END against outstanding writes.

Client adapters: translate their EXISTING application records, retain their
identities, and apply only their application laws. No adapter runs the Field
interpreter in RTL or creates a private residency namespace.

3.2 Keep the existing context-indexed uop store initially
-------------------------------------------------------
The existing executor stores uops by {context,pc}. Do not redesign that store
solely to make this migration look elegant. On first activation of a code image,
load that code into the execution contexts assigned to the association; tag
each context's loaded code with the complete physical-code identity. Reuse
those words only on an identity match. Copying code is activation cost and is
counted. PROGS and CTX are no longer required to be equal.

A subsequent measured optimization may share one program store plus a context
program-base lookup. It must preserve ready/valid and registered fetch timing,
show a real resource/activation benefit, and not get mixed into first conformance.
This keeps the first repair smaller and lets the existing full-engine tests
continue to exercise the actual arithmetic/execution path.

3.3 Do not replicate everything to make isolation easy
-----------------------------------------------------
Exclusive active-association ownership is deliberate. A separate four-table
cache and scalar bank for each of eight programs is not necessary for correctness
when at most one prepared-data domain executes at once. Context parallelism
still hides the v3 instruction pipeline within that domain.

The price is nonzero switching cost. If mixed-workload acceptance proves this
choice insufficient, measure a TWO-domain tagged-cache candidate, including
all service-cache keys and grouping keys. Do not jump directly to five engines.
Such a change needs a new physical resource sheet and re-run mixed-identity tests.


4. CANONICAL PROFILES AND TRANSPORT DIMENSIONS
=============================================

Canonical lanes in spec/form/field-ir.md, by listed field rather than its
occasionally wrong parenthetical count:

 Profile    Input lanes                                            Outputs
 Earth 0    x,z,age,phase,p0..p7                       12            4
 Warp 1     px,py,pz,nx,ny,nz,a0..a3,time,p0..p3       15            6
 Flow 2     px,py,pz,vx,vy,vz,age,seed,dt,p0..p3       13            7
 Formation3 index,time,parent_rot[2],parent_trans[2],p0..p5 12       6
 Stamp 4    u,v,age,strength,p0..p3                     8            3

Warp's old "14" is a count typo, not permission to remove p3. Formation's
listed fields likewise add to 12, not the old parenthetical 11. Validate the
full profile-specific type/order list in the shared signature registry.
The decoder currently permits generic program I/O records; it does not enforce
these exact per-profile signatures. Keep generic decoder tests valid while
making APPLICATION binding strict. [S03,S04,S20]

Canonical outputs:
 Earth: height, velocity, material(u32), nav_cost.
 Warp: displacement dx,dy,dz and replacement nx,ny,nz.
 Flow: replacement position[3], replacement velocity[3], attr0.
 Formation: translation[3], rotation(angle), scale, material phase.
 Stamp: tag_op(u32), strength(unit fx16), emissive(unit fx16).

Capacity constants:
  FIELD_MAX_INPUTS = 15
  FIELD_MAX_OUTPUTS = 7
  canonical register count = 64
  canonical instruction ceiling = 64 globally, profile ceilings unchanged
  active canonical tables = 4, each with independent 2..64-entry count

These are semantic transport maxima, NOT a promise to preload every lane on
all profiles or to execute every program in one cycle. Request metadata carries
the actual input and output contracts. Padding is zeroed, ignored and never
considered an output obligation.

Maintain semantic profile id separately from physical client id. For example,
legacy clients Stamp=0 and Flow=1 may remain numbered that way while their
profiles remain Stamp=4 and Flow=2. Generate the mapping; never infer one from
the other's array index.

Do not reset payload RAM arrays asynchronously. Reset validity, generations,
credits and small control registers. Payload becomes readable only after its
own complete write and publication condition.


5. CANONICAL PROGRAM -> FPLAN -> PHYSICAL EXECUTABLE
===================================================

5.1 Three representations, one numerical authority
--------------------------------------------------
A. Canonical .zprog: the game-visible semantic object. Existing validation,
   instruction encoding, hash and interpreter remain authoritative.
B. Logical FPLAN: existing exact uniform/varying decomposition, source-kind
   tags, output map, preparation block and demand vector.
C. Host physical image: a versioned mapping to the CURRENT v3 ports, preload
   schedule, output registers/scalars, supported service routes and capacities.

Do not write B directly into C's old 64-bit words by stripping source tags.
Do not invent a new arithmetic interpreter for C. Its C++ executable model
calls the existing semantic step layer for operations and models only physical
placement, data ownership and ordering.

5.2 Productionize the existing native-register lowering
------------------------------------------------------
Move the useful Earth benchmark logic into a library such as:
  reference/include/zfield/zfield_host_plan.hpp
  reference/src/zfield/zfield_host_plan.cpp
and a tool:
  tools/field/pack_field_host.cpp
These are PROPOSED new paths, not existing evidence.

The first native mapping is the existing strategy:
  physical varying registers: lower region
  broadcast prepared scalar registers: upper region
  prepared RING descriptors: existing 64-slot scalar bank

Use the existing FPLAN n_vreg, scalar slot identity and OutTag objects. The
physical mapper may compact actually referenced scalar slots, provided every
reference, preparation export and source-map entry moves consistently. It
must check the final register high-water mark, not assume n_vreg alone is the
RF requirement. The current corpus example needing 7+29=36 is a concrete
reason REGS=32 is insufficient. [S07]

5.3 Complete opcode shapes, rather than expanding the helper's guesses
---------------------------------------------------------------------
For every canonical opcode, read the generated source group widths and operand
roles. Map flattened FPLAN sources back to the actual A/B/C group starts.
Examples that must be explicit:
  DOT3: A[3], B[3], one destination.
  LEN3/NORMALIZE3: A[3], no invented B group.
  DIST2: A[2], B[2], not A[3]+B[1].
  ROT2: A[2] and angle B, not the third flattened source as C.
  ROT3: A[3] and angle B plus the axis immediate.
  MAD/SELECT/CLAMP: three scalar operands in their canonical roles.

Check physical adjacency for EVERY multi-member group. A logical group with
some scalar and some vector members may not remain adjacent after the split.
The initial mapper may insert exact MOV packing into reserved scratch if it
proves space and counts the added instructions. It may not alias neighboring
registers and hope the resulting numbers agree.

If the native mapping cannot meet physical register/code capacity or adjacency,
select the exact canonical execution form described in 5.5. Do not reject an
otherwise valid .zprog solely because this optimization failed.

5.4 Prepared RING and smoothstep contraction
-------------------------------------------
Preserve the existing UOP_RING_PREP encoding and its scalar index checks.
Four six-bit scalar indices occupy bits 0..23. The CURRENT Earth translator
also carries smooth mode in bit 24. Some older comments still describe bits
31..24 as wholly reserved; do not implement the old comment over the live
smooth-mode consumer. Reconcile documentation with source and tests. [S08,S10]

Promote the proven contraction once, with its differential control. Do not
hand-copy pattern matching into each profile or packer. The untouched logical
FPLAN and canonical interpreter remain the comparison oracles. The optimization
must preserve outputs AND numerical status, including intermediate saturation.
A shorter instruction stream with different sticky flags is not equivalent.

5.5 Exact canonical form on the same fabric
-------------------------------------------
Every canonical input already occupies R0..R(n_in-1), and input registers are
read-only. A canonical execution image can keep the original register numbering,
original instruction count and original output-register map. Uniform input
registers are loaded once per context activation; varying inputs change per
point. Scratch does not require per-point clear under section 6.

Complete shared opcode coverage before calling this a universal exact route:
- Add canonical RCP to the shared dispatch/service fabric using the existing
  exact Field reciprocal law/leaf, including rcp0. Do not substitute the
  raster/projector reciprocal merely because its width looks similar.
- Add a bounded canonical varying-radius RING route. It must evaluate the same
  midpoint, saturating differences, reciprocals and separately rounded products
  as the canonical step law. Sequence those through the shared services; factor
  reusable v3 ring product logic instead of building a private Warp arithmetic
  copy. Prepared uniform RING remains the faster route.
- All other long op routes must be verified from actual service dispatch, not
  only from field_long_width. A classified opcode with no live consumer fails
  structural conformance.

This adds support to the existing engine generation; it is not resurrection of
the v1/v2 sequencer. Distinct cold service microsequences are permitted; a second
complete interpreter datapath is not. Their costs and op matrices are explicit.

Canonical legality does not guarantee realtime admission. The actual code and
service demand decide HOT/COLD. Keep the caller's selected execution class in
captures and completion evidence. A cold failure to meet a HOT deadline is
reported as such, not hidden by reduced work or a silent software substitution.

5.6 Versions and identities
---------------------------
Keep FIELD_IR_VERSION unchanged unless canonical semantics/validation changes.
Keep the logical FPLAN ABI unchanged if its existing schema is unchanged.
Introduce FIELD_HOST_PROTOCOL_VERSION=2 and FIELD_HOST_IMAGE_VERSION=1 for this
new transport/image. Allocate a new fabric version/capability revision when
the new physical opcode routes or packing become active; do not execute a
cached physical image certified for the previous fabric by matching only hash.
Record the actual newly assigned version in ONE generated registry.

The canonical hash omits some metadata, including the output map, because its
law hashes code and tables. It is an attribution/cache component, NOT proof
that two complete program objects have identical binding semantics. The program
record also identifies the full canonical image (byte length + validated image
CRC, and the capture/resource identity). A same-hash different-image collision
must never silently select another output map. Do not change the canonical hash
formula to make this problem disappear.

CRC equality is not byte equality. Deduplication of independently supplied
canonical objects requires software's exact byte comparison, or else keep them
as distinct immutable object generations. Never deduplicate solely on a pair of
32-bit checksums. A repeated canonical resource handle/epoch must identify the
same immutable canonical bytes; a different object requires a new generation.

A canonical program may have multiple physical images (different varying masks,
execution forms or capacity-certified layouts). Each installed image gets its
own generation-checked PROGRAM image handle. An association names a binding to
ONE such image. Its varying mask and output/preload maps must match that image;
changing them does not mutate an older pinned variant. This is metadata inside
the program catalogue, not another private execution engine.


6. SAFE REMOVAL OF PER-POINT CLEARING
====================================

6.1 Canonical proof
-------------------
For every validated canonical program:
  - every instruction source is an input or was defined by a preceding op;
  - no instruction writes an input register;
  - every declared output is defined by the program;
  - the program is straight-line and terminates at the validated END.

Therefore, after loading all changing inputs for the new point and ensuring
unchanged inputs still belong to this association, previous-point scratch
contents cannot affect a legal execution. This is an induction over the
instruction sequence, not a performance heuristic. [S04]

Erase the blanket E_ZERO walk from the strict validated path. Keep a slow
clear control for differential testing and explicit legacy unvalidated bench
images only. Production may not bypass validation to enter the fast path.

6.2 Native physical initialization proof
----------------------------------------
The production lowerer/validator emits and checks:
  - physical varying input map and required per-point write set;
  - association preload set, values and destination registers;
  - physical instruction definitions and reads, including expanded group members;
  - immutable broadcast registers not clobbered by the vector program;
  - output-source maps and their required validity;
  - code/register bounds after any packing or contraction.

Start the symbolic defined-set with this association's committed preload set
plus this point's accepted varying writes. Walk every physical instruction,
checking reads before adding its destination group. Reject the physical image
if a read is unsupported by that set. Never "repair" a bad proof by setting
all registers defined because a previous context happened to use them.

6.3 Input immutability is a caller contract
-----------------------------------------
zfield::decode does NOT discover whether time, p0 or a vertex attribute is
constant across a caller's work. zfield::plan accepts a varying mask.
The association builder chooses the mask from the real producer and freezes
all uniform values. The host validates that point traffic cannot overwrite
uniform-only lanes. Changing one of those values requires a new association
version or an explicit close/reactivate, never a live pin change.

Typical masks, subject to the actual application signature:
  Earth: x,z vary; age,phase,p0..p7 uniform for one field/patch/tick association.
  Flow: position,velocity,age,seed vary; dt and p0..p3 uniform for one selected
        population/program/tick cohort.
  Warp: position,normal vary; STREAM4 attributes vary; INLINE attributes can be
        uniform; time and p0..p3 uniform per immutable draw descriptor.
  Stamp: u,v vary; age,strength,p0..p3 are explicit frozen association inputs.
  Formation: index varies; any other value declared varying by the actual
        caller must remain varying rather than being guessed uniform.

6.4 State that DOES reset per point
-----------------------------------
Clear export seen/required bookkeeping, point-local status/ledger, pending END,
write obligations, point identity and any service request state whose lifetime
is one point. This is small control state, not a 64-word payload clear.

After context reassignment, do not reuse a previously loaded uniform register
unless its association-generation tag matches. A matching program hash is not
a matching parameter set. Check retained code identity separately from retained
prepared-data identity.

6.5 Proof controls
------------------
Run the same legal corpus through slow-clear and no-clear forms with deliberately
different initial RF garbage, alternate associations, and reused contexts.
Compare all outputs, flags and final terminal classification. Poison the scratch
set in the test model; a real source read from stale storage must fail visibly.
The proof must cover the maximum register indices and all adjacent groups.


7. REQUIRED OUTPUTS, UNIFORM OUTPUTS AND RETIREMENT
===================================================

7.1 Strict output contract
--------------------------
Each physical image carries:
  output_count: 1..7 at a production profile binding;
  required_mask: exactly the declared output ordinals, never bus padding;
  source[output_ordinal]: VECTOR_REG or PREPARED_SCALAR plus checked index;
  canonical output ordinal/type correspondence;
  physical image/signature version.

An internal test/compatibility binding may declare a smaller arity than a full
application profile. It remains explicitly such a binding. A proper canonical
Earth application declares its four outputs; Warp declares six; Flow seven.
Two output ordinals may reference one prepared scalar if the logical FPLAN
legitimately produces that result. Capture by output ordinal, not by a unique
register-to-output assumption. The canonical decoder's distinct output-register
rule still applies to canonical bytes; physical aliasing is a different layer.

7.2 Immediate corrective commit on the old host
----------------------------------------------
At the final refresh, gz/fieldp4 has already implemented R101's window mask
at header bits [32 +: OUT_LANES], ST_PARTIAL=0xF3 and out_incomplete_o. Integrate
that work and its controls first. Complete the larger migration from it;
do not recreate the same patch from the older baseline. [S30]

Update every strict producer/fixture to supply its actual output contract. A header extension can use a
versioned field in currently unused header bits, after verifying all consumers.
Do not treat nonzero old unused bits as silently valid on a legacy decoder.

For contiguous legacy physical images:
  required_count <= OUT_LANES;
  required_mask derived from that count, or explicitly checked;
  out_base + required_count <= REGS using a carry-preserving expression.

Replace the any-output success decision with a next-state mask comparison:
  seen_next = seen_before | writes_accepted_this_clock | valid_uniform_seeds;
  complete_outputs = (seen_next & required_mask) == required_mask;

For legacy fixtures whose program has one output, declare one. Do not change
it to pretend the program promised four. For new strict imports, absent
metadata or zero required_mask is a load-time refusal. Do not use zero to mean
"accept whatever happened" in the selected production host.

R101 uses a PHYSICAL WINDOW mask, not an output-ordinal mask. For example,
the new lane reports crater_ring outputs R13,R14,R15,R17: with out_base=13 the
window mask is 0x17, while four required canonical output ordinals have mask
0x0F. A window mask can detect a missing write; it cannot compact window slots
0,1,2,4 into canonical result slots 0,1,2,3. Name those quantities separately
in the generated schema and implement the actual map in the new host.

This patch is not the final sparse/uniform-output implementation. Label that
scope precisely; it is a useful first commit, not a reason to stop the campaign.

7.3 Sparse and uniform exports
------------------------------
For VECTOR_REG output j, a granted write to its physical register updates
export_value[j] and sets seen[j] for that context/lane. If several outputs name
the register, update all matching ordinals. A later write replaces an earlier
value, so the result at retirement is the FINAL value.

For PREPARED_SCALAR output j, validate the scalar's written bit and preparation
identity at association seal, then seed the export when a point/context starts.
The value zero is fully valid if those provenance conditions hold. Do not wait
for a vector write which an all-uniform program will never generate.

All-uniform programs need a defined terminal path: prepare once, seed every
required output and numeric status, and produce one response for each accepted
point. This is exact constant-result execution, not a fake program result.
Do not start a context that can never emit END merely to make a counter move.

7.4 END is not sufficient by itself
------------------------------------
Publish a successful response only after:
  - the point/group has a currently RUNNING identity;
  - a genuine terminal END has been observed for that identity, OR the
    validated UNIFORM_ONLY form has generated its explicit zero-body terminal;
  - all prior ALU and long-op writes have retired;
  - no instruction/service completion can still modify its outputs;
  - every required export is valid for this point;
  - no transport/execution fault has invalidated it;
  - its terminal-result credit is still owned by this request.

Important: a mask alone cannot catch a missing FINAL overwrite of an output
that was already written earlier. The engine's write/drain fence is necessary
in addition to the mask. Verify the current END/release pipeline; repair the
engine if END can precede earlier committed work. A fixed guessed "wait five
clocks after END" is not a fence and fails with service backpressure.

The Earth benchmark already records duplicate/late done and late writes.
Production must own this state in hardware. Observe executor events on EVERY
clock, including loader/preload/refill clocks. [S08]

7.5 Context and response lifetimes differ
-----------------------------------------
Reserve an output slot before accepting a point/group. Once the final result
has been copied to that reserved slot and all internal work is drained, the
execution context can be reused even if the application has not consumed the
response. The reserved slot cannot be reused until response delivery or a
counted cancellation terminal event.

No consumer may hold the physical Field fabric in E_RESP forever. A stalled
client may consume its own finite output credits; it must not hold table/
scalar ownership after all its arithmetic is done. Separate client result
queues or reserved shares of a common ROB provide this isolation.


8. NUMERIC STATUS, FAULTS AND POINT IDENTITY
===========================================

8.1 Result shape
-----------------
Logical result fields, carried directly or through an indexed owned record:
  session_epoch u32;
  association_handle {index,generation} u32;
  request_sequence u32;
  original_point_ordinal u32;
  client_cookie u64;
  output_present_mask u8;
  output_words[7] s32/raw32, canonical output order;
  numeric_sat bool;
  numeric_rcp0 bool;
  numeric_ledger cause bits/counters at the scope the numerical contract requires;
  terminal_code enum;
  source_id u32 for attribution.

client_id is fixed in the association and result-router record. If separately
carried, compare it. The client_cookie refers to the adapter's full point
identity; it is NOT a truncated source_id. Warp's geometry token remains in
its owned join table or is carried whole; a lookup cookie has an index and a
generation with a bounded-outstanding proof.

request_sequence is a dense acceptance order. original_point_ordinal is the
application's index and can be sparse (e.g. covered lattice points). Do not
confuse the two when ordering returns or checking counts.

8.2 Suggested terminal-code meanings
--------------------------------------
Names are proposed; allocate exact numbers in one generated host-protocol enum:
  OK; NO_PROGRAM; STALE_BINDING; BAD_SIGNATURE; BAD_IMAGE; BAD_PREPARATION;
  INCOMPLETE_OUTPUT; UNSUPPORTED_PHYSICAL_OP; EXECUTION_FAULT; CANCELLED;
  NO_CAPACITY; BAD_ORDER; BAD_VERSION; MEMORY_REFUSED.

Every refused accepted transaction receives exactly one terminal event. Unaccepted
ready/valid offers owe no response. Never interpret the old 0xF0--0xF2 namespace
as canonical sat/rcp0. The legacy bridge translates it explicitly.

8.3 Per-point numeric status
----------------------------
Uniform numeric status is attached to the association preparation. Varying
status is collected from that point's actual executed operations. Return their
logical OR, exactly as the canonical interpreter would for one evaluation.
Where a full SatLedger is part of a differential, preserve its specified
per-cause semantics as well; do not replace counts with booleans unnoticed.

The existing vector ALU's l_sadd/l_smul/l_srescale arrays provide an extraction
point BEFORE group reduction. The long-op services need the corresponding
lane/context attribution through their tagged completion path. Prepared RING
already has per-lane reply flags; carry them instead of OR-ing them early.
Expose rcp0 from the shared reciprocal/normalization/ring paths where the
canonical step law reports it. [S09,S10,S11]

A global sticky fabric alarm is useful for diagnosing fabric corruption, but
cannot supply exact per-point numerical status when contexts overlap.
For unrecoverable fabric-internal corruption, fail the active execution domain
and drain/reset it safely; do not guess which innocent point to blame.

8.4 Tail masks
--------------
A quad contains 1..4 live points. Invalid lanes must not create results, advance
logical point counters, change terrain material/dirty state, or contribute flags
to a live lane. Duplicate a live lane as safe physical padding only when no
lane-specific numeric path can contaminate another; otherwise gate lane effects.
A group-level aggregate may OR only LIVE lane statuses.

8.5 Fault is not zero, but adapters may have explicit fallback laws
------------------------------------------------------------------
The host always returns the real terminal classification. An application may
then use its already-declared failure policy: Warp poisons a batch, Flow may
continue without field acceleration under its existing policy, and Stamp must
finish/cancel its traversal without orphaning the shared service. Those policies
belong in the adapter contract and their tests. They are never implemented by
making the host return OK with fabricated zeros.

An unused result lane at an application seam is not an absent result from the
host. R40 deliberately consumes only Flow's returned velocity at PART.UPDATE.
The host must still correctly evaluate and return every declared Field output.


9. PROGRAM, ASSOCIATION AND CONTEXT LIFETIMES
============================================

9.1 Program object
-------------------
One immutable loaded program object records:
  full handle32 (current convention: index in high 24, generation in low 8);
  resource/session epoch;
  canonical hash, canonical full-image length and CRC/fingerprint;
  logical-plan version, host-image version, fabric capability version;
  profile and application signature;
  native/canonical execution form and its validated physical image;
  code/map/table counts and bounds;
  pinned backing image address/extent;
  directory generation, valid/ready state, references, replacement information.

Use full handle/epoch validation. Do not compare only the 24-bit index or only
the content hash. The hash remains useful for content reuse; a share is legal
only if all semantic metadata required by the binding is identical.

9.2 Association object
-----------------------
An association is a program applied to a fixed set of uniform values and an
ordered stream of varying points. It records:
  owner/client, frame identity and full source attribution;
  pinned program object/generation and selected physical form;
  prepared-input values and prepared scalar image;
  preparation serial/generation, not merely the program hash;
  varying-input mask, required input map and actual output contract;
  expected point/work bound and next request/retirement sequence;
  scheduled work class/quantum and cancellation state;
  pinned backing storage plus a ready/validated state.

Two draws using one .zprog with different time/parameters are two associations.
Two different programs using scalar slot 5 do not share the meaning of slot 5.
A preparation can be reused only when its entire immutable-input contract and
version identity match. Immutable content sharing does not imply shared state.

9.3 Execution context
----------------------
An execution context temporarily owns a point group:
  state FREE / PRELOAD / READY / RUNNING / END_PENDING / EXPORT / DRAINING;
  association and code/preparation identities;
  1..LANES live points, their cookies and original ordinals;
  reserved result credits;
  per-point exports/status and generation;
  engine-write/service obligations.

A context index is never sent as a persistent program handle. On reuse, all
control/provenance fields change atomically and old replies must be impossible
or rejected. Existing narrow service tags may remain narrow only under the
proved rule that no context/tag is reused before its entire old transaction
is drained. Do not add a generation field in prose and omit it from the path
where reuse can occur.

9.4 Directory and binding services
----------------------------------
Extend the existing residency implementation rather than maintaining a parallel
"Warp binding cache". Program lookup returns a logical program identity and
ready state; association OPEN acquires a pin and creates a checked association
handle. Every context references that handle/generation.

An evictable programme-directory slot may move/reuse after its references reach
zero. An existing association cannot silently start executing its replacement.
Either retain its pinned backing program or reject its subsequent work as stale
BEFORE execution. Pinned objects cannot be evicted simply because they are LRU.
If no legal victim exists, return bounded NO_CAPACITY/BUSY and let the host
retry; do not overwrite live data or block result draining behind the request.

9.5 Active working data
-----------------------
At any instant, scalar/table caches have:
  active_program_image_identity;
  active_preparation_identity;
  active_generation;
  outstanding-context/service count.

Activation completes only after all required words and independent table counts
are installed. No request sees a partially activated set. On a domain switch,
all old internal work drains, caches invalidate where their data changed, and
new valid tags are committed last. A same-program/different-parameter switch
may retain immutable knot tables but MUST update prepared scalars and any
prepared descriptor caches. Do not infer this from coincidentally equal slots.

9.6 Resource lifetime and replay
--------------------------------
HPS backing is immutable while referenced. A capsule address is not ownership.
Use the project's staging-region/epoch discipline, hold references until all
accepted work and loader reads finish, and record canonical/prepared bytes in
captures. A user/controller resetting the Field domain does not authorize HPS
to recycle the memory before the reset/drain acknowledgment.

Generation wrap is handled by a quiescent epoch reset, not by assuming the
counter never wraps. Reject creation that would alias a still-live generation.


10. TRANSACTIONAL LOADING, BINDING AND THE DOORBELL
==================================================

10.1 Do not silently change the old protocol's meaning
------------------------------------------------------
The current doorbell supports LOAD, COMMIT and LOOKUP. Its final else selects
LOAD for every other op. Its COMMIT can leave the target header invalid until
re-headering, as expected by the existing raw host tests. [S12]

That is not a safe turnkey install transaction for a new consumer, but it is
not to be "repaired" by deleting an invalidation on a guess. Keep the old
protocol's tests as a labeled compatibility surface. New production installs
use the explicit FH2 transaction below and never depend on software guessing
which directory slot will be allocated after the bytes were written.

10.2 Chosen extension of the existing posted mailbox
----------------------------------------------------
Use the currently encodable post_op=3 ONLY AFTER exhaustive decoding is added.
For op 3, post_kind selects:
  0: INSTALL_CAPSULE
  1: BIND_PROGRAM
  2: CONTROL
  3: reserved, answered as BAD_OPERATION

All operands are captured on POST ACCEPTANCE, including plan/frame identity.
The old drain samples cfg_plan_base_i later; do not propagate that live-pin
metadata pattern into FH2. Payloads remain stable under backpressure.
Every FH2 accepted post reserves one completion record. Raw LOAD words inside
the legacy protocol may keep their old acknowledgment policy, distinctly.

INSTALL_CAPSULE payload:
  post_data[63:0]  = HPS source address, little-endian words;
  post_data[95:64] = byte length, positive multiple of 64;
  post_hash       = expected capsule CRC32C using the SAME zeroed-field rule
                    as header.body_crc32c (bytes 12..15 treated as zero);
  post_ticket     = opaque caller ticket;
  post_slot/post_addr = reserved zero (the capsule names its object).
The address stays 64-bit until the real bridge's reachable-range check. A
source above the supported address space is refused, never truncated.

BIND_PROGRAM payload:
  post_data[31:0]  = full canonical program handle32;
  post_data[63:32] = READY program-image handle returned by INSTALL, including
                    its generation (NOT a raw physical cache slot);
  post_data[95:64] = resource epoch;
  post_hash       = expected canonical full-image CRC;
  post_ticket     = caller ticket;
  other FH2 operands reserved zero.
It resolves that exact READY program-image object and verifies its canonical
handle, epoch and complete image identity. Its reply is a checked binding handle
with generation. The canonical hash is taken from the matched object/header,
not reconstructed from a physical slot. Alias/collision mismatches refuse.
Different physical variants of the SAME canonical program can coexist as
different image handles; BIND never chooses the first matching canonical hash.

CONTROL payload:
  post_addr[7:0] = control verb; higher bits zero if the port is wider;
  post_data[31:0]  = association/binding handle;
  post_data[63:32] = session/resource epoch as specified by that verb;
  post_data[95:64] = verb argument;
  post_hash = reserved zero unless the generated verb schema assigns it;
  post_ticket = caller ticket.
Verbs: OPEN_ASSOCIATION, CLOSE_ASSOCIATION, CANCEL_ASSOCIATION, RELEASE_BINDING,
QUERY_OBJECT and EPOCH_BARRIER. OPEN names a READY association capsule handle.
CLOSE means no more points will be offered, not "throw away owed results".
EPOCH_BARRIER completes only under the full drain/lifetime rule.

The present LDADDRW default is 7. FH2 control decoding needs 8 bits only if
using this proposed 8-bit verb field; widen that mailbox field explicitly to
at least 8 through its wrappers. Alternatively use a generated 7-bit verb
schema consistently. Do not write [7:0] onto an unchanged 7-bit port. This
brief selects an 8-bit FH2 control address; legacy loader addressing retains
its separately derived width.

10.3 Install FSM
-----------------
  ACCEPT: reserve completion credit and capture the full request.
  VALIDATE_ENVELOPE: alignment, length, carry-safe range and allowed staging region.
  READ_HEADER: actual HPS bridge transaction and exact received-byte accounting.
  RESERVE_OBJECT: select an unpinned slot; never publish it yet.
  READ_AND_CHECK: receive every required section, validate framing/CRC and
                  physical structural metadata, count each written item.
  SEAL: publish READY only if all section/schema/version checks passed.
  RETURN: reply with the caller's original ticket and full object generation.

On any failure, discard the incomplete staging object, retain prior ready
objects unless explicitly replaced under the transaction, and return a failure.
CRC checked only after bytes have already made a slot executable is too late.

An INSTALL or BIND on a full catalogue must not monopolize the maintenance head
while the only operation that could release capacity is queued behind it.
Return BUSY/NO_CAPACITY promptly or use an independent release/cancel queue.
The result/drain/control progress path always remains available.

10.4 Bridge correctness
------------------------
Use real existing bridge/arbiter request semantics and the current guard.
Match burst alignment, length, byte enables, verdict latency and response shape.
Do not assume a response channel can be backpressured if it has no ready.
Reserve whole-burst receive space before issuing such a read. Early last,
late/extra data, refusal without grant, and orphan responses are separate cases.

A loader retry is bounded and tied to the same immutable object generation.
An infinite retry loop is not a fairness mechanism. Failure leaves no runnable
partial image and never grants an association referring to missing tables.

10.5 Hardware validation vs software decoding
---------------------------------------------
SW.STREAM runs the actual canonical decoder and production lowerer. The FPGA
checks the compact physical envelope, identities, bounds, completeness, field
versions and destination ownership. This is not a second implementation of the
canonical opcode interpreter or its full high-level validator.

A bare software "ok" bit is not a substitute for all bytes arriving, all
output-map fields being present, or the object's identity matching the request.
Trusted software and deterministic capture are the intended trust model; a
CRC is an integrity check, not cryptographic authorization.


11. FROZEN HOST-IMAGE ENVELOPE AND RECORDS
=========================================

This is a PROPOSED physical transport format, separate from the frozen .zprog
format and from any game-facing command record. Generate C++/SV constants and
packer/reader tests from one schema. Do not hand-maintain offsets in three
languages. Validate sizes BEFORE using counts to allocate/read arrays.

11.1 Common 64-byte header
--------------------------
Offset  Bytes  Field
 0      4      magic = ASCII ZFH2 (bytes 5A 46 48 32)
 4      2      image_version = 1
 6      1      object_kind: 0 PROGRAM, 1 ASSOCIATION
 7      1      flags: zero in this revision
 8      4      total_bytes, positive, 64-byte aligned
12      4      body_crc32c: whole image with bytes 12..15 zero
16      2      host_protocol_version = 2
18      2      reserved zero
20      4      canonical_program_hash
24      4      canonical_program_handle32
28      4      resource_epoch
32      4      logical_fplan_abi_version
36      4      execution_fabric_version
40      4      source_id32
44      2      section_count
46      2      header_bytes = 64
48      4      parent_binding_handle (zero for unbound PROGRAM install)
52      4      canonical_full_image_crc32c (all serialized .zprog bytes)
56      4      object_serial (software identity; hardware also assigns generation)
60      4      reserved zero

A PROGRAM's semantic identity is not object_serial alone. The return ticket
belongs to the mailbox and is not duplicated in this header. An ASSOCIATION
must match its pinned parent program across handle, epoch, hash and versions.
canonical_full_image_crc32c covers the EXACT complete serialized .zprog,
including that file's own embedded CRC field. The canonical decoder separately
checks its existing zeroed-field CRC law. This full-image integrity value is
not a replacement canonical program hash and is never the sole dedup key.

11.2 Section directory
-----------------------
section_count entries immediately follow the header, each 16 bytes:
  kind:u16, element_bytes:u16, element_count:u32, offset:u32, byte_length:u32.
The directory is followed by zero padding to a 64-byte boundary. Section bodies
are 64-byte-aligned, bounds checked, nonoverlapping and fully covered by CRC.
byte_length equals checked element_bytes * element_count (widen before multiply).
The last body is zero-padded to total_bytes. All unknown section kinds refuse
in image revision 1. An optional section is a KNOWN section that may be absent,
not permission to ignore an unknown schema. Reserved fields/bits must be zero.
Duplicate singleton sections refuse. Directory entries are sorted by kind; body
padding is outside byte_length and must be zero.

Section-kind assignments for this proposed image revision:
  0x0001 CANONICAL_IMAGE       0x0002 PROGRAM_META
  0x0003 PHYSICAL_UOPS         0x0004 INPUT_MAP
  0x0005 OUTPUT_MAP            0x0006 INIT_PROOF
  0x0007 DEMAND                0x0010..0x0013 TABLE[0..3]
  0x0020 ASSOCIATION_META      0x0021 CANONICAL_INPUTS
  0x0022 PREPARED_SCALARS      0x0023 PRELOAD
  0x0024 LEDGER
These are FH image section kinds, NOT cartridge page/section allocations.

11.3 PROGRAM sections
----------------------
CANONICAL_IMAGE: the validated .zprog, exact bytes. Source-map/name metadata
remains canonical and is not silently stripped before identity comparison.

PROGRAM_META, one 64-byte record:
  profile:u8, binding_signature:u8, execution_form:u8, flags:u8;
  input_count:u8, output_count:u8, required_mask:u8, table_count:u8;
  canonical_instruction_count:u16, physical_uop_count:u16;
  physical_register_count:u16, prepared_scalar_count:u16;
  varying_input_mask:u32, point_preload_mask:u32;
  code_image_crc:u32, maps_crc:u32;
  logical_plan_identity:u32, reserved:u32[7].
Exactly 64 bytes: first 8 + next 8 + next 8 + next 8 + next 4 + final 28.
The final reserved words are not capacity for undocumented policy.
varying_input_mask and point_preload_mask are CANONICAL INPUT ORDINAL masks
(at most fifteen meaningful bits), NOT physical RF register masks. Physical
register coverage is sixty-four bits and belongs to INIT_PROOF below.
execution_form: 0 CANONICAL, 1 PREPARED_REGISTER, 2 UNIFORM_ONLY.
UNIFORM_ONLY requires a checked logical plan with no varying instructions,
all output sources valid prepared scalars, and zero physical uops. It produces
an explicit terminal result per accepted useful point without an engine start.
The other forms include their actual terminating END within physical_uop_count.
An empty arbitrary physical program is NOT the uniform-only optimization.

PHYSICAL_UOPS: 8-byte native words for the current exact register-based format;
registered addresses and immediate interpretation validated against the selected
fabric capability table. A new word layout requires an image version change.

INPUT_MAP: one 8-byte record per canonical input ordinal:
  ordinal:u8, lane_type:u8, source_class:u8, flags:u8,
  physical_register:u16, prepared_slot:u16.
source_class: 0 VARYING_INPUT, 1 UNIFORM_INPUT, 2 UNUSED_PROVEN. Only an actually
unused input may be UNUSED_PROVEN; declared input values still exist in the
canonical association record for validation/capture. The unused address field
in a map row is 0xFFFF, never an implicitly valid register/slot zero. Lane-type
codes come from the existing canonical Field I/O-map registry.

OUTPUT_MAP: one 8-byte record per output ordinal:
  ordinal:u8, lane_type:u8, source_kind:u8, flags:u8,
  source_index:u16, reserved:u16.
source_kind: 0 VECTOR_REG, 1 PREPARED_SCALAR. Reserved/unknown kinds refuse.
Flags include REQUIRED and no undocumented meanings. Required fields agree
with PROGRAM_META.required_mask. Validate the map as a complete ordinal set.

TABLE[t], zero to four separately numbered sections: use the EXISTING canonical
table body bytes: kind:u8, reserved:u8=0, entry_count:u16, then entry_count
{x:s32,y:s32,dy:s32} triples. Directory kind identifies t; element_bytes=1 and
element_count=byte_length=4+12*entry_count. Each t retains its independent
2..64-entry count. A zero-table program invalidates all old active table-valid
bits on activation. Do not include alignment padding in the table's entry count.

INIT_PROOF, one 64-byte record:
  offset  0: proof_version:u16=1, record_bytes:u16=64, flags:u32;
  offset  8: association_register_mask:u64;
  offset 16: point_register_mask:u64;
  offset 24: immutable_register_mask:u64;
  offset 32: initial_defined_mask:u64;
  offset 40: vector_write_mask:u64;
  offset 48: code_image_crc:u32, maps_crc:u32;
  offset 56: expected_association_preload_count:u16, reserved:u16=0;
  offset 60: reserved:u32=0.
flags: bit0 canonical validation, bit1 prepared physical validation; exactly the
one corresponding to execution_form is set, and other bits are zero. A checked
UNIFORM_ONLY image uses bit1 and empty execution-register masks.

Every mask above is indexed by PHYSICAL REGISTER 0..63. initial_defined_mask
must equal association_register_mask | point_register_mask. Immutable registers
are association-owned; they must not overlap vector_write_mask or the changing
point writes. All set bits fit the selected register count. The complete physical
read-before-definition walk is checked by the C++ physical-image validator,
including every actual instruction operand group and contraction. The hardware
checks the bounded masks/counts, installed identity and required accepted preload
writes before start. The preload count is the mask population count, not the
highest register number plus one.

This is not a claim that a CRC mathematically proves the program. Software
verification establishes the physical initialization proof; hardware ensures
that it installed the certified image and did not skip a required preload.
No u32 mask may silently discard physical registers 32..63.

Optional DEMAND: validated per-resource counts for the SELECTED physical form.
A demand vector from the unlowered logical plan is not automatically the count
of added MOVs, padded groups, setup loads or cold service microsteps.

11.4 ASSOCIATION sections
--------------------------
ASSOCIATION_META, one 64-byte record:
  association_serial:u32, frame_id:u32, client_id:u8, profile:u8,
  execution_class:u8, flags:u8, expected_points:u32;
  varying_input_mask:u32, uniform_input_mask:u32;
  preparation_serial:u32, max_group_quantum:u32;
  source_id:u32, numeric_uniform_status:u32;
  client_binding_cookie:u64;
  reserved:u32[4].
Exactly 64 bytes. Uniform numeric status only uses generated defined bits.
Masks are disjoint and cover required used inputs; unused inputs are declared.
expected_points counts useful application points, not physical padding lanes.

CANONICAL_INPUTS: 15 raw s32/u32 words, 60 bytes plus four zero pad bytes.
Uniform positions have their actual values. Varying positions are declared
placeholders whose values are supplied only by actual point traffic; they must
not become default point data in hardware.

PREPARED_SCALARS: exact values from zfield::prepare, with explicit count.
For the native HOT form, the active scalar-bank indices must fit its measured
capacity. An overflowing native preparation selects the exact canonical form
or a separately commissioned larger layout, never a modulo index.

PRELOAD: 8-byte rows {physical_register:u16, flags:u16, value:s32}.
Every required register is supplied exactly as its map demands. Duplicates
with conflicting values refuse; same-value duplicates may be canonicalized
by the packer but must not weaken the installed completeness check.

Optional LEDGER: exact uniform per-cause ledger when required by the profile
instrumentation. Its units/scope must be stated: events executed once during
preparation versus the canonical per-evaluation status represented at each
point are not the same reporting counter.

11.5 Required installation checks
----------------------------------
Check cross-record agreement, not just each record separately:
  header profile/identity vs decoded program;
  association vs pinned program;
  maps vs counts/masks;
  exact required table set vs actually received table set;
  preload destinations vs physical source/use proof;
  output scalar indices vs actually prepared/written scalars;
  code length vs END and physical instruction store capacity;
  desired execution class vs actual supported native operations.

The packer emits a machine-readable manifest and golden capsule bytes. The
hardware loader test receives THOSE bytes over the modeled real bridge, not a
parallel handwritten sequence of raw loader writes assumed to be equivalent.


12. SCHEDULING, BATCHING, FAIRNESS AND ACTIVATION
================================================

12.1 Two levels, not a single round-robin pointer
------------------------------------------------
Association scheduler: chooses a ready client's bounded batch, taking mandatory
reservations, deadlines, activation cost and fairness into account.
Context scheduler: fills several contexts with distinct point groups from the
currently active association and reuses each only after real retirement.

The current executor's issue selection is a lowest-ready scan. Do not assume
it supplies a hard fairness bound. Either prove a bounded result for the selected
constant-size workload or adopt a round-robin/age-based issue selector and
measure the cost. Changes to issue policy need the full engine regressions.

12.2 Activation sequence
-------------------------
  stop new starts for the old association;
  flush incomplete service gather groups when no further matching work can join;
  drain all old instructions/services/writebacks;
  copy finished replies into reserved storage independent of client readiness;
  invalidate changed scalar/table/descriptor caches;
  install the new code where context code tags do not match;
  install changed knot tables with all four independent count/valid fields;
  install preparation and broadcast uniform registers into reusable contexts;
  seed uniform output descriptors/status;
  commit the active association identity;
  enable new point acceptance/start.

There is no overlap between old execution and mutable replacement of its active
prepared data in the selected initial implementation. Loading a new immutable
backing capsule into a disjoint staging object may overlap; writing the live
fabric's tables/scalars may not.

12.3 Useful batching
--------------------
Earth generates up to four adjacent points per row-bounded group. Warp batches
vertices of one immutable draw/association. Flow may gather records from the
same population/program/parameter generation. Stamp walks one stamp's ordered
texels. Do not group points from distinct preparation identities merely because
they use the same opcode or canonical program hash.

A scalar input source must be decoupled from its output with a real finite
capture queue if multiple points are to be outstanding. Changing FAB_LANES or
CTX while retaining a consumer that refuses to present point N+1 until N returns
does not manufacture concurrency. All such queues are included in the resource
sheet and stress tests.

12.4 Frame and fairness certificate
------------------------------------
For each mandatory profile workload, the admission certificate includes:
  maximum ready-to-service wait;
  maximum groups before a scheduling yield;
  activation/reload clocks and memory beats;
  execution/service demand;
  output drain cost;
  other admitted clients' blocking envelopes;
  required frame deadline and the clock assumption.

A sufficient nonpreemptive blocking bound includes the largest permitted batch
of another client PLUS its unavoidable drain/switch cost. The sum of admitted
work/reservations must fit every shared resource, not just a scalar cycle sum.

Choose a bounded quantum from the real workload measurements. Do not invent
"20% per profile" or one universal quantum that was never tested. Store the
selected machine constants/certificates centrally, fail admission or report a
miss rather than silently increasing the quantum forever, and retain the
failing sweep point that establishes why the chosen value is needed.

No scheme earns realtime acceptance until Earth, active Warp, actual Flow/Stamp,
memory contention, and the applicable render/post load have been exercised
together at their required tier. If the exclusive-domain design fails due to
switch cost, quantify that failure and build the bounded two-domain alternative;
do not label the workload unreasonable after previously promising it.

12.5 Result credits and stalled clients
---------------------------------------
Give each live client reserved minimum output capacity and a bounded share of
any common overflow pool. Reserve a slot before accepting the request, not at
END. Export can drain into that slot even if the external client never asserts
ready. That client's new work then stops at its credit limit while other clients
and maintenance progress remain possible.

A shared response bus with one valid bit can still be used physically, but its
storage/arbiter must not be a single head-of-line queue that lets one blocked
client prevent every other client from consuming its result. State the exact
queue organization and derive its M10K/ALM cost.

12.6 Loader fairness
---------------------
The old host gives ld_valid priority over the next client grant. Replace that
unbounded global precedence with explicit maintenance admission. Installation
into staging, activation into live storage, cancellation, and result draining
have different dependencies. A full staging job cannot hold a lock needed by
an active result, and a continuous series of valid load offers cannot starve
mandatory evaluation indefinitely.

-------------------------------

13.5 Bounded working storage, with an honest physical price
-----------------------------------------------------------
Four 32-bit result channels over 1,089 vertices contain 139,392 payload bits.
That is only a BIT lower bound. The probe's four banks x four channels give

256x32 M10K configuration. A straightforward mapping can require 32 M10Ks,
not the old prose's 16--20. Verify actual synthesis when authorized. [S17,S27]

Commission a smaller serial-channel organization as the production candidate:
  four vertex-residue banks;
  one 32-bit word per {local_vertex,channel};
  four channel phases per quad update, skipping unwritten channels;
  height/velocity/nav share the corresponding four saturating add lanes;
  material uses its own selection policy in its channel phase;
  one bounded input skid and explicit backpressure.

Each bank holds roughly 273*4 = 1,092 x32 words. Explicitly splitting a 1,024-word
main region and a bounded tail can target five 256x32 blocks per bank, about
20 M10Ks for the four accumulators. This is a PACKING CANDIDATE, not a fitted
claim; a naive power-of-two depth inference could still allocate more. Count
address mux/control, base/bottom replay storage, tags and buffers separately.

It accepts at most one four-channel quad update per four channel phases, not
one per clock. Price that actual service rate in the full Earth slice. If it
misses the workload, use the fully parallel candidate and report its real cost;
do not use the smaller number with the larger version's throughput.

Keep one patch working set initially. More patch buffers require an observed

16. ABORT, RESET, RECOVERY AND BACKPRESSURE
===========================================

16.1 Ready/valid ownership
--------------------------
Every offer remains stable until transfer or an explicitly defined cancellation
handshake. A request cannot change operands because another context became
available. A response cannot disappear because its client lowered valid on a
different channel. Keep registered boundaries across the scheduler/loader/core
and result router; no multi-island combinational ready chain.

16.2 Cancel without orphaning shared work
------------------------------------------
Cancel marks the association as no-new-work, drains or discards already accepted
results with exact accounting, and releases resources only after internal
retirement. It does not immediately mark contexts free. A later result from
an old context must never update a new association with the same index.

Queued but unstarted requests receive CANCELLED; started requests either finish
and are discarded/count-cancelled or use a proven context abort. The current
engine has no magic per-context abort guarantee simply because the host needs
one. For unrecoverable internal failure, stop admission, quarantine all active
contexts in the domain and perform a coordinated fabric reset/epoch barrier.
Do not reuse state until that barrier completes.

16.3 Reset protocol
---------------------
Reset clears small valid/control state, not large payload memories. New-session
validity prevents reads of old bytes. External memory responses already issued
must be drained/discarded by their ownership tag or prevented by the enclosing
bridge reset protocol. Do not assume resetting the local counter cancels a
transaction elsewhere in the system.

Clear/rebuild the active code/table/scalar-valid tags. Previously READY backing
objects may be reinstalled or reacquired under the new session epoch; they do
not remain implicitly runnable because their RAM still contains bits.

16.4 Watchdogs
----------------
Separate:
  active arithmetic progress;
  waiting for accepted internal service work;
  waiting for external memory;
  waiting for result/ingress credits;
  waiting for an application's ready.

A counter is useful even when no valid cycle bound is known. A destructive
watchdog timeout is allowed only with the stated assumptions that make its
bound valid. Do not abort a correct job simply because an external consumer
legally holds ready low. Result credit isolation should make that hold unable
to block already accepted arithmetic.

An engine hard hang after accepted bounded internal work must become a visible
fault with a safe reset/recovery path, not infinite silence. Test the next good
association after each injected failure; surviving the bad job alone is not
proof that the shared fabric recovered.

16.5 No unbounded maintenance dependency cycle
------------------------------------------------
Specifically test this graph:
  pending install wants a free program/association slot;
  a live job wants result space;
  the application wants a completion before releasing its binding;
  a release/cancel command is behind the blocked install.

Break it by reserved completion credits, independent progress for cancellation/
release and bounded BUSY refusals. Do not solve it with a larger FIFO alone.


17. RESOURCE ACCOUNTING AND TIMING BOUNDARIES
=============================================

17.1 A resource sheet, not arbitrary department budgets
-------------------------------------------------------
For each selected configuration report:
  program/association descriptor entries and actual row widths;
  active code words and whether replicated per context;
  RF contexts x registers x lanes x read replicas/banks;
  active table store and table-count/valid metadata;
  active scalar/preparation storage;
  export registers/RAM, input capture, result queues and credits;
  per-client identity/ordering buffers;
  Earth working accumulator and substrate/drain buffering;
  additional shared opcode service/control resources;
  HPS fetch/arbiter/guard integration delta;
  unchanged shared arithmetic explicitly counted once.

No fixed ALM ceiling is asserted by this brief. Estimate ranges, identify the
unmeasured terms and price them at the authorized physical fit. If a selected
microarchitecture cannot meet its allowed total, redesign it; do not reinterpret
"mandatory" to remove a function or erase its data from a fit harness.

17.2 Memory shapes must include port topology
---------------------------------------------
The current RF has four residue banks and three read copies. At 8 contexts,
64 registers and four lanes, each of the 12 memories is 128 x128 bits. A direct
simple-dual-port M10K implementation can need four width slices per memory,
about 48 M10Ks, although the logical bit count alone suggests far fewer.
At 32 contexts that row depth becomes 512 and the direct width/depth price
can double. These are STRUCTURAL EXPECTATIONS, not measured results. [S18,S27]

Consequently increasing CTX and LANES cannot be sold as a free way to fix the
front. Measure the 8/16/32-context and scalar/quad frontier with the SAME actual
workload. The old quad benchmark's chosen configuration remains an evidence
point; its throughput is not inherited by an eight-context scalar composition.

The Earth accumulator's 273-word tail problem is described in 13.5. The same
rule applies everywhere: round width/depth to a legal physical mode per bank,
include replication, byte-enable/read-during-write requirements and valid bits,
then verify inference. M10K is not a bottomless ALM replacement currency.

17.3 Intended savings and additions
------------------------------------
Expected architectural benefits, NOT fitted savings claims:
  remove the per-point 64-word clear;
  replace repeated uniform loading with association/context activation;
  fill existing vector lanes with useful distinct work;
  amortize code/table setup and directory acquisition;
  reuse shared arithmetic instead of private profile engines;
  reuse the existing lowerer/driver knowledge rather than duplicate it.

Expected additions that must be charged:
  descriptors and generations, stricter output maps/validity;
  credited result routing and adapter identity queues;
  real activation/association scheduler;
  hardware loader and checked image metadata;
  full canonical register/code capacity;
  per-point status propagation;
  missing shared exact-op routes;
  the bounded Earth working set.

A faster correct machine can cost more than the incomplete scalar front.
That is not a surprising regression to hide. Report both the functional
coverage difference and the area delta.

17.4 Timing rules
------------------
Register request arbitration, descriptor reads, RF preload selection and output
routing at explicit boundaries. Use RAM-backed indexed state rather than wide
all-entry combinational compares when the transaction rate permits a scan.
A request/response token lookup may take several clocks; it must not create a
long combinational path across memory, scheduler, executor and consumer.

Do not widen multiplier operands as a side effect of writing address math with
large signed temporaries. Use widened ADDRESSES for overflow checking, and
correctly bounded arithmetic operands for computation. The host itself should
not acquire new DSP-heavy numerical datapaths beyond the explicitly added
shared canonical services.

Check inferred RAM lists, hierarchical logic/DSP ownership, critical path
families and routing/logic split when the authorized complete fit is run.
One attractive leaf Fmax or a clean Verilator run proves none of those.

21.8 Formal and assertion obligations
---------------------------------------
Use formal verification on bounded control subproblems where tractable, and
explicit simulations/structural proofs where whole arithmetic is not tractable.
Do not claim an SMT proof for a test that only ran a few deterministic cycles.

Prove or assert, with an independent observation point:
  a) Accepted work <= reserved terminal capacity; no credited queue overflows.
  b) A context is never reused before its write/service obligations reach zero.
  c) A READY object implies every mandatory section and map was installed.
  d) An active association's scalar/table namespace cannot be written by another.
  e) No inactive/padded point can publish an application output or accumulator write.
  f) Every success has a complete required mask and final-value retirement fence.
  g) No rejected/partial object can become a binding target.
  h) Payload/identity stable while valid and not ready, at every registered seam.
  i) Reset/epoch separation prevents old accepted replies satisfying new work.
  j) No subsystem silently relies on a ready signal that the real port lacks.

For liveness properties state the environment assumptions: response eventuality,
bounded memory refusal, and downstream credit availability as appropriate.
"Eventually completes under arbitrary permanently blocked memory" is not a
meaningful promise. The failure must still be bounded/attributed under the
explicit timeout/abort contract without corrupting the next session.

21.9 Mandatory mutant classes
-------------------------------
At least these planted defects must be caught by actual semantic tests:
  required mask tested as ANY instead of ALL;
  final overwrite dropped after an earlier output already set seen;
  uniform output seeded from the previous preparation;
  scalar tag stripped and interpreted as a vector register;
  op 3 aliased to LOAD;
  raw persistent slot reused after eviction;
  mixed-table association switched before the old service drains;
  canonical RCP0 lost or treated as execution failure;
  SIMD flags ORed back into every point;
  padded lane writes or counts enabled;
  Earth field completion order substituted for command order;
  273 UPDATE groups used in place of 297;
  point N+1's cookie paired with point N's result;
  a pulse completion lost while another context is preloaded;
  an unknown physical opcode classified before its service exists;
  a partial image published READY before CRC/completeness verification.

Do not write a test whose only expected behavior is that the buggy design
returns a wrong answer. Assert the correct behavior; the planted mutant must
make that assertion fail. A coverage counter that still balances under a wrong
answer is not a substitute for comparing the answer.


22. COMPLETION RULES AND REQUIRED EVIDENCE
==========================================

22.1 Four independent conclusions
----------------------------------
SEMANTICALLY CONFORMANT means:
  valid canonical programs produce the correct declared outputs and numeric
  status through the selected physical form, including full profile signatures,
  uniform/sparse outputs, maximum canonical bounds, and actual cold operations.
  No claimed operation relies on a mock or on an unimplemented service route.

COMPOSED means:
  the selected console accepts the real producer's captured command/resource
  data, loads and binds it through the actual host path, runs useful points,
  and the real consumer uses the results. Correctly disconnected intermediates
  remain labeled as such. A testbench may model HPS and physical memory; it
  may not stand in for a missing FIELD loader, result producer or application.

WORKLOAD-QUALIFIED means:
  the complete production-transport scenarios meet the declared deadlines,
  including switching/preload/activation, real masks/ordering and competing
  clients. State the exact program set, content tier and clock assumption.
  A scalar correctness pass does not qualify a vector throughput promise.

PHYSICALLY QUALIFIED means:
  the actual selected hierarchy with its real parameters has a provenance-pinned
  synthesis/fit/timing result on the relevant device. An isolated leaf, a flat
  census, a parser pass, and a complete board fit answer different questions.
  No result from one is relabeled as another.

These four statuses are published separately even when the headline is only
one line. If the implementation is correct but exceeds a resource/deadline,
say exactly that and retain its useful correctness evidence. Do not pretend
that a failed physical gate retroactively proves the numerical law impossible.

22.2 What closes the shared-FIELD commission
---------------------------------------------
All the following must be true before reporting this commission DONE:
  - the real production packer and loader are used, not only described;
  - the selected host carries full signatures and required output metadata;
  - canonical and prepared physical forms have honest operation coverage;
  - association, program-image, context and result lifetimes are enforced;
  - uniform data and all four table identities are safe across switches;
  - no-clear execution has a real validation proof and differential controls;

22.4 Read-only architecture-review limitations
------------------------------------------------
This document is based on the listed committed files, not access to the user's
uncommitted worktrees or live agents. It does not establish that a concurrent
worker has or has not started a repair since the pinned snapshot. Refresh on

The architecture intentionally makes several NEW choices: strict output
metadata; versioned host capsules and transactional publication; distinct
association/context identities; exclusive active prepared data with several
contexts; canonical exact support on the shared fabric; field-major Earth
composition with one working-set reducer. They require implementation and
measurement. They are not claimed as already fitted, universally optimal,
or a guarantee that the complete Zhaozhou fits the target FPGA.

What this document does provide is an explicit implementation decision for the

APPENDIX B -- NUMERICAL SANITY CHECKS AND INVARIANTS
===================================================

These calculations check this brief's own accounting. They are not Quartus
or runtime results.

B1. Canonical lane counts, by fields:
  Warp = 3 position + 3 normal + 4 attributes + 1 time + 4 parameters = 15.
  Formation = 1 index + 1 time + 2 rotation + 2 translation + 6 params = 12.
  Maximum listed input/output transport = 15 words / 7 words.

B2. Profile limits are not the physical store size:
  Warp canonical ceiling 48, global canonical ceiling 64.
  A 32-word store cannot hold all legal Warp programs.
  A physical native plan may add packing operations; count the final image.

B3. Earth traversal:
  vertices = 33*33 = 1089.
  row-bounded UPDATE quads = 33*ceil(33/4) = 297.
  aligned INIT or DRAIN quads = ceil(1089/4) = 273.
  Difference = 24 UPDATE groups/association, 3072 over 128 associations.
  Logical vertices remain 1089; padded physical lanes are not logical work.

B4. Old per-point transport illustration:
  old lower bound from clear and input walk at REGS32/IN13 is 46 clocks,
  and the reported full FSM expression is 49 + T_run before further stalls.
  Widening to IN15 changes that expression to 51 + T_run.
  Removing clear/preload cost alone does not remove actual instruction,
  activation, contention and consumer costs; no three-clock FULL evaluation
  is promised by a three-clock transport estimate.

B5. Rejected complete intermediate matrix:
  16 fields * 1089 vertices * 4 output words * 32 bits = 2,230,272 bits.
  This excludes its ports/replicas, metadata and validity. It is not the chosen
  Earth transpose solution.

B6. Patch working-set baseline:
  4 vertex banks * 4 channels * 273 rows * 32 bits = 139,776 payload bits.
  Sixteen independent 273x32 memories exceed the 256-row wide-word mode;
  a straightforward mapping can cost two M10Ks per array, i.e. 32 blocks.
  Candidate serialization: four banks each 1092x32, explicitly split into
  1024x32 + 68x32, has a structural 4+1 blocks per bank, i.e. 20 blocks,
  if the intended modes and controls actually infer. Extra state still counts.

B7. Example register file at CTX8/REGS64/LANES4:
  4 banks * 3 copies = 12 physical logical arrays.
  depth per array = 8*(64/4) = 128; width = 4*32 = 128.
  A direct width partition against 256x32/40 modes is roughly four blocks per
  array, 48 M10Ks. A denser transformed layout is a different implementation
  to measure, not free packing. At CTX32 depth becomes 512 and may double it.

B8. Host-image fixed records:
  common header = 64 bytes; each section directory entry = 16 bytes.
  PROGRAM_META = 64 bytes; ASSOCIATION_META = 64 bytes.
  INPUT_MAP and OUTPUT_MAP rows = 8 bytes; PRELOAD rows = 8 bytes.
  INIT_PROOF = 64 bytes, with five physical-register u64 masks.
  canonical table section payload = 4 + 12*entry_count bytes.
  max input record = 15*4 = 60 bytes plus 4 explicit padding bytes.
  Every range/product is widened before bounds checking.

B9. Output completion:
  success requires required_mask != 0 AND
    (seen_next & required_mask) == required_mask AND
    terminal_for_this_identity AND no_outstanding_modifying_write AND
    no_execution_fault AND owned_result_credit.
  A previously set seen bit does not prove a later overwrite has retired.
  UNIFORM_ONLY uses a validated explicit terminal without pretending to run END
  on a nonexistent physical program.

B10. Lifetime separation:
  Canonical resource identity != physical program-image identity.
  Program-image identity != association/preparation identity.
  Association identity != execution context index.
  Execution completion != application response consumption.
  Content hash equality != complete semantic object equality.
  A CRC is not proof of cryptographic identity or authorization.

B11. Claims permitted at this document's creation:
  architectural choices, source-grounded defects/mismatches, an implementation
  sequence, required tests and structural arithmetic.
  Claims NOT permitted: tests executed here, fitted ALMs/DSP/M10K, achieved Fmax,
  deadline compliance, independent verification of the user's uncommitted tree,
  or certainty that the final console fits.
