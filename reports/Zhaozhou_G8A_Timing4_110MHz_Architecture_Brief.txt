ZHAOZHOU G8A TIMING4: COMFORTABLE 100 MHz CLOSURE
Architecture and implementation brief for the hardware agent
Prepared 15 September 2026
Final reconciliation includes plan update 8579e7b, published during this review.

Engineering objective: retain the measured 30-DSP architecture, preserve exact
rendering and lifetime semantics, and produce a connected implementation with
real timing margin above 100 MHz. Proposed comfort target: at least 110 MHz;
design towards 115 MHz where this does not create a disproportionate area cost.

This is an implementation proposal, not a timing receipt. None of the proposed
changes has been synthesized, placed, routed, or run through RTL simulation as
part of this brief. The accompanying executed checks cover arithmetic and small
abstract transport models. Their scope is stated explicitly in Section 23.

===============================================================================
0. EXECUTIVE DIRECTION
===============================================================================

Do not solve Timing3's remaining setup debt by restoring the old multipliers,
relaxing the clock, adding false paths, clearing ownership on faults, or fitting
one tiny correction while other known negative cones remain.

The useful unit of work is one coherent Timing4 batch:

  A. Capture the combiner's READ_LATE source bundle before operand selection.
     Replace long signed product finishing with exact short carry arithmetic.
     Protect its eight-context throughput with narrowly scoped queue forwarding,
     rather than assuming another stage is free.

  B. Isolate the owner admission event from the large per-slot initialization
     fanout. Preserve the external acceptance edge and immediately reserved
     ownership. Do not delay the canonical lifetime-fault admission block.

  C. First use the newly published latency-preserving BIL2 retime: register the
     vertical product/base in the existing B2 slot and finish from those held
     registers. A four-slot version, widened occupancy and complete/refill repair
     are explicit fallbacks only if the short output cone still fails.

  D. Simplify the divider's negative-magnitude preparation algebraically, with
     no extra divider cycle or DSP. Capture attribute validity verdicts beside
     the existing join payload, without another wide payload stage.

  E. Register reciprocal result identity before the UVW lookup. Capture the
     descriptor trust verdict at an existing payload boundary. Stage AUX fault
     facts and use a shared subtract/borrow result in its divider. Prefer these
     narrow cuts before adding full payload stages.

  F. Remove the fit wrapper's combinational fault/ready auto-clear feedback with
     a held recoverable-clear request. Where deep quiet fanout remains, use the
     conservative FULL-quiet certificate with a complete pending-work inventory.

  G. Inventory the nonnegative paths below the intended margin. The existing
     497-negative-path census is not a complete inventory for 110 MHz closure.

The highest-risk work is ownership event retiming, not the arithmetic. Give it a
separate review and a complete early-event/late-event priority matrix. The
lowest-risk high-value work is the exact finish arithmetic, divider identity,
and two registered attribute verdict bits.

This is still G8A. It is not a redesign of the whole machine, a new texture
architecture, an R1 arithmetic campaign, or permission to adopt Packet H or the
production shell prematurely.

2. DEFINE COMFORTABLE CLOSURE BEFORE IMPLEMENTING IT
===============================================================================

The operating requirement remains 100 MHz. A measurement that just touches
100.01 MHz is not the requested comfortable result.

Proposed acceptance categories:

  RED:
    Any required setup/hold or other mandatory timing check fails at 100 MHz,
    or any existing functional, ownership or RAM gate fails.

  100 MHz GREEN, LIMITED MARGIN:
    The canonical 100 MHz constraints pass, but the design does not demonstrate
    the additional headroom described below. This is useful progress; report it
    honestly rather than calling it comfortable.

  COMFORTABLE G8A:
    Canonical 100 MHz checks pass and the same physical design also passes the
    explicitly reported 110 MHz clock analysis at all applicable timing corners,
    with zero setup/hold TNS and no new timing exclusions. Restricted Fmax is at
    least 110 MHz on the relevant clock, but the Fmax table alone is not signoff.

  DESIGN AIM:
    Develop principal data stages towards approximately 115 MHz capability.
    This is an engineering target, not a forecast that the first fit will reach it.

For an ordinary same-clock path whose other terms remain unchanged:

  100 MHz period = 10.000000 ns
  110 MHz period =  9.090909 ns
  115 MHz period =  8.695652 ns

Therefore +0.909091 ns slack at 100 MHz corresponds approximately to zero slack
at 110 MHz for that particular path. Use actual TimeQuest analysis, not this
arithmetic alone, for final acceptance: uncertainty, pulse-width requirements,
clock relationships, I/O requirements and corner-specific limits still matter.

The current worst path needs about 1.903 ns of improvement to reach 110 MHz under
unchanged clock terms, not merely the 0.994 ns needed to scrape through 100 MHz.

Maintain the canonical 100 MHz experiment for comparability. A 110 MHz analysis
of the retained post-fit database can be a separately named margin report; it
need not be a second placement run. Do not overwrite the 100 MHz constraints or
receipt and pretend the source experiment was unchanged.

At the whole-machine composition, the clock tree and neighbours change. G8A
comfort is a useful local reserve, not a guarantee that G8C will inherit it.

4. CLOCK SKEW IS A BUDGET TERM, NOT A FALSE-PATH EXCUSE
===============================================================================

The worst path [S01, S02] starts at the sample-result bank's inferred RAM control
register and ends at material-combiner o_a0[3]. It has:

  Data delay        9.083 ns
  Clock skew       -1.731 ns
  Setup slack      -0.994 ns at a 10 ns relationship

Calling this a 10.994 ns combinational path is wrong. The effective timing
requirement includes skew and setup terms. A data path below 10 ns can fail badly
when the capture edge arrives unfavourably.

Under the same terms, the data budget at 110 MHz is approximately 7.179 ns. This
is why merely trimming one small mux is not the primary solution. Split the RAM
read from recipe-dependent operand selection.

Inspect actual clock routing to the RAM, DSP and fabric endpoints. Check the
fitted global-clock resources and full launch/capture clock paths. The absence
of an explicit GLOBAL_SIGNAL assignment is not proof that Quartus routed clk as
ordinary data; automatic promotion exists. Conversely, do not assume a clock is
well routed merely because it is named clk.

Do not introduce a board PLL into this characterization wrapper, change reset
semantics, disable uncertainty, or create false/multicycle exceptions to hide a
real synchronous dependency. A node named PORT_B_WRITE_ENABLE_REG is a vendor
mapping label; it does not by itself prove an illegal read/write collision.

First preserve the existing device, seed, source boundary and effort settings.
A separately justified clock-network experiment is permissible only after the
actual clock report identifies the problem and its provenance is retained.

5. NON-NEGOTIABLE BEHAVIOURAL CONTRACTS
===============================================================================

Preserve these contracts through every timing change:

  - One lifecycle owner, 64 owner slots, complete slot/generation identity.
  - Existing generation wrap/fence rules, not an invented drain-every-64 policy.
  - Owner credit reserved on the real admission edge; returned only by the
    existing release protocol.
  - Required, issued, claimed and committed remain distinct events.
  - Publish after actual payload write; read only when ownership permits it.
  - No use of old-data RAM collisions as an implicit forwarding mechanism.
  - All four filter lanes and the measured 30-DSP implementation remain present.
  - Material recipe counts, phases, arithmetic, status, alpha and sample-0 index
    remain exact. AUX is still a separate typed plane, never sample 2.
  - Count-zero/no-AUX material phases issue no source-plane request.
  - Ready/valid offers hold identity and payload under backpressure.
  - Reset clears valid/control, not wide payload RAMs.
  - Recoverable frame errors remain distinct from reset-only structural faults.
  - Existing output/cancellation laws are not replaced by simply suppressing
    valid and abandoning an already accepted owner.
  - Quiet covers every pending transaction, including newly inserted stages.
  - Throughput is checked at leaf, class-service, phase-engine and connected
    workload boundaries. II=1 in a leaf is not proof of unchanged system rate.

The existing read-only source bank and registered one-hot write-enable structure
is a protection against historical RAM-to-flop disasters [S13]. Keep it. A
clock-enable expression around a payload array can change inference materially.

===============================================================================
6. WORK PACKAGE M1: REGISTER THE COMBINER SOURCE BUNDLE
===============================================================================

6.1 Actual baseline, rather than a generic pipeline drawing

The selected READ_LATE combiner [S03] has eight contexts and an internal pipeline
with Q, R, D, O, M and WB responsibilities. Its phase-valid registers shift every
clock. There is no internal ready/valid stall at every phase stage. Credits and
context ownership make the writes safe; the completion output is elastic.

Q chooses a continuation before new work and captures context/phase and slot.
R performs synchronous payload, scratch and source-plane reads.
D aligns their outputs.
O performs required-source status reduction, channel selection, signed-difference
preparation and recipe-dependent operand selection.
M registers exactly two products.
WB captures the finished row; its following edge writes scratch/completion RAM.

The failing path exists because READ_LATE aliases the live source-plane outputs
directly into the O-stage logic. Context alignment alone did not register the
source payload ahead of the operand-selection cone.

6.2 Proposed boundary (called S in the newest repository plan)

Insert one fixed-rate source-capture stage P between the aligned RAM output and
O. P captures everything needed to select the operands of exactly one phase.
All P fields are written on the same valid transfer and remain associated with
one context and phase. Do not capture payload today and read its phase from a
live queue tomorrow.

A compact selected-mode bundle is:

  sample 0: full result48                                   48 bits
  sample 1: status8 plus RGBA32, no unused raw index          40 bits
  sample 2: status8 plus RGBA32, no unused raw index          40 bits
  AUX: status8 only                                           8 bits
  material row including admission-frozen refusal            47 bits
  scratch row                                               33 bits
  context index                                               3 bits at NCTX=8
  phase                                                       2 bits
  valid                                                       1 bit
                                                         ------------
  illustrative total                                       222 bits

This is one in-flight phase register, not another 64-owner plane copy or FIFO.
Derive context width from NCTX, not a literal three in reusable RTL.

Do not move source selection/status reduction in front of P simply to reduce its
width further. That recreates the RAM-output-to-selection path. Only discard
fields proven never consumed by the material law. Keep copy-mode admission data
and READ_LATE data on equivalent documented phase boundaries for differential
verification.

In count-zero/no-AUX cases P may carry irrelevant source wires, but they cannot
influence the result and no source read request may be emitted. Refusal behaviour
and required-source status masking remain exactly as before.

P is a pipeline stage, not an independently stalled cache. If the phase pipeline
is converted to elasticity, every upstream store-read reservation and consumer
must be redesigned consistently. That larger rewrite is not the default plan.

6.3 RAM and ownership checks

Every phase source request continues to use the captured owner slot. P does not
release the owner. Final-result production, ownership claim and public release
remain downstream, after the last required read and use of the stored payload.
Retain the source-before-final and release-not-under-reader assertions, extending
their in-flight lifetime to P.

All new valid bits appear in idle_o. Do not infer idle from a phase counter alone;
a held completion, prefetched response or newly captured source can still exist
when a counter happens to match another counter.

7. WORK PACKAGE M2: EXACT SHORT PRODUCT FINISHING
===============================================================================

The current finish_lane performs wide signed negate, bias, shift, base addition
and clipping before scratch-row assembly [S03]. Shortening it is preferable to
immediately adding yet another phase stage behind M.

Let p be the raw unsigned 16-bit product, h=p[15:8], l=p[7:0], and a the 8-bit
LERP base. All formulas below preserve the current function even for arbitrary
raw 16-bit p, not merely products of two legal byte operands.

7.1 OP_UNIT

Current result:
  ((p + 128) >> 8) modulo 256

Equivalent:
  (h + (l >= 128)) modulo 256

Use an explicitly sized sum and retain the original low-eight-bit behaviour.
The full arbitrary-product domain includes values outside ordinary byte-product
reachability; this formulation still agrees with the existing function there.

7.2 OP_MOD2

Current result:
  r = (p + 64) >> 7
  output = min(r, 255)
  saturation witness = (r > 255)

Equivalent saturation condition:
  p >= 32704

If not saturated:
  output = (p >> 7) + ((p & 127) >= 64)

The threshold is 32704, not 32640, 32768, or an inferred signed comparison.
Preserve the saturation witness separately from the clamped output byte. R9's
one-rounding law remains one-rounding; do not unit-round and then double.

7.3 Positive LERP contribution

Current:
  clamp_0_255(a + floor((p + 128) / 256))

Build one explicitly unsigned nine-bit sum:
  u9 = zext9(a) + zext9(h) + (l >= 128)
  result = u9[8] ? 255 : u9[7:0]

The largest sum is 511, so the ninth bit is sufficient.

7.4 Negative LERP contribution

Current:
  clamp_0_255(a + floor((-p + 128) / 256))

Since p=256*h+l:
  floor((-p+128)/256) = -h - (l > 128)

Therefore compute:
  u9 = zext9(a) + zext9(bitwise_not_8(h)) + (l <= 128)
  result = u9[8] ? u9[7:0] : 0

Here bit 8 is the no-borrow witness of the unsigned subtraction. The complement
must be eight bits before zero extension. The thresholds are asymmetric:
positive uses l>=128; negative borrow uses l>128. This is how the original
negative-half rounding towards positive infinity is preserved.

Do not implement negative LERP as a - round(p/256). That disagrees at real ties.
Do not shift a signed value after silently converting it to unsigned.

7.5 Integration

Keep the O->M multiplication sites, product counts and metadata unchanged.
Implement the shorter finish primitives under the existing recipe controller.
Feed the current scratch construction and WB stage. Both saturation counters and
row construction must use the same exact newly finished values; otherwise the
visible colour can pass while instrumentation disagrees.

Use a balanced predecoded recipe/phase selection where useful, but do not create
eight parallel full arithmetic engines. Do not add a small ROM for this byte
arithmetic merely because a table is possible. A short carry chain is the first
candidate; mapped area and delay decide whether the mapper already optimized an
expression equivalently.

The accompanying host check exhaustively compared all 65,536 raw products for
UNIT and MOD2, and all 33,554,432 product/base/sign combinations for LERP. Those
checks passed. This establishes arithmetic equivalence in the checked model;
it does not establish RTL sizing, synthesized structure or clock frequency.

7.6 Separate finish register and reconciliation with the latest plan

The new repository plan proposes M->F->WB [S16]. The exact short arithmetic in
this brief is compatible with that plan: it can make F cheaper and faster. If F
is already implemented and validated, retain it rather than undoing work to match
this document's illustrative one-added-stage calendar. Before implementing F from
scratch, inspect whether the short finish can meet the margin with the current
WB boundary. If it cannot, introduce F between M and row assembly. Carry finished lane bytes and
witnesses, context, phase, recipe, final/bypass, saved scratch/direct data, alpha,
status and index as one aligned bundle.

Move counters according to their specified event meaning, not whichever stage is
convenient. A finished product and a completed phase are still different events.
An extra F stage changes context recurrence again. It cannot be merged without
the throughput analysis in the next section; it is not automatically included
in the preferred one-source-stage portfolio.

8. WORK PACKAGE M3: DO NOT LOSE EIGHT-CONTEXT THROUGHPUT
===============================================================================

8.1 The trap

One accepted phase per clock does not mean one completed job per clock. There are
only eight contexts; a context remains occupied until its output is consumed.
Multi-phase recipes also wait for scratch write and continuation rescheduling.
Adding two registers can increase those recurrences even when each stage itself
has II=1.

Retain NCTX=8 as the first implementation. Do not double every context store and
queue to 16 before showing that a narrower scheduling fix is insufficient.

8.2 Baseline edge calendar

Use E0 as the edge on which a phase is launched into R. A zero-stall baseline
phase has this illustrative calendar, directly following the existing registered
assignments:

  E0: Q launch, capture r context/phase/slot
  E1: R->D and synchronous store outputs
  E2: D->O operand capture
  E3: O->M product capture
  E4: M->WB finished row capture
  E5: actual scratch/completion write and queue insertion
  E6: earliest next Q from a newly queued continuation, or DONE read issue
  E7: completion read arrival can fill output
  E8: earliest public completion handshake

Adding P shifts the write to E6. Without further work, continuation reissue moves
to E7 and final handshake to E9. Repeating that penalty per phase is avoidable.

8.3 Narrow WB-to-Q continuation forwarding

Candidate selection order:
  1. An existing queued continuation, preserving its priority.
  2. The current registered WB nonfinal phase, if not already queued.
  3. New work.

When case 2 is selected, the WB phase writes scratch on that edge and launches
its next-phase context/phase record into R. Suppress that continuation's queue
insertion; never enqueue and bypass the same event.

The next phase's actual scratch read occurs on the FOLLOWING edge. It therefore
observes the completed write without depending on same-edge old-data behaviour.
The bypass carries the registered WB context and incremented phase. It must not
reach backwards into unregistered finish arithmetic.

If a queued continuation wins, the WB continuation is enqueued normally. A
simultaneous old queue pop and new queue push remains legal. Do not overwrite a
queue head just because the queue was empty in a different phase of the cycle.

Keep phases_issued tied to actual Q launch and phases_completed tied to actual
scratch/completion write. There is one of each for each physical phase.

8.4 Narrow WB-final-to-completion-read forwarding

When DONE is empty and the existing two-slot completion response reservation has
room, the current WB-final record can launch directly into the completion-read
response pipeline instead of first occupying DONE.

Still perform the real completion RAM write. Read the immutable tag for that
context on this edge. Register a one-bit forwarded-response selection, the exact
49-bit WB row, and the context beside the read-in-flight state. On the response
arrival edge select the explicitly forwarded row instead of cmp_rd.

The RAM's simultaneous old-data result is irrelevant on this route; it must not
be used. When no forwarding occurs, the original completion RAM response remains
the source. Old queued completions retain priority over a new WB-final record.

Suppress DONE insertion only for the exact record successfully bypassed into a
reserved response slot. If credit is unavailable, enqueue normally. The existing
out_full/prefetch_full/read_in_flight reservation law counts this forwarded
arrival as one in-flight response, not as an extra invisible slot.

Public output stability is unchanged. A bypass is not permission to overwrite a
stalled output. Free a context only on its output handshake as before.

8.5 Why these two bypasses are useful

With one added P stage and the two empty-queue bypasses:
  next continuation Q can again occur every six clocks;
  earliest one-phase output handshake can again be E8 from initial Q.

The latest repository plan proposes both S and F, with an approximately eight-
clock continuation recurrence [S16]. Eight contexts can cover an eight-clock
recurrence in an ideal phase schedule, but this does NOT by itself prove full
job throughput: completed contexts still wait for completion delivery and free-
queue visibility. Test one-phase streams and public-output stalls as well as
multi-phase recurrence. The bypass calendars below describe the one-added-source-
stage option; an S+F option needs its own explicit calendar and rate evidence.

The accompanying model verifies the one-added-source-stage abstract calendars
for one-, two- and three-phase recipes. It does not simulate actual arbitration, RAM hazards or
backpressure. This is a reason to implement and test the candidate, not a claim
that all throughput regressions have already been disproved.

Required RTL comparisons include saturated streams, alternating recipes,
NCTX-full admission, mixed continued/new work, DONE backlog, output stalls,
completion/refill coincidence and fast error/count-zero jobs. Record accepted
jobs, completed jobs, issued/completed phases, context occupancy, maximum wait,
and first/last completion clocks for identical input sequences.

If either bypass becomes the new critical path, do not keep adding bypasses.
Use its registered selection/data boundary or revisit the P/F distribution.
Any context-count increase is an explicit measured fallback, with area impact
and public/internal parameter checks accounted for.

9. WORK PACKAGE O1: REMOVE RAW FAULT FANOUT FROM OWNER INITIALIZATION
===============================================================================

9.1 Diagnose the actual connection

The report names owner_mask_lifetime_fault_q and the UV lifetime fault as major
launch families [S01, S02]. In the inspected RTL, the island ORs these into
lifetime_admission_block_w. That signal gates the atomic owner/RCP admission.
The owner's resulting adm_fire_c participates in initialization of the wide
per-slot control arrays [S05, S06].

There is no generic owner-reset input in this path that can simply be pipelined.
The timing objective is to prevent a distant fault reduction from traversing
admission qualification, slot decode and the many state-update muxes in one
cycle. Confirm the full path before choosing the precise RTL cut.

The source also directly aliases owner output valid at the island boundary.
Preserve the existing outer Packet-C/D fault/cancellation handling. Do not add a
new global valid mask and assume that it is equivalent to the report's phrase
"publication blocking." Retracting a held valid can lose an accepted owner.

9.2 Preferred architectural candidate: capture an accepted admission event

Keep the externally observable admission edge E exactly where it is:

  - The existing canonical lifetime predicate blocks admission on the same
    visible fault cycles as before.
  - Owner credit is reserved at E.
  - Tail/generation progression belongs to E.
  - The accepted owner identity is issued at E.
  - RCP admission and descriptor/material/UVW writes remain atomic at E.
  - Capture init_pending = {valid, slot, generation, required_mask} at E.

Apply the many per-slot initialization writes at E+1 using this registered
accepted-event record, rather than the current external admission predicate.
The record is about work already accepted; it is not a second allocator.

One pending event can be committed while the next is captured. The event pipe
must accept one admission per clock under legal credit/fence conditions. The
existing registered context-bank write already supplies part of this structure.
Reuse it where fields and timing are actually identical, not by approximate name.

9.3 Logical ownership exists before delayed physical initialization

Between E and E+1, the admitted slot is logically reserved/live even though some
physical per-slot arrays still contain the previous occupant's bits. Every reader
that can inspect that slot during this interval must see the logical new state.

Use the pending identity as a narrow bypass at the relevant addressed snapshot
or decision point. Do not build a second 64-slot speculative scoreboard. Do not
feed a whole-array combinational overlay into every owner decision and recreate
the very fanout cone being removed.

The event contains generation as well as slot. Never match pending state solely
by slot. Stale previous-generation returns must remain stale even when their
slot is currently pending for a new owner.

Inventory all consumers, including C1 snapshots, immediate issue notifications,
zero-required-mask readiness, read-publication checks, generation-shadow
assertions, fence logic and any debug probes used as evidence. A consumer omitted
from this inventory is a correctness bug, not an acceptable transient mismatch.

9.4 Event ordering is the hard part

The existing immediate admission initialization has highest same-edge precedence
because it creates the new occupant on that very edge. The delayed event refers
to a creation from the PREVIOUS edge. Its precedence must therefore change.

At E+1:
  1. Establish the pending owner's initialized base state.
  2. Apply legal current events to that new state in the existing semantic order.
  3. Commit the resulting state once.

Do not place the delayed initializer last and erase a legitimate earliest issue
or claim that arrived for the newly admitted owner. Likewise, do not apply stale
old-generation events before silently relabelling their result as the new owner.

Write an explicit collision matrix for:
  pending init + current admission to another slot;
  pending init + matching issue;
  pending init + stale issue;
  pending init + earliest matching return;
  pending init + old-generation return;
  pending init + zero-mask ticket creation;
  pending init + final/retire attempt;
  pending init + generation wrap/fence event;
  pending init + lifetime fault visibility;
  pending init + reset.

Return C0/C1/C2 claim forwarding and the existing issue/combine-notification
forwarding windows remain intact. If a pipeline boundary changes snapshot age,
rederive the forwarding window from its actual edge calendar. Do not assume the
old one-cycle window still covers an extra delayed state event.

9.5 Fault and reset rules

A fault that blocks new admission must not retroactively erase the initialization
of an owner already accepted. The pending accepted event either completes under
the existing drain/barrier semantics or is invalidated by the actual reset law.

Do not register the global fault level and use the delayed level as the new
admission permission. That permits an additional admission on a fault-visible
cycle. Preserve the baseline event/visibility distinction: a newly detected
cause and an already asserted sticky fault are not automatically the same edge.

Only reset clears reset-only faults. Recoverable frame clear is not a license to
clear lifetime ownership or a pending initialization record. Include pending
initialization in quiet, live/reservation accounting and structural assertions.

9.6 Extend event capture to combine-pop and join-validation state

The latest cone review also names combine-pop to completion reservation and the
island's join_validation_pending_q [S16]. Apply the same distinction between an
accepted logical event and its later wide physical updates. Capture the complete
accepted combine owner and generation; reserve its logical capacity immediately.
Do not allow another claimant to see the physical reservation as free while the
accepted event is pending.

The existing READ_LATE source check already forwards a recent cmb_accept event
with full slot/generation comparison. Extend that forwarding window if a new
registered pop changes when cbi/reservation state becomes visible. Do not add a
second nominal event register without auditing the existing one.

If join_validation_pending_q is physically initialized from the registered
admission event, logical validation-pending still starts on original admission.
Provide a narrow pending-event match at a consumer that can observe the interval,
or prove structurally that the consumer cannot run until physical initialization.
Count-zero owners are the important case. No stale false-pending bit may authorize
COMBINE for the newly admitted generation.

9.7 Lower-risk implementation alternative

If the accepted-event pipeline cannot be proven within this bounded change,
retain immediate owner initialization and investigate local permission/predecode
replication. That is a different candidate, not something to add on top blindly.

Copies must be driven from the same source-next-state fault events on the same
edge as the authoritative flag, with identical reset and sticky precedence.
Registering an already registered OR is not equivalent. Any replicated local
permission must be checked against the canonical predicate on every cycle,
including all fault sources and same-edge admissions.

Preservation/duplication attributes are tool-specific and must be verified in the
mapped hierarchy. Identically driven registers may otherwise merge back into a
single high-fanout source. This route may help routing but has no promised gain.

For either route, prove the relevant owner endpoints no longer have a same-cycle
cone from a distant lifetime-fault OR through full admission initialization.
Merely renaming signals or adding an unused local fault register is not a fix.

10.0 PREFERRED: preserve the three elastic slots and public latency

term, token and channel, and compute the short final sum/round from those held

  V.pv    = signed27((b1_b - b1_a) * signed9({0,fv}))

  V.token = b1_token
  V.chan  = b1_channel

  sum = (sign_extend27(V.a) << 8) + V.pv

10.3 Elasticity and exact capacity

The four-stage lane has four valid bits and storage slots. In the simple local
implementation:
  ready_B2 = !valid_B2 || out_ready
  ready_V  = !valid_V  || ready_B2
  ready_B1 = !valid_B1 || ready_V
  ready_B0 = !valid_B0 || ready_B1

Each register updates only when its own stage is ready, and copies old upstream
state. Token, channel, arithmetic payload and validity move together. Hold the
public output immutably while valid and not ready.

The original occupancy output is TWO BITS. Four live slots require THREE BITS.
Update the timing variant, island signal widths, wrappers, probes, casts and
tests. An occupancy that reports zero for four live jobs can produce false quiet
or misleading proof results even when the pixels happen to look correct.

All four colour-channel lanes remain present. The current island remembers each
channel's request acceptance and response arrival separately; do not replace this
with a requirement that all four lanes accept/respond on one exact edge.

If the expanded ready chain becomes critical, use a bounded credit/skid cut with
real reserved capacity. Registering ready alone loses data when a downstream

10.4 Architectural latency

Specify latency by edges, not ambiguous "four cycles" prose. If an input is
accepted at E0 into B0, then horizontal B1 is captured at E1, V at E2, output B2
at E3, and the earliest pre-edge-qualified output handshake is E4.

The current baseline's earliest output handshake is E3 under that convention.

counts again. The existing dual18 horizontal proof remains applicable only if its
actual signed inputs and both distinct outputs remain connected.

11. CONDITIONAL B2: PROTECT THE ONE-ACTIVE-BILINEAR-SAMPLE LOOP
===============================================================================

Apply this section ONLY if the four-slot BIL2 fallback is selected. The preferred
three-slot product-register retime preserves the existing class calendar and does
not require these edits.

This is a second throughput constraint found directly in the island [S06]. It is
not addressed by simply saying that a retimed leaf has II=1.

The island has one bil_busy_q sample, one captured token/data/metadata bundle,
four request-pending bits, four seen bits, and one held completed tuple.
bil_capture_c currently requires !bil_busy_q. bil_busy_q clears when the complete
four-channel result is assembled. A new sample therefore waits until the next
cycle even when completion and new cache data are both available.

With one extra arithmetic stage, leaving this loop unchanged adds a cycle per
bilinear sample at this boundary. Avoid that hidden rate reduction.

11.1 Primary candidate: complete and refill on the same edge

Allow a new BIL sample capture when:
  no sample is active, OR the old active sample completes on this edge.

The old completion must be computed entirely from the old active token,
metadata, saved channels and current matching lane arrivals. Capture the next
sample's cache data/token/metadata separately on that edge.

Sequential priority must be rewritten intentionally:

  A. Form/write the OLD completed terminal tuple when old_complete is true.
  B. If new_capture is true, initialize the NEW active sample and keep busy=1.
  C. Else if old_complete, clear active state.
  D. Else update old request-pending, seen and channel state normally.

The existing code has a later completion block that clears busy/pending/seen.
Simply broadening bil_capture_c while leaving that block last will erase the new
sample. This is an explicit implementation trap.

Keep sticky old identity-error events outside the capture-versus-update choice,
so an old mismatch is not swallowed by a simultaneous new capture. Keep terminal
output updates separate from active-sample updates. A stalled terminal tuple
cannot be overwritten.

When complete/refill occurs, old channel results are consumed and the old request
mask must already be fully delivered. The next request mask becomes 1111 for the
new sample after the edge; no lane receives a mixture of old texels and new token.

In an ideal always-ready class calendar, baseline capture E0 -> lane accept E1 ->
old lane output E3 -> assembly E4 -> next capture E5 becomes retimed capture E0 ->
lane accept E1 -> output E4 -> assembly AND next capture E5. This restores the
five-edge initiation interval at this particular boundary. It is an illustrative
calendar, not a measured island benchmark.

11.2 If the new ready feedback is physically too long

Complete/refill can introduce a path from terminal readiness or four-channel
completion through cache acceptance and active-register enables. Inspect that
path; do not solve timing in the arithmetic and recreate it in the control.

A bounded fallback is one registered prefetched BIL input bundle:
  data64 + token18 + metadata40 + valid = 123 bits.

The prefetch slot absorbs the next already identified cache response. When the
active sample completes, the prefetched bundle becomes active on that same edge.
The next sample's launch no longer depends on a live cache payload path. Maintain
explicit capacity for active plus prefetched work and the existing held terminal.
No unbounded queue or second set of filter lanes is required.

Count the prefetch entry in quiet, reset and owner lifetime. Release the cache
response and metadata ownership only on their true accepted capture. Do not read
live metadata again when the prefetched sample starts later.

Choose either a proven direct complete/refill boundary or this bounded buffered
version after inspecting the mapped control path. Do not build both speculative
frameworks. Record whether startup latency changes separately from steady-state
class throughput.

12. WORK PACKAGE D1: EXACT DIVIDER PREPARATION WITH ONE CARRY CHAIN
===============================================================================

The reported ATTR3 path is inside zhao_raster_attrdiv_v2, from dividend_r[0] to
dividend_r[96] [S02, S07]. It is not evidence that the three-DSP setup worker must
be abandoned.

The divider already separated rounded-numerator capture from magnitude formation.
The negative PREP expression is now:

  (-x + d - 1) mod 2^98

where x is the 98-bit captured signed-rounded numerator representation and d is
the zero-extended 47-bit denominator.

The exact bit-vector identity is:

  (-x + d - 1) mod 2^98 = ((~x) + d) mod 2^98

because two's-complement -x is (~x)+1 and the explicit -1 cancels that carry-in.
Implement one explicitly 98-bit addition of the bitwise complement and denominator.
Do not retain a separately materialized negate and decrement in front of it.

This retains the same D_PREP edge, register bank and state sequence. Positive
preparation remains a direct copy. Zero-area and saturation fast paths remain
unchanged. The original rounded numerator num+floor(area/2), signed saturation
thresholds, 98-step radix-2 division and held-output handshake remain untouched.

Be exact about width: ~x must complement all 98 bits, and d must be zero-extended
to 98 bits. Do not complement a narrowed positive magnitude or zero-extend a
negative 96-bit numerator before the original signed rounding capture.

The host checks compared the identity on 100,024 wide cases and the complete
signed rounded/saturated quotient law on 25,245 cases. The algebra is exact for
all 98-bit bit patterns. RTL equivalence and whether Quartus already performs
this normalization still require checking; the physical benefit is not measured.

If one explicit 98-bit carry chain still misses the reserve, consider a
latency-neutral 49/49 carry-select formulation before spending a preparation cycle:

  low50 = zext50(~x[48:0]) + zext50(d47);
  high0 = ~x[97:49];
  high1 = (high0 + 1) modulo 2^49;
  result = {low50[49] ? high1 : high0, low50[48:0]}.

All denominator bits fit in the lower 49-bit half. The high increment is computed
in parallel with the low addition, and the low carry selects the high result.
This trades some logic/select fanout for shorter carry dependence, with no extra
state or changed divider latency. Inspect mapped structure; this is not a measured
improvement and may be unnecessary if Quartus already factors the carry well.

The new repository plan instead proposes two sequential 49-bit preparation steps
[S16]. That is a valid fallback only with an explicit latency contract: preserve
the original high half while updating the low half, hold the carry, and update the
high half on the next edge. Do not complement an already complemented half again.
Recheck fast zero/saturation paths, first-row seed and each normal row's divide
calendar. One extra PREP cycle is not magically free merely because RUN has 98
iterations. The original single-carry identity remains the arithmetic law.

Also inspect the iterative remainder compare/subtract and final quotient-sign
paths in the near-critical inventory. A proven shared subtract/borrow formulation
may remove duplicated comparison work, but do not insert a register inside each
division iteration or silently change radix to hide the timing problem. Those
changes would affect the per-row service budget and the prior ATTR3 schedule.

17. WORK PACKAGE Q1: WRAPPER CLEAR FIRST, SAFE QUIET IF STILL NEEDED

17.0 REQUIRED: repair the characterization wrapper's clear-request feedback

The generated fit wrapper currently assigns:
  frame_fault_clear_valid_w = frame_fault_w && frame_fault_clear_ready_w.
This was read directly from the generated wrapper [S17]. Its downstream ready
and upstream fault can contain the same large subsystem control families. Do not
ignore the path because it is "only the wrapper"; it is in the measured design.

Replace it with a registered held recoverable-clear request. Use a small RUN,
CLEAR_PENDING, RECHECK control sequence: latch a recoverable fault request,
assert clear valid independent of ready while pending, consume it on the actual
handshake, then recheck the resulting fault level on a later edge before allowing
new synthetic jobs. A fresh fault that wins over clear must remain actionable;
do not wait forever for it to fall without another clear request.

Bring the separate lifetime_structural_fault output into the wrapper's control
logic. A lifetime fault must never be treated as a recoverable clear request or
authorize synthetic traffic to resume. A fatal arriving during an already held
clear request must follow the clear channel's documented cancellation/reset law;
do not retract a held offer arbitrarily. Clearing recoverable state cannot clear
the fatal condition.

Stop generating NEW synthetic jobs while clear is pending/rechecked or fatal is
latched. A job already offered must still be held or accepted by the existing
abort sink, not silently withdrawn to manufacture quiet. Preserve deterministic
legal activity and all original datapath observability. Add directed tests for
clear backpressure, clear/fault coincidence, fatal arrival and resumption.

Edit the generator/template identified by
  tools/quartus/gen_raster_texture_v3_fit_top.py
and regenerate the wrapper/manifest. Do not hand-edit the GENERATED FILE only.
Bind this wrapper revision in the new measurement and disclose the boundary
change. Do not credit all resulting timing improvement to production RTL.

After this narrow fix, inspect whether the deep internal quiet/clear path still
needs a registered certificate. Sections 17.1-17.6 specify that safe fallback; do
not add it automatically if the wrapper fix plus other cuts already resolves the

17.1 What the names conceal

The island's q_owner_idle, q_rcp_idle and many other q_* terms are combinational
aliases in the inspected RTL, not registered certificates [S06]. data_quiet is
a large AND over idle terms and the absence of many pending offers. quiet_o adds
configuration, palette and external-offer conditions. frame_fault_clear_ready_o
is directly quiet_o, and its accepted clear enables several 32-bit counter
baseline captures.

A measured path from owner iss0t_v_q to owner_src_unpublished_base_q can therefore
be an occupancy -> deep quiet -> clear-enable path, rather than a slow addition
of the counter value. Inspect the complete path before changing counters.

17.2 Conservative certificate

Define raw_full_quiet as the existing complete quiet predicate, updated to include
all new Timing4 state. It must include both internal state and all external
sources that could create work or invalidate the empty condition.

Proposed certificate:
  at edge E:
    quiet_cert_q <= raw_full_quiet_before_E
  externally during a cycle:
    quiet_o = quiet_cert_q && !external_offer_now && !reset_or_init_block

Reset quiet_cert_q to false. It may become true only after the complete machine
has been observed empty. It can assert one cycle later than the old exact
combinational quiet, which is conservative. Any new external offer revokes public
quiet immediately, before its possible acceptance.

The safety argument requires an explicit invariant: when all enumerated internal
state is empty, no internal source can generate new work except an enumerated
external ingress/reset/configuration transition. Prove that invariant against
actual RTL, including delayed notifications, counters/events, speculative reads,
initialization engines and wake-up timers. The host model checks the argument
under this assumption; it cannot prove that the real state inventory is complete.

17.3 Do not implement the tempting broken variant

This is unsafe:
  internal_empty_q <= internal_empty
  quiet_o = internal_empty_q && !external_offer_now

An external offer can be accepted on the edge that samples internal_empty=true.
The offer disappears next cycle, but new internal work now exists. The stale
empty register and absent current offer can falsely claim quiet.

Sampling FULL quiet, including offers on the sampling edge, closes that gap. A
separate sticky invalidation/credit protocol could also close it, but do not
invent another control framework when the complete predicate already exists.
The included model contains this specific counterexample as a negative control.

17.4 Required inventory

In addition to every existing quiet term, include:
  combiner P, any optional F, WB bypass response in flight;
  pending owner initialization and any local barrier transition;
  BIL V stages, active/refill and optional prefetched BIL sample;
  reciprocal result head and UVW read response;
  raw and validated descriptor responses;
  AUX Ain and all owed responses;
  any delayed fault/counter event used by the new implementation.

External invalidators must include the existing fragment offer, cache fill data
OR denial, Sheet response, configuration command/response, palette load and any
new ingress. Keep offers in the predicate even where the input would currently
be refused. Dropping unsolicited response visibility can falsely permit clear.

Do not infer quiet only from accepted/completed counter equality. Do not infer it
only from owner live count. Do not ignore a held output because downstream is
currently not ready. Do not clear a pipeline to manufacture quiet.

17.5 Counter baseline and fault ordering

Use the short registered certificate for the clear handshake after its safety
conditions pass. Preserve the current baseline-capture and set-dominates-clear
law. A new event on a clear edge must remain visible, not be absorbed into the
new baseline or hidden by a delayed event pulse.

If counter updates are retimed, either keep their pending events nonquiet until
posted, or explicitly preserve epoch alignment. Never sample a stale counter as
baseline and then relabel its later update as a new frame error accidentally.
Conversely, never capture the updated counter in a way that erases a same-edge
real fault.

A lifetime structural fault is still reset-only. The quiet certificate does not
make frame clear capable of recovering a corrupted ownership namespace.

17.6 Timing expectations

This change moves a deep reduction to a small certificate destination and removes
it from many baseline/control enables. It does not guarantee the reduction itself
is under the margin. Inspect raw_full_quiet -> quiet_cert_q after mapping. If it
remains long, use component-level proven empty certificates with safe immediate
ingress invalidation, not an arbitrary delayed AND of stale idle signals.

18. SMALLER RESIDUALS AND WHY THEY MUST NOT BE IGNORED
===============================================================================

The report's "other" family contains 94 negative launch rows. Its worst named
example is the RCP-token-to-UVW path addressed above, but fixing that example does
not prove the other 93 disappear. Likewise, 50 owner-control rows can contain
several distinct enable and payload cones.

Before freezing Timing4, assign every negative family and every low-margin module
pair to one of these dispositions:

  FIXED STRUCTURALLY:
    The RTL now contains a named register/shortened arithmetic boundary that
    breaks the reported causal chain. Verify its live selection in mapping.

  EXPECTED TO IMPROVE INDIRECTLY:
    A fanout or placement change may affect it. This is weaker evidence; retain
    it in the first post-fit review and do not declare it closed beforehand.

  UNCHANGED BUT ADEQUATE:
    Only valid for a path whose existing margin already exceeds the chosen
    threshold under the corresponding clock relationship and corner.

  UNRESOLVED:
    Inspect it before pretending the primary batch is a comfortable-closure plan.

Particular checks:

  - Tile-control endpoints may be driven by abort or job-ready enable logic, not
    source-ID arithmetic. The captured attribute verdicts should terminate one
    contributing chain, but inspect remaining stage/quiet conditions.

  - Owner read-publication error counters can depend on cbi/recent acceptance
    forwarding. Do not widen that path while inserting owner initialization.

  - AUX protocol-fault reductions and unsolicited-response sinks may remain
    visible at the wrapper after input arithmetic is retimed. Keep fault output
    timing honest rather than declaring such ports unimportant.

  - Material saturation counters should use the shortened finish predicates;
    leaving a second copy of the old wide function solely for counters preserves
    the critical arithmetic even when the pixel path improves.

  - A deeper bilerp ready chain, direct complete/refill path or completion queue
    bypass can itself become a new critical control path. Analyze them by name.

  - Wide source or continuation fields do not need fresh reset muxes simply
    because another valid stage is added. Reset valid bits; leave invalid payload
    unspecified where the existing contract allows it.

Do not add an extra pipeline stage to every residual blindly. First identify the
actual logic and whether a small predicate capture or algebraic simplification
will remove the same path with less state.

19. PROPOSED RESOURCE BUDGET AND WHAT IT DOES NOT PREDICT
===============================================================================

Retain 30 physical DSPs as the primary Timing4 target. None of the proposed main
changes requires another multiplier. Do not silently accept 31 or 32 because a
new expression inferred differently. Diagnose it and request an explicit trade
decision if retaining an extra DSP becomes the best supported option.

A gross register inventory for the basic changes is approximately:

  Combiner source stage                              222 bits
  Four BIL vertical product stages                   264 bits
  AUX raw input                                     240 bits
  Reciprocal result head                             46 bits
  Validated descriptor response                     305 bits
  Owner accepted initialization event                19 bits
  Attribute verdicts                                  2 bits
  Quiet certificate                                   1 bit
  Explicit completion-forward row/control          ~54 bits
                                                    ---------
  Gross illustrative new register storage         ~1,153 bits
  Optional BIL prefetch                             +123 bits

This is NOT an ALM prediction and not a claim that each bit survives synthesis.
Some fields replace or retime existing registers; some duplicated control may
collapse; some registers may be absorbed into device primitives; new muxes,
control and routing duplication can consume additional logic. Exact widths are
profile-dependent and must be derived in RTL.

The latest plan's preferred three-slot BIL retime, compact descriptor verdict,
and A0 fault-fact capture avoid much of the FULL-STAGE fallback inventory above.
Using those preferred choices changes the gross estimate approximately to:
  combiner source222 + BIL replacement148 + RCP head46 + owner event19
  + attribute verdict2 + a few descriptor/AUX/clear control bits,
  plus optional completion forwarding and any deliberately retained finish stage.
That is roughly 450-550 additional raw register bits before F/other control,
not an ALM prediction. Do not add both preferred and fallback costs together.
The full-stage 1,153-bit inventory is retained to make fallback cost visible.

The short finish and divider transformations may recover logic that offsets some
of this storage, but no ALM saving is booked before the fit. Likewise, moving
wide payload behind synchronous reads should preserve or improve RAM inference,
not simply turn storage into more fabric registers.

Proposed design review guide, not a replacement for the owner's resource contract:
  Prefer a connected ALM increase of no more than roughly 500 over 13,195.
  An increase above roughly 750 deserves explicit attribution before adoption.
  Do not sacrifice correct throughput merely to meet that guide, and do not call
  it a whole-machine budget. A measured trade is preferable to an invented one.

A large increase usually warrants checking for:
  hidden context-count doubling;
  loss of M10K inference from reset/decoding on RAM outputs;
  copied owner planes rather than one bounded in-flight source bundle;
  duplicate arithmetic in counters or dead migration branches;
  fanout-buffering/register duplication that the source estimate did not include;
  a new general scheduler for a job that needed only one event register.

The 71 critical RAM blocks and 92,964 fitted payload bits are the baseline to
reconcile, not a magical fixed count that every legal retime must reproduce.
Critical payload stores must still infer. Any changed memory count needs a
named reason, not a silent unexplained shift into flip-flops.

21. VERIFICATION CONTRACT: TRANSACTION IDENTITY, TIMING AND CAPACITY
===============================================================================

21.1 Preserve independent oracles

Use the current R9 material law, the retained three-stage BIL2/V2 comparison and
the current attribute divide law as reference. New reference code must not be
written by mechanically copying the new RTL implementation; that merely makes
the same mistake twice.

The current BIL2 differential [S14] is cycle-exact: it compares ready, valid,
identity, occupancy and idle each cycle, then compares new output on the old
output's handshake. Removing only its same_control assertion is not a valid
latency-aware test. Its data scoreboard would still be using the wrong schedule.

Retain that test unchanged for the baseline candidate. For BIL2T, use independent
accepted-input and output-handshake accounting for each design, or drive each
with its own source cursor through the same logical transaction sequence. Match
results by test transaction ID/owner/token/channel, not by the current clock.

Check the intended new fixed latency in an unstalled test and sustained acceptance
rate in a saturated test separately. Semantic equivalence alone can hide a
throughput regression; cycle equality cannot be demanded where latency changes
were explicitly authorized.

21.2 Minimum directed arithmetic matrix

Material:
  all eight recipes; exact sample-count legality; zero-sample PASSTHRU;
  required versus unrequested status bits; independent true sample 2 and AUX;
  alpha retention versus MASK alpha product;
  signed LERP at low product bytes 127/128/129;
  MOD2 at products around 32704 and all endpoint byte rails;
  saturation witness and per-recipe meaningful-product counts;
  malformed material and source-error terminal colour/status/index/tag.

Bilerp:
  all 16 zero/255 texel rail patterns across all 65,536 fraction pairs;
  diverse full-byte random inputs, unequal horizontal products;
  channel permutation, token substitution and last-channel delayed arrival;
  no intermediate rounding and exact final ties.

Divider/attributes:
  negative exact halves, zero denominator, saturation on both signs;
  minimum/maximum signed96 numerators and denominator47 rails;
  signed 98-bit preparation representation;
  sparse coverage masks, row transitions and global-min-X tile offset;
  coordinate mismatch, last-bit disagreement and invalid lane0 inverse-W range.

21.3 Transport and occupancy matrix

For every new stage or pending event:
  reset while empty and while each possible occupancy is present;
  arbitrary output stalls, including stalls beginning on a response-arrival edge;
  simultaneous consume/refill;
  source payload changes while invalid;
  held valid payload that must not change;
  full capacity, last free entry, pointer wrap and recovery after backpressure;
  finite drain with no dropped, duplicated or invented transaction;
  quiet must remain false until the actual last owned work is gone.

For the four-stage bilerp specifically, reach occupancy four and observe four,
not zero. For the combiner, test a stalled public output with prefetch and read in
flight together. For WB forwarding, fill the response reservation immediately
before another final result appears.

21.4 Owner collision and fault matrix

At least these relationships must be exercised with full slot/generation identity:
  prior accepted init versus earliest issue, TMU return and AUX return;
  simultaneous TMU/AUX terminal traffic;
  duplicate same-owner same-sample returns on adjacent cycles;
  a stale generation while the slot is pending for reuse;
  zero-required-mask owner readiness;
  COMBINE accept/read/final/release coincidence;
  reset while an accepted init event is pending;
  every lifetime fault source on cycles adjacent to admission;
  recoverable frame clear versus a same-edge new event;
  return/refusal draining after admission is blocked.

Check that the new pending-event priority cannot overwrite legitimate recent
issued/claimed bits. Check that no pending owner is mistaken for an old published
owner by source-read validation.

21.5 Connected performance traces

Run the same deterministic workload definitions on Timing3 and Timing4 with the
same virtual memory/service schedules. Include:
  all one-phase material recipes under saturated admission;
  repeated DETAIL_LIGHT and mixed one/two/three-phase material streams;
  CLUT, nearest, bilinear and refusal-class interleaving;
  sustained bilinear samples with all channels and metadata always available;
  delayed single bilinear channel and held terminal output;
  dense and sparse attribute coverage, multiple rows and tiles;
  count-zero fragments, maximum owner pressure and full-context stalls;
  configuration/refusal/fault activity near the end of a frame.

Report first-result latency, last-result latency, steady-state accept/complete
rates, completed work per defined interval, maximum occupancy, and total frame or
tile clocks. An authorized fixed startup/drain latency increase is not the same
as a worse steady-state rate; quantify both. It is only acceptable where the
existing frame/workload contract still passes with its required reserve.

Do not claim that a faster MHz number compensates for an unapproved cycle-rate
loss. The console still intends to operate at 100 MHz. Compare useful work per
100 MHz clock against the actual workload obligations.

22. DELIBERATE FAILURE CONTROLS
===============================================================================

Every major correction needs a test that detects a plausibly wrong version, with
a distinct expected failure signature rather than a generic simulation crash.

Recommended controls:

  M1: advance source payload without context/phase; use the next live RAM output
      instead of the captured source on one phase.
  M2: use l>=128 for negative borrowing; omit the MOD2 saturation witness;
      unit-round before doubling.
  M3: enqueue a continuation that was bypassed; read old completion RAM data on
      a forwarded write; free a context at WB rather than output handshake.
  O1: delayed init has highest precedence over earliest matching issue;
      forward pending state by slot but not generation;
      gate admission using a one-cycle delayed global lifetime fault.
  B1: retain two-bit occupancy for four stages; fail to carry token or channel
      through V; round a horizontal intermediate.
  B2: let old completion clear a simultaneously captured new sample;
      swallow an old identity mismatch when a new sample arrives.
  D1: omit the floor correction by using -x+d rather than -x+d-1;
      complement fewer than 98 bits.
  D2: compute verdict from live inputs while the held payload is stalled;
      update verdict on consume without capture.
  R1T: read UVW using the next live RCP owner while retaining the previous token.
  E1: combine a staged descriptor with live generation/usable flags;
      gate away a bad response instead of delivering its refusal semantics.
  A1: delay issue notification relative to the expander acceptance;
      omit Ain from lifetime credit or quiet.
  Q1: register internal empty without sampling external offers;
      omit one new pending event; let frame clear erase a simultaneous new fault.

Retain the original positive controls as well. A renamed signal or a new generate
branch can accidentally disconnect a mutant while leaving the test executable
and its PASS text intact. Validate live mutation selection, expected observation
and no unrelated early abort that prevents reaching the intended check.

28. FINAL INSTRUCTION TO THE IMPLEMENTING AGENT
===============================================================================

The point is not to create more paperwork around 90.96 MHz. The point is to remove
specific long combinational dependencies while retaining useful work per clock.

Build the smallest coherent version of this batch that addresses the measured
families and the intended margin band. Keep ownership, phase scheduling, memory
ports and error behaviour explicit. Prefer exact shorter arithmetic and narrow
registered predicates before adding large queues. Where latency is added, repair
the real feedback loop or prove its workload budget, rather than quoting leaf
II=1 and moving on.

Target a comfortably timed 30-DSP G8A, not a lucky barely-green fit and not a new
machine with fewer features. Report actual measurements immediately and distinguish
100 MHz closure, 110 MHz reserve, and production adoption. A clean physical result
is the arbiter of timing and area; the proposal does not pre-award that result.
